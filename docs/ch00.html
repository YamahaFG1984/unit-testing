把第一个测试跑起来

原书默认你已经会搭环境、会运行测试。如果你还没有，这一章先把这道坎迈过去： 装什么、文件放哪、怎么跑、怎么看懂失败信息和覆盖率报告，以及怎么让它在每次提交时自动跑。 已经熟悉这些的话，可以直接跳到第 1 章。

本章目标

  • 知道测试框架在背后替你做了哪三件事
  • 在你选的语言里从零写出并运行第一个测试
  • 看懂一条失败信息
  • 把教程的配套示例跑起来（含需要真数据库的集成测试）
  • 生成覆盖率报告，并且不被它误导
  • 把测试接进 CI，让它每次提交都跑
ⓘ 这一章不是原书内容

本章和第 12 章是这套教程补充的。本章出现的命令都在教程仓库的 examples/ 目录里实际运行过。

测试框架替你做了什么

「测试」本质上只是一段普通代码：调用你的函数，检查结果对不对，不对就报错。 你完全可以手写一个 main 函数来做这件事。测试框架只是把三件重复的事接了过去：

💡 从第一天起就把单元测试和集成测试分开

单元测试要快到你愿意每改一行就跑一次；集成测试慢、还需要数据库。把它们放在不同目录（或打上不同标签）， 就能分别运行：写代码时反复跑单元测试，提交前再跑一遍集成测试。第 8 章会解释这背后的道理。

第 2 步：写被测代码

package hello;

public class Company {
    private final String domainName;

    public Company(String domainName) {
        this.domainName = domainName;
    }

    public boolean isEmailCorporate(String email) {
        String emailDomain = email.split("@")[1];
        return emailDomain.equals(domainName);
    }
}

class Company:
    def __init__(self, domain_name: str) -> None:
        self.domain_name = domain_name

    def is_email_corporate(self, email: str) -> bool:
        email_domain = email.split("@")[1]
        return email_domain == self.domain_name

export class Company {
  constructor(readonly domainName: string) {}

  isEmailCorporate(email: string): boolean {
    const emailDomain = email.split('@')[1]
    return emailDomain === this.domainName
  }
}

第 3 步：写测试

package hello;

import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class CompanyTests {
    @Test
    void an_email_on_the_company_domain_is_corporate() {
        var sut = new Company("mycorp.com");

        boolean result = sut.isEmailCorporate("alice@mycorp.com");

        assertThat(result).isTrue();
    }

    @Test
    void an_email_on_another_domain_is_not_corporate() {
        var sut = new Company("mycorp.com");

        boolean result = sut.isEmailCorporate("alice@gmail.com");

        assertThat(result).isFalse();
    }
}

from company import Company


def test_an_email_on_the_company_domain_is_corporate():
    sut = Company("mycorp.com")

    result = sut.is_email_corporate("alice@mycorp.com")

    assert result is True


def test_an_email_on_another_domain_is_not_corporate():
    sut = Company("mycorp.com")

    result = sut.is_email_corporate("alice@gmail.com")

    assert result is False

import { expect, test } from 'vitest'
import { Company } from './company'

test('an email on the company domain is corporate', () => {
  const sut = new Company('mycorp.com')

  const result = sut.isEmailCorporate('alice@mycorp.com')

  expect(result).toBe(true)
})

test('an email on another domain is not corporate', () => {
  const sut = new Company('mycorp.com')

  const result = sut.isEmailCorporate('alice@gmail.com')

  expect(result).toBe(false)
})

先别管为什么变量叫 sut、为什么中间空两行、为什么测试名是一句话 —— 这些是第 3 章的内容。现在只要它能跑。

⚠ 覆盖率是指示器，不是目标

这是第 1 章的核心论点之一：覆盖率很低能说明测试不够，覆盖率很高却什么都说明不了。 用它来找没测到的重要代码，不要拿它当 KPI。

接进 CI：让测试每次提交都跑

第 1 章说成功的测试集第一个特征是「融入开发流程」。最低限度的做法是：每次推送代码，由一台干净的机器把所有测试跑一遍。 这样「在我电脑上是好的」就不再是理由了。

下面是教程仓库实际在用的 GitHub Actions 配置（节选了 Python 部分；完整文件在 .github/workflows/examples.yml）：

name: examples
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest

    # 受管依赖用真的：给每次构建起一个 PostgreSQL
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_USER: crm, POSTGRES_PASSWORD: crm, POSTGRES_DB: crm }
        ports: ['54329:5432']
        options: --health-cmd "pg_isready -U crm -d crm" --health-interval 2s --health-retries 30

    steps:
      - uses: actions/checkout@v4

      - name: 应用数据库迁移
        env: { PGPASSWORD: crm }
        run: |
          for f in examples/db/migrations/*.sql; do
            psql -h localhost -p 54329 -U crm -d crm -v ON_ERROR_STOP=1 -f "$f"
          done

      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - working-directory: examples/python
        run: |
          pip install -e '.[dev]'
          pytest tests/unit          # 先跑快的
          pytest tests/integration   # 再跑慢的
💡 三条够用很久的 CI 规矩
  • 红了就先修，不要在红的基础上继续提交。第 4 章会讲「狼来了」效应：大家一旦习惯了红，测试就废了。
  • 不要用「重跑一次就好了」对付偶发失败。偶发失败说明测试之间有共享状态或依赖了时间，去找原因（第 2、11 章）。
  • 不要设覆盖率门槛。理由见上一节。

常见问题

现象多半是因为
框架说「没有找到测试」命名不符合约定。Python：文件要叫 test_*.py、函数要以 test_ 开头；TS：文件要叫 *.test.ts；Java：类要在 src/test/java 下，方法要有 @Test
Python 报 ModuleNotFoundError没在虚拟环境里，或者没执行 pip install -e .；示例项目靠 pyproject.toml 里的 pythonpath = ["src"] 让测试找到代码
集成测试报连接被拒绝数据库没起来。docker compose ps 看状态；端口 54329 被占用的话改 docker-compose.yml 并设置 CRM_DB_URL
改了迁移脚本但表结构没变示例里的迁移只在容器第一次初始化时执行。docker compose down -v 后重新启动
单独跑能过，一起跑就挂测试之间共享了状态。这正是第 2 章「隔离」要讲的事
在我电脑上能过，CI 上挂依赖了本机才有的东西：时区、文件路径、没提交的文件、数据库里的旧数据

小结

  • 测试框架只做三件事：按约定发现测试、逐个运行、汇报结果。测什么、怎么断言是你的事。
  • 生产代码和测试代码分开放；单元测试和集成测试也分开，以便分别运行。
  • 写完一个测试，故意让它失败一次，确认它真的在检查东西，顺便练习读失败信息：哪个测试、期望与实际、哪一行。
  • 配套示例 examples/ 里有 CRM 的三种语言实现：10 个单元测试不需要任何依赖，1 个集成测试连真实的 PostgreSQL。
  • 覆盖率报告要分部分看，用来找没测到的重要代码，不要当成目标。
  • 把测试接进 CI：每次推送都在干净环境里跑，快的在前、慢的在后，红了先修。

动手练习

  1. 按「从零写第一个测试」走一遍，包括故意弄坏再修好那一步。
  2. 把配套示例克隆下来，跑通你所用语言的单元测试和集成测试。
  3. 打开示例里的 User 类，把 changeEmail 里 delta 的 1 : -1 改成 -1 : 1。跑单元测试：哪些测试红了？失败信息告诉了你什么？
  4. 改回来。再把 MessageBus 里的 "NewEmail" 改成 "Email"。这次跑单元测试是红还是绿？集成测试呢？想想为什么（答案在第 9 章）。
  5. 生成 HTML 覆盖率报告，找到 domain 里没被覆盖的那几行。它们值得补一个测试吗？
