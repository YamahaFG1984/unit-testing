第 1 章

单元测试的目标

「要不要写单元测试」早就不是问题了。真正的问题是：为什么有的项目测试写了一大堆，开发却还是越来越慢、Bug 越来越多？ 这一章先把目标讲清楚 —— 目标错了，后面的技巧都是白费力气。

本章目标

  • 说出单元测试的真正目标：让项目可持续地增长
  • 理解「测试也是代码，代码是负债」这句话
  • 会算代码覆盖率和分支覆盖率，并知道它们为什么不能衡量测试质量
  • 知道一套成功的测试长什么样

现状：测试很多，日子却不好过

过去二十年，单元测试从「加分项」变成了「必选项」。很多企业项目里，生产代码和测试代码的比例在 1:1 到 1:3 之间（每写一行业务代码，配一到三行测试代码），极端的能到 1:10。

但你很可能见过这种项目：测试数量惊人，可是加一个新功能要改半个月，已经上线的功能隔三差五出问题， 每次改代码都要顺手修一堆「莫名其妙变红」的测试。测试不但没帮上忙，反而成了负担。

★ 讨论的重心变了

问题已经从「我们该不该写单元测试？」变成了「什么才算好的单元测试？」。 好测试和坏测试的差别不是个人口味，它直接决定项目的成败。这套教程（以及原书）回答的就是后一个问题。

ⓘ 什么是「企业应用」

原书的例子大多来自企业应用 —— 用来自动化或辅助一个组织内部流程的软件。它的典型特征是： 业务逻辑复杂、项目寿命长、数据量中等、性能要求不高。 不过书里的核心思想对任何软件项目都适用。

单元测试的目标

常听到一种说法：「写单元测试能让代码设计更好」。这话没错 —— 为了让代码能被测试，你不得不把它拆得更干净。 但这只是一个令人愉快的副作用，不是目标。

🔬 「能不能测」是一块单向的试金石

很难测 → 基本可以断定代码设计有问题（通常是耦合太紧，各部分拆不开）。这是一个靠谱的负面指标。
很好测 → 并不能说明代码质量好。解耦做得很漂亮的项目照样可能是一场灾难。这是一个不靠谱的正面指标。

记住「好的负面指标、差的正面指标」这个句式，本章后面讲覆盖率时还会再遇到它。

那真正的目标是什么？一句话：

单元测试的目标

让软件项目能够可持续地增长（sustainable growth）。关键词是「可持续」—— 从零开始把项目做大很容易，难的是一直保持住这个速度。

为什么没有测试的项目会越来越慢

这个现象有个名字，叫软件熵（software entropy）。熵是「系统混乱程度」的度量。 每改一次代码，代码库里的混乱就多一点；如果没有人持续地清理和重构，系统就会越来越复杂、越来越乱。 到最后，修一个 Bug 会带出三个新 Bug，改一处会坏好几处 —— 像多米诺骨牌一样。

测试的作用，就是在你下面张开一张安全网：无论是加新功能，还是为了适应新需求而重构， 它都能告诉你「原来能用的东西现在还能用」。

回归（regression）

一个原本正常的功能，在某次变更（通常是改代码）之后不再正常工作。在本教程里，「回归」和「Bug」可以当同义词用。

安全网不是免费的：写测试需要前期投入，有时投入还不小。但从长期看它是划算的， 因为没有测试持续把关的开发方式无法扩展。

好测试与坏测试

再看一眼图 1-1 里中间那条橙色曲线。坏测试在开始阶段确实有点用，下滑没那么快； 但大趋势没有变，停滞照样会来。光是「往项目里堆测试」达不到目标。

每一个测试都有两面：它带来的价值，和它的维护成本。成本来自这些地方：

⚠ 代码是负债，不是资产 —— 测试代码也一样

很多人下意识觉得：生产代码有成本，测试代码是「白送的」，所以测试越多越好。这是错的。

你引入的代码越多，潜在 Bug 的面积就越大，维护成本就越高。测试也是代码：它也会有 Bug，也需要维护。 应该把测试看成代码库里「专门负责保证正确性」的那一部分 —— 能用更少的代码解决问题，永远更好。

覆盖率：最常见的误区

既然测试有好有坏，那怎么衡量一套测试的质量？最常见的做法是看覆盖率。

覆盖率指标（coverage metric）

测试集执行到了多少源代码，范围从 0% 到 100%。

普遍的看法是「覆盖率越高越好」。可惜没这么简单。先说结论，再一步步看为什么：

★ 覆盖率是好的负面指标、差的正面指标

覆盖率很低（比如 10%）→ 可以肯定测试不够。
覆盖率很高（哪怕 100%）→ 什么都说明不了，测试集照样可能很烂。

代码覆盖率（行覆盖率）

最常用的一种，也叫测试覆盖率。公式很简单：

来看一个例子。isStringLong 判断一个字符串是不是「长」的（长度超过 5 就算长）， 测试只用 "abc" 试了一次： 

// 生产代码
public static boolean isStringLong(String input) {
    if (input.length() > 5)
        return true;      // ← 测试没走到这一行
    return false;
}

// 测试
@Test
void abc_is_not_long() {
    boolean result = isStringLong("abc");

    assertThat(result).isFalse();
}

# 生产代码
def is_string_long(text: str) -> bool:
    if len(text) > 5:
        return True       # ← 测试没走到这一行
    return False


# 测试
def test_abc_is_not_long():
    result = is_string_long("abc")

    assert result is False

// 生产代码
export function isStringLong(input: string): boolean {
  if (input.length > 5)
    return true        // ← 测试没走到这一行
  return false
}

// 测试
test('abc is not long', () => {
  const result = isStringLong('abc')

  expect(result).toBe(false)
})

按原书的数法（花括号也算一行），方法共 5 行，测试走过了 4 行，覆盖率是 4/5 = 80%。

分支覆盖率

分支覆盖率更精确一些。它不数行，而是数控制结构（if、switch 等）产生的分支， 看有多少条分支至少被一个测试走过：

问题一：执行过 ≠ 验证过

分支覆盖率比行覆盖率好，但它仍然不能衡量测试质量。第一个原因： 覆盖率只知道代码被执行了，不知道结果有没有被检查。

看这个版本的 isStringLong，它多做了一件事 —— 把最近一次的结果记到一个公开字段里：

public class StringChecker {
    public static boolean wasLastStringLong;

    public static boolean isStringLong(String input) {
        boolean result = input.length() > 5;
        wasLastStringLong = result;   // 结果一：隐式的（改了状态）
        return result;                // 结果二：显式的（返回值）
    }
}

@Test
void abc_is_not_long() {
    boolean result = StringChecker.isStringLong("abc");

    assertThat(result).isFalse();     // 只验证了结果二
}

was_last_string_long = False


def is_string_long(text: str) -> bool:
    global was_last_string_long
    result = len(text) > 5
    was_last_string_long = result   # 结果一：隐式的（改了状态）
    return result                   # 结果二：显式的（返回值）


def test_abc_is_not_long():
    result = is_string_long("abc")

    assert result is False          # 只验证了结果二

export let wasLastStringLong = false

export function isStringLong(input: string): boolean {
  const result = input.length > 5
  wasLastStringLong = result   // 结果一：隐式的（改了状态）
  return result                // 结果二：显式的（返回值）
}

test('abc is not long', () => {
  const result = isStringLong('abc')

  expect(result).toBe(false)   // 只验证了结果二
})

📖 原书作者讲的一个真实故事

多年前，作者所在的公司有几位开发者参加技术大会回来，决定推广单元测试。管理层很支持，于是下了一道全公司的硬性规定： 所有团队必须把代码覆盖率做到 100%，之后任何让覆盖率下降的提交都会被构建系统拒绝。

结果呢？被这条规定压得喘不过气的开发者开始找捷径。很多人不约而同地发现： 把测试用 try/catch 包起来、里面一个断言都不写，测试就一定能过。 大家开始机械地为了凑数而写测试。

这些测试没有带来任何价值，反而伤害了项目：它们占用了本该做正事的时间，之后还要花钱维护。 指标后来被降到 90%，再降到 80%，最后干脆取消了。

问题二：看不见外部库里的路径

好，假设你认真地验证了每一个结果，再配上分支覆盖率，总该可靠了吧？还是不行。 因为任何覆盖率工具都不会统计你调用的外部库内部的分支： 

public static int parse(String input) {
    return Integer.parseInt(input);
}

@Test
void parses_five() {
    int result = parse("5");

    assertThat(result).isEqualTo(5);
}

def parse(text: str) -> int:
    return int(text)


def test_parses_five():
    result = parse("5")

    assert result == 5

export function parse(input: string): number {
  return Number.parseInt(input, 10)
}

test('parses five', () => {
  const result = parse('5')

  expect(result).toBe(5)
})

分支覆盖率 100%，方法唯一的结果（返回值）也验证了。可这个测试离「测全了」还差得远：

这不是说覆盖率工具应该去统计外部库（不应该），而是说明： 覆盖率没法告诉你测试是否测全了，也没法告诉你测试够不够。

把覆盖率数字定成目标，会发生什么

想象医院里有个发烧的病人。体温高是一个有用的观察结果，说明病人可能有炎症。 但如果医院把「让体温正常」本身定成不惜一切代价要达到的目标， 那最「高效」的方案就是在病床旁边装一台空调对着病人吹。数字正常了，病一点没治。

💡 微妙但关键的区别

系统的核心部分有很高的覆盖率，是好事。
把很高的覆盖率定成硬性要求，是坏事。
低于 60% 基本是出问题的信号；但高的数字本身什么也不能说明。覆盖率只是通往高质量测试的第一步。

一套成功的测试集长什么样

说了这么多「不该怎么衡量」，那该怎么衡量？唯一可靠的办法是一个一个地评估测试集里的每个测试。 不需要一次做完，可以慢慢来。重点是：没有自动化手段能替你判断，你必须运用自己的判断力 （第 4 章会给你一把判断用的尺子）。

先从整体上看，一套成功的测试集有三个特征：

🔄

① 融入开发流程

自动化测试的全部意义在于不断地用它。理想情况下，每一次改动 —— 哪怕再小 —— 都要跑一遍。

🎯

② 只瞄准最重要的部分

代码库的各个部分并不值得同样的关注。测试的价值不仅取决于测试怎么写，还取决于它测的是什么。

⚖

③ 用最小成本换最大价值

只留下「价值远大于维护成本」的测试。这是最难的一条，也是本教程的主线。

测试的精力应该花在哪

对绝大多数应用来说，最重要的部分是包含业务逻辑的那部分 —— 也就是领域模型（domain model）。 测试业务逻辑，是时间投入回报最高的地方。

集成测试可以越过领域模型，验证整个系统协同工作的情况（包括那些不重要的部分），这没问题。但重心始终在领域模型上。 怎么把领域模型隔离出来，是第二部分（第 4–7 章）的内容。

「识别」好测试和「写出」好测试是两种能力

第三个特征（最小成本换最大价值）其实包含两种不同的本事：

能力需要什么打个比方
识别一个测试有没有价值一套参照系（第 4 章的「四大支柱」）听得出一首歌好不好听
写出一个有价值的测试参照系 + 代码设计能力自己能作曲

作曲比听歌难得多。写测试也一样：你不是在真空里写测试，测试和它背后的代码是纠缠在一起的。 不在被测代码的设计上下功夫，就写不出有价值的测试。 所以这套教程虽然讲的是测试，却会花很大篇幅讲代码设计。

💡 那用什么衡量「测试有没有在验证」

原书到此为止：覆盖率不行，要逐个评估测试的价值（第 4 章给出标尺）。教程在补充部分介绍了一种能自动回答这个问题的工具 —— 第 14 章的变异测试，那里有一个实测：把断言全删掉，覆盖率一点没变，被验证到的行为却少了一大半。

小结

  • 代码会自然腐化。每次改动都增加混乱（熵），测试是对抗这个趋势的安全网。
  • 单元测试的目标是让项目可持续地增长。「让设计更好」只是副作用。
  • 坏测试和没有测试的结局一样：要么停滞，要么每次发布都带一堆回归。
  • 每个测试都有价值和成本两面。只保留净价值为正的测试。生产代码和测试代码都是负债。
  • 「代码能不能被测」和「覆盖率」都是好的负面指标、差的正面指标。
  • 分支覆盖率比行覆盖率更诚实，但它不知道有没有断言，也看不见第三方库里的路径。
  • 把覆盖率数字定成硬性目标会产生反向激励。核心部分覆盖率高是好事，强制要求高是坏事。
  • 成功的测试集：融入开发流程；只瞄准最重要的代码（领域模型）；用最小维护成本换最大价值。

自测

团队的覆盖率是 95%，能说明测试质量很高吗？

不能。高覆盖率只说明代码被执行过，不说明结果被验证过，更看不到外部库里的路径。它只能排除「测试严重不足」这一种情况。

一个方法有 4 条分支，测试走了 3 条，行覆盖率是 100%。分支覆盖率是多少？哪个数字更可信？

分支覆盖率是 3/4 = 75%。分支覆盖率更可信，因为它不受代码排版和写法的影响。

为什么说「测试越多越好」是错的？

测试也是代码，也有 Bug，也要维护。一个净价值为负的测试（比如经常误报、又抓不到真问题）会拖慢整个团队。应该追求的是高价值测试的数量，而不是测试的数量。

动手练习

  1. 挑一种你熟悉的语言，把本章的 isStringLong 和它的测试敲出来，用覆盖率工具跑一遍 （Java 用 JaCoCo，Python 用 pytest --cov --cov-branch，TypeScript 用 vitest --coverage）。
  2. 分别用「5 行」和「3 行」两种写法，观察行覆盖率和分支覆盖率各自怎么变。
  3. 把测试里的断言删掉再跑一次。覆盖率变了吗？这个测试还有用吗？
  4. 打开你手头项目里的任意一个测试文件，挑三个测试，各用一句话写下：它带来了什么价值？上一次它变红是因为真 Bug 还是误报？
