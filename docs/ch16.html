ⓘ 怎么用

写代码时最常遇到的是这三个问题：这段代码该写哪种测试、这个依赖要不要换掉、 这个测试写得行不行。遇到具体的麻烦，直接跳到「遇到问题查哪里」。 第 1–11 章的结论来自原书；第 0、12–15 章是本教程的补充。

这个依赖要不要换成替身

依赖类型测试里怎么办
另一个领域类、值对象、工具函数进程内用真的
只有本应用读写的数据库受管集成测试里用真的；单元测试根本不该碰到它
和其他应用共用的数据库两者兼有别的应用看得到的表当作不受管依赖（替换）；其余的表当作受管依赖（用真的）
消息总线、邮件网关、支付等第三方接口不受管替换。优先手写一个记录调用的 Spy，放在最外层的适配器上
当前时间隐式的输入作为值或时钟显式传入（第 11 章、第 13 章）
日志看给谁看业务方要求的支持日志是可观察行为，当作不受管依赖来验证；给开发者看的诊断日志不测（第 8 章）
★ 一句话版本

Mock 用来验证「你的系统对外界说了什么」，不是用来把被测的类和它的邻居隔开。 只有跨出应用边界、外部系统看得见的通信才是可观察行为；应用内部的通信是实现细节。

四大支柱

三种测试风格

风格验证的是抗重构可维护性什么时候用
基于输出给定输入，返回值是什么最好最好首选。需要代码是没有副作用的函数 —— 把决策写成「函数式核心」
基于状态操作之后，对象或数据库的状态是什么好（只看公开的状态时）中等领域对象；集成测试里验证数据库
基于通信被测系统对协作者调用了什么最差，最容易绑住实现最差只用于跨出应用边界、发给不受管依赖的通信

出处：第 6 章。两个学派的区别（「隔离」指隔离测试还是隔离类）见第 2 章；本教程和原书都站在经典学派一边。

写一个测试的清单

@Test
void changing_email_from_non_corporate_to_corporate() {          // 名字：一句业务上的话
    var company = new Company("mycorp.com", 1);                  // 准备（Arrange）
    var sut = new User(1, "user@gmail.com", UserType.CUSTOMER, false);

    sut.changeEmail("new@mycorp.com", company);                  // 执行（Act）：一行

    assertThat(company.getNumberOfEmployees()).isEqualTo(2);     // 断言（Assert）：字面量
    assertThat(sut.getEmail()).isEqualTo("new@mycorp.com");
    assertThat(sut.getType()).isEqualTo(UserType.EMPLOYEE);
}

def test_changing_email_from_non_corporate_to_corporate():       # 名字：一句业务上的话
    company = Company("mycorp.com", 1)                           # 准备（Arrange）
    sut = User(1, "user@gmail.com", UserType.CUSTOMER, False)

    sut.change_email("new@mycorp.com", company)                  # 执行（Act）：一行

    assert company.number_of_employees == 2                      # 断言（Assert）：字面量
    assert sut.email == "new@mycorp.com"
    assert sut.type == UserType.EMPLOYEE

test('changing email from non corporate to corporate', () => {   // 名字：一句业务上的话
  const company = new Company('mycorp.com', 1)                   // 准备（Arrange）
  const sut = new User(1, 'user@gmail.com', UserType.Customer, false)

  sut.changeEmail('new@mycorp.com', company)                     // 执行（Act）：一行

  expect(company.numberOfEmployees).toBe(2)                      // 断言（Assert）：字面量
  expect(sut.email).toBe('new@mycorp.com')
  expect(sut.type).toBe(UserType.Employee)
})
检查项说明出处
三段结构：准备、执行、断言用空行分开。一个测试只有一轮；出现第二个「执行」就拆成两个测试第 3 章
「执行」只有一行需要好几行才能完成一个操作，说明被测代码的接口有问题（封装不到位）第 3 章
测试里没有 if 和循环测试应该是一条直线。要覆盖多种输入，用参数化测试第 3 章
名字是一句话讲给不懂代码的人也听得懂；不带被测方法的名字；不套固定格式第 3 章
被测对象叫 sut一眼分清谁是被测的、谁是配角第 3 章
准备代码的复用用工厂方法不要放进构造函数或全局的初始化方法里 —— 那会让测试互相耦合、读起来要来回跳第 3 章
期望值是字面量不在测试里把算法再写一遍第 11 章
只通过公开接口不测私有方法，不为了测试暴露私有状态第 11 章
验证的是一个行为，不是一个类或一个方法一个行为可以跨好几个类；一个类也可以有好几个行为第 2 章
异步：每个结果都等到了把期望值改错，确认它会红第 13 章

反模式速查

看到这个问题改成出处
为了测试把私有方法改成公开的测试绑住了实现细节通过公开接口间接测。私有方法复杂到必须单独测，说明里面藏着一个该抽出来的类第 11 章
为了断言而暴露私有字段同上像生产代码那样去观察：看它的行为产生了什么可见的结果第 11 章
测试里把算法又写了一遍代码错，测试跟着错把期望值写成字面量第 11 章
生产代码里有只给测试用的开关或方法代码污染把不同的行为放到接口的不同实现里第 11 章
Mock 一个具体类，只替换它的一部分方法这个类同时在做两件事把「做决定」和「和外界通信」拆成两个类第 11 章
代码里直接读系统时间测试结果依赖运行的时刻把时间作为值或时钟显式传入第 11 章
验证领域对象之间的调用内部通信是实现细节断言最终状态或返回值第 5 章
Mock 掉自己的数据库受管依赖的交互是实现细节；而且测不出真实的数据库问题集成测试里用真的第 8 章
Mock 第三方库的类你不掌握它的行为，Mock 出来的是你的想象写一个自己的适配器，Mock 适配器第 9 章
没有断言，或只断言「不为空」有覆盖率，没有验证断言具体的结果第 1 章、第 15 章
给覆盖率（或变异得分）定硬指标数字会被优化，测试质量不会把它当成发现漏洞的线索，不当成目标第 1 章、第 14 章
测试里用固定的 sleep 等结果又慢又不稳等到结果；或把时间换成替身；最后才是轮询加超时第 13 章

💡 只记一条的话

测试要验证的是「系统做了什么」，不是「系统是怎么做的」。 前者让你敢改代码；后者让你不敢改代码。这一页上几乎每一条规则，都是这句话在某个具体场合的展开。
