第 10 章

测试数据库

上一章解决了不受管依赖（Mock），这一章解决集成测试的最后一块拼图：受管依赖，也就是应用自己的数据库。 用真数据库跑测试能提供近乎无懈可击的保护，但搭起来不容易。我们从「开始写测试之前要先做好什么」讲起，再讲事务、测试数据的清理，以及怎么让集成测试保持短小。

本章目标

  • 做好测试数据库的三项准备：结构进版本库、每人一个实例、用迁移交付
  • 在生产代码里正确管理事务（仓储 + 事务 / 工作单元）
  • 在测试里每一段用独立的事务
  • 知道测试数据该在什么时候清理，以及为什么别用内存数据库
  • 用工厂方法、装饰方法、流式断言把集成测试缩短
  • 回答两个常见问题：读操作要不要测？仓储要不要单独测？
ⓘ 适用范围

本章以关系型数据库为例，但其中很多原则也适用于文档数据库，甚至纯文本文件存储。

测试数据库的前提条件

受管依赖在集成测试里要用真的，这比不受管依赖费事 —— 没法 Mock 了。动手写测试之前，先要把三件事准备好。 和测试里的几乎所有事情一样，这些做法即使不写集成测试也对你的数据库有好处。

① 把数据库放进版本控制

第一步是把数据库结构当成普通代码来对待，存进 Git。有些团队的做法是维护一个专门的数据库实例作为参照（「模型数据库」）：

把所有数据库结构的变更放进版本控制，你就有了唯一的事实来源，还能让数据库的变化和代码的变化一起被追踪。 任何对数据库结构的修改都不应该绕过版本控制。

参考数据也是数据库结构的一部分

说到「结构」，大家想到的是表、视图、索引、存储过程 —— 这些以 SQL 脚本的形式存在，任何时候都能用它们建出一个功能完整的、最新的数据库。 但还有一样东西属于结构却常被忽视：

参考数据（reference data）

为了让应用正常工作而必须预先填好的数据。比如 CRM 里建一张 UserType 表存放所有用户类型（客户、员工）， User 表通过外键引用它 —— 那么 UserType 表的内容就是参考数据，没有它用户根本存不进去。

💡 怎么区分参考数据和普通数据

应用能修改的，是普通数据；应用不能修改的，是参考数据。 参考数据要和表、视图一起，以 INSERT 语句的形式放进版本控制。

② 每个开发者一个独立的实例

对着真数据库跑测试已经够难了，如果还得和别人共用一个库就更难：不同开发者跑的测试会互相干扰； 不向后兼容的改动会卡住别人的工作。给每个开发者一个独立的数据库实例，最好就在他自己的机器上，这样测试跑得最快。

③ 基于状态 vs. 基于迁移的数据库交付

基于状态（state-based）基于迁移（migration-based）
版本库里存什么描述数据库当前应有状态的 SQL 脚本一个个把数据库从一个版本变到下一个版本的迁移脚本
数据库的状态显式隐式（要把迁移依次叠起来才知道）
迁移的过程隐式（由比对工具自动生成）显式（你自己写）
擅长处理合并冲突处理数据迁移

迁移通常就是普通的 SQL 脚本，也可以用各语言的迁移工具提供的 DSL 来写：

为什么选基于迁移

数据迁移（data motion）

改变现有数据的形态，使其符合新的数据库结构的过程。

「好处理合并冲突」和「好处理数据迁移」看起来差不多重要，但在绝大多数项目里，数据迁移重要得多： 只要应用已经上过生产，你手里就总有不能随便丢弃的数据。所以基于状态的做法在大多数项目里不实用 —— 最多在项目还没发布时临时用用（那时测试数据不重要，改一次库重建一次就行），发布第一个版本后就得切到基于迁移。

★ 迁移的规矩
  • 对数据库结构的每一次修改（包括参考数据）都通过迁移来做。
  • 迁移一旦提交到版本库，就不要再改。迁移写错了？新建一个迁移来修正，而不是改旧的。
  • 唯一的例外：错误的迁移会导致数据丢失时。

数据库事务管理

事务管理对生产代码和测试代码都很重要：在生产代码里它防止数据不一致；在测试里它帮你在接近生产的环境下验证与数据库的集成。

生产代码里的事务

到目前为止，CRM 的 Database 类在每次方法调用时都新开一个连接，每个连接背后隐式地开一个独立的事务。 于是控制器在一次业务操作里总共开了四个事务：读用户、读公司、存公司、存用户。

只读操作开多个事务没问题。但如果业务操作要改数据，这次操作里的所有更新必须是原子的。 否则可能出现：公司存成功了，存用户时数据库连接断了 —— 公司的员工数和库里实际的员工用户数对不上了。

原子更新（atomic updates）

以「全有或全无」的方式执行：一组更新要么全部完成，要么一点效果都不留下。

要避免不一致，需要把两种决定分开：

  • 更新哪些数据 → 交给仓储（Repository）：负责访问和修改数据库里的数据。示例里有两个：UserRepository 和 CompanyRepository。
  • 这些更新是保留还是回滚 → 交给事务（Transaction）：把数据更新整体提交或整体回滚。

之所以要分开，是因为控制器没法同时做这两个决定：只有业务操作的所有步骤都成功了，它才知道更新能不能保留； 而要走完这些步骤，它又必须先访问数据库、尝试更新。两者的生命周期也不同：事务贯穿整个业务操作；仓储是短命的，一次数据库调用结束就可以丢弃。 所以仓储总是工作在当前事务之上。 

public class UserController {
    private final Transaction transaction;
    private final UserRepository userRepository;
    private final CompanyRepository companyRepository;
    private final EventDispatcher eventDispatcher;

    public UserController(Transaction transaction,                // 接收一个事务
                          MessageBus messageBus, IDomainLogger domainLogger) {
        this.transaction = transaction;
        this.userRepository = new UserRepository(transaction);    // 仓储建立在事务之上
        this.companyRepository = new CompanyRepository(transaction);
        this.eventDispatcher = new EventDispatcher(messageBus, domainLogger);
    }

    public String changeEmail(int userId, String newEmail) {
        Object[] userData = userRepository.getUserById(userId);
        User user = UserFactory.create(userData);

        String error = user.canChangeEmail();
        if (error != null) return error;                          // 提前返回 → 没有 commit → 回滚

        Object[] companyData = companyRepository.getCompany();
        Company company = CompanyFactory.create(companyData);

        user.changeEmail(newEmail, company);

        companyRepository.saveCompany(company);
        userRepository.saveUser(user);
        eventDispatcher.dispatch(user.getDomainEvents());

        transaction.commit();                                     // 只有成功走到最后才提交
        return "OK";
    }
}

    @Override
    public void close() { /* 结束事务：commit 过就持久化，否则回滚 */ }
}

Transaction 有两个方法，配合起来保证只有快乐路径才会改动数据库：

  • commit()：把事务标记为成功。只在业务操作成功、所有修改都准备好持久化时调用 —— 所以它在 changeEmail() 的最后。任何错误（校验失败或未处理的异常）都会让流程提前返回，事务也就不会被提交。
  • close() / dispose()：结束事务，业务操作结束时无条件调用。之前 commit() 过就持久化，否则回滚。

调 commit() 需要做决定，所以由控制器来调；调 close() 不需要做决定，可以交给基础设施层 —— 也就是创建控制器并给它提供依赖的那个类（Web 框架的请求管道、依赖注入容器等）。

把事务升级为工作单元

工作单元（unit of work）

维护一份「本次业务操作影响到的对象」的清单。操作完成时，工作单元算出需要对数据库做哪些更新，并把它们作为一个整体执行。

维护修改清单、再生成 SQL，听起来工作量很大，但你不用自己做 —— 大多数 ORM 已经替你实现了工作单元模式：

语言ORM充当工作单元的类提交
C#（原书）Entity FrameworkDbContextSaveChanges()
JavaJPA / HibernateEntityManager / Session事务 commit() 时自动 flush
PythonSQLAlchemySessionsession.commit()
TypeScriptMikroORM / TypeORMEntityManagerem.flush() / 事务提交

🔬 非关系型数据库怎么办

大多数文档数据库（如 MongoDB）没有传统意义上的跨文档事务，原子更新只在单个文档内有保证。 它们从另一个角度解决不一致：要求你把文档设计成任何业务操作都不会同时修改多个文档。 文档比关系表的行灵活得多，一个文档就能装下很复杂的数据。 领域驱动设计里「一次业务操作不要修改多个聚合」的准则，目的也是这个。

集成测试里的事务

★ 准则

不要在测试的各个阶段之间复用数据库事务或工作单元。 集成测试里至少用三个：准备、执行、断言各一个。

为什么？在生产环境里，每次业务操作都有一个独占的工作单元实例：控制器方法调用前创建，调用后立刻销毁。 测试如果在三个阶段共用同一个实例，就造出了一个和生产不一样的环境。 而且第 8 章说过，断言时要独立于输入数据去检查数据库状态 —— 共用上下文时，很多 ORM 会为了性能缓存查询过的对象， 你「重新查出来」的可能还是刚才内存里那个。

测试数据的生命周期

数据库是共享依赖，集成测试之间需要相互隔离。为此要做两件事：顺序执行集成测试；在测试运行之间清理残留数据。 总的原则是：测试不应该依赖数据库当前的状态，它应该自己把状态摆到需要的样子。

并行还是顺序

让集成测试并行要花很多功夫：得保证所有测试数据唯一（否则会违反数据库约束，或者一个测试误拿到另一个的数据），清理也更麻烦。 顺序跑集成测试更实际。多数测试框架都能把测试分组并单独关掉某一组的并行 —— 分成单元测试和集成测试两组，只关掉后者的并行即可。

ⓘ 用容器并行呢？

可以给每个集成测试起一个新的数据库容器，但实践中维护负担太重：要维护镜像、保证每个测试拿到自己的容器、分批执行、回收用过的容器。 除非你非常需要压缩集成测试的执行时间，否则不推荐。每个开发者一个数据库实例就够了 —— 这个实例本身跑在 Docker 里完全没问题。作者反对的是过早的并行化，不是 Docker。

什么时候清理数据

删除要按特定顺序进行，以满足外键约束。有人会用复杂的算法自动推断表之间的关系来生成删除脚本，甚至先禁用所有约束再恢复 —— 没必要。 手写 SQL 脚本：更简单，对删除过程的控制也更细。把它放进所有集成测试的基类里，每个测试开始时自动执行： 

abstract class IntegrationTests {
    protected static final String CONNECTION_STRING = "...";

    @BeforeEach
    void clearDatabase() throws SQLException {
        String query =
            "DELETE FROM users;" +          // 先删依赖别人的表
            "DELETE FROM company;";         // 只删普通数据，不动参考数据

        try (var connection = DriverManager.getConnection(CONNECTION_STRING);
             var statement = connection.createStatement()) {
            statement.execute(query);
        }
    }
}

export const CONNECTION_STRING = '...'

export function useCleanDatabase(): void {
  beforeEach(async () => {
    const query =
      'DELETE FROM users;' +            // 先删依赖别人的表

💡

删除脚本要清掉所有普通数据，但一条参考数据都不能动。参考数据和其他数据库结构一样，只能由迁移来管理。

避免使用内存数据库

另一种隔离办法是把数据库换成内存里的替代品（比如 SQLite、H2）。看起来很美：不用清数据、更快、每次测试都能新建一个。 而且它不再是共享依赖，集成测试实际上变成了单元测试。

⚠ 但是不推荐

内存数据库和真正的数据库在功能上并不一致 —— 又是生产环境和测试环境不匹配的老问题。 这些差异会让你的测试出现误报，或者（更糟）漏报。靠这样的测试你永远得不到可靠的保护，最后还是得手工做大量回归测试。

测试里用和生产相同的数据库管理系统。版本号或版本类型（社区版 / 企业版）不同通常没关系，但厂商必须相同。

在测试的各个阶段复用代码

集成测试很容易越写越长，可维护性越来越差。要让它尽量短，但不能让测试彼此耦合，也不能牺牲可读性 —— 再短的测试也不该互相依赖，而且必须保留测试场景的完整上下文。 最好的办法是：把技术性的、与业务无关的部分抽到私有方法或辅助类里。

先看「每段一个工作单元」之后测试长什么样 —— 正确，但啰嗦：

ⓘ Object Mother vs. Test Data Builder

上面这种「帮你创建测试夹具的类或方法」叫 Object Mother。另一个达到同样目的的模式是 Test Data Builder，它提供流式接口： new UserBuilder().withEmail("…").withType(EMPLOYEE).build()。

Builder 读起来稍好一点，但样板代码多。原书作者在 C# 里推荐 Object Mother，因为 C# 有可选参数。 Python 和 TypeScript 同理；Java 没有默认参数，所以在 Java 里用 Builder（或 Lombok 的 @Builder）往往更顺手。

💡 工厂方法放哪

从简单开始：默认放在测试类里。等重复成了明显的问题，再挪到单独的辅助类。 不要放进基类 —— 基类只留给每个测试都必须运行的代码，比如数据清理。

执行段：装饰方法

每个执行段都要创建工作单元、创建控制器。把这些包进一个方法，让它接收一个「要调用控制器的哪个方法」的函数： 

private String execute(Function<UserController, String> func,
                       MessageBus messageBus, IDomainLogger logger) {
    try (var context = new CrmContext(CONNECTION_STRING)) {
        var controller = new UserController(context, messageBus, logger);
        return func.apply(controller);
    }
}

// 使用：执行段缩成了一句
String result = execute(
    x -> x.changeEmail(user.getUserId(), "new@gmail.com"),
    messageBus, loggerMock);

def execute(func: Callable[[UserController], str],
            message_bus: MessageBus, logger: DomainLogger) -> str:
    with CrmContext(CONNECTION_STRING) as context:
        controller = UserController(context, message_bus, logger)
        return func(controller)


# 使用：执行段缩成了一句
result = execute(
    lambda x: x.change_email(user.user_id, "new@gmail.com"),
    message_bus, logger_mock)

async function execute(
  func: (controller: UserController) => Promise<string>,
  messageBus: MessageBus,
  logger: IDomainLogger,
): Promise<string> {
  const context = new CrmContext(CONNECTION_STRING)
  try {
    const controller = new UserController(context, messageBus, logger)
    return await func(controller)
  } finally {
    await context.dispose()
  }
}

// 使用：执行段缩成了一句

  (x) => x.changeEmail(user.userId, 'new@gmail.com'),

// 测试代码里的断言辅助类（Java 没有扩展方法，用一个包装类实现流式接口）
public class UserAssert {
    private final User user;
    private UserAssert(User user) { this.user = user; }

    public static UserAssert assertThatUser(User user) { return new UserAssert(user); }

    public UserAssert exists() {
        assertThat(user).isNotNull();
        return this;
    }
    public UserAssert hasEmail(String email) {
        assertThat(user.getEmail()).isEqualTo(email);
        return this;
    }
    public UserAssert hasType(UserType type) {
        assertThat(user.getType()).isEqualTo(type);
        return this;
    }
}

# 测试代码里的断言辅助类
class UserAssert:
    def __init__(self, user: User | None) -> None:
        self._user = user

    def should_exist(self) -> "UserAssert":
        assert self._user is not None
        return self

    def with_email(self, email: str) -> "UserAssert":
        assert self._user.email == email
        return self

    def with_type(self, user_type: UserType) -> "UserAssert":
        assert self._user.type == user_type
        return self

// 测试代码里的断言辅助函数
export function expectUser(user: User | null) {
  const api = {
    toExist() {
      expect(user).not.toBeNull()
      return api
    },
    withEmail(email: string) {
      expect(user!.email).toBe(email)
      return api
    },
    withType(type: UserType) {
      expect(user!.type).toBe(type)
      return api
    },
  }
  return api
}

ⓘ 事务数量变多了，要紧吗？

简化之后，测试用了五个工作单元（两个 create、一个 execute、两个 query），原来只有三个。这会让测试慢一点。 这又是一个取舍 —— 这次是快速反馈和可维护性之间。在这里拿性能换可维护性是值得的： 数据库在本机时性能损失不大，可维护性的提升却很可观。

数据库测试的常见问题

读操作要不要测

写操作必须充分测试，因为风险高：写出错常常导致数据损坏，不仅影响你自己的数据库，还可能波及外部应用。 读操作的 Bug 通常没有这么严重的后果，所以测试的门槛应该更高：只测最复杂或最重要的读操作，其余忽略。

顺带一提，读操作也不需要领域模型。领域建模的主要目的是封装，而封装是为了在数据变化时保持一致性 —— 读操作不改数据，封装就没有意义。 你甚至不需要 ORM，直接写 SQL 性能更好。既然读操作几乎没有抽象层，单元测试也就派不上用场；要测就用集成测试对着真数据库测。

仓储要不要单独测

单独测试仓储「怎么把领域对象映射到数据库」看起来挺有用，毕竟这里出错的空间不小。 但这种测试对测试集来说是净亏损：

💸

维护成本高

在四象限里，仓储属于控制器那一格：复杂度低，却和进程外依赖（数据库）打交道。测它的成本和普通集成测试一样高。

📉

防止回归的增益低

仓储本身没多少复杂度，而它能带来的保护，大部分已经被常规的集成测试覆盖了。重复了。

★ 准则

不要直接测试仓储，只把它作为整体集成测试的一部分来测。 如果仓储里确实有一点复杂逻辑，最好把它抽成一个不带任何协作者的独立算法单独测（之前的 UserFactory 就是这个思路）。 不过用了 ORM 之后，映射和数据库访问分不开，就只能靠集成测试整体覆盖了。

同理，也不要单独测 EventDispatcher：要维护复杂的 Mock 机制，换来的保护却太少。

结语

精心编写的、直接对着数据库跑的测试能提供近乎无懈可击的保护。按原书作者的经验，它们是最有效的工具之一 —— 没有它们，你不可能对自己的软件有十足的信心。在你重构数据库、更换 ORM 或者更换数据库厂商时，这类测试的帮助尤其大。 本章中途把示例项目切换到了 ORM，集成测试只改了几行就确认了切换是成功的。

小结

  • 把数据库结构和源代码一起放进版本控制。结构包括表、视图、索引、存储过程，以及参考数据（应用正常运行所必需、但应用自己不能修改的数据）。
  • 每个开发者一个独立的数据库实例，最好在自己的机器上。
  • 优先选择基于迁移的数据库交付方式，因为处理数据迁移远比处理合并冲突重要。所有结构变更（含参考数据）都通过迁移来做；已提交的迁移不要修改。
  • 业务操作必须原子地更新数据，依靠数据库的事务机制实现。把「改什么」（仓储）和「提交还是回滚」（事务）分开。
  • 尽量使用工作单元模式：它建立在数据库事务之上，并把所有更新推迟到业务操作结束时执行。大多数 ORM 已经实现了它。
  • 不要在测试的各阶段之间复用事务或工作单元：准备、执行、断言各用各的。
  • 集成测试顺序执行。并行要付出很大代价，通常不值得。
  • 在测试开始时清理残留数据。这样快、不会造成行为不一致，也不会被意外跳过；也就不需要单独的清理阶段。
  • 避免内存数据库。测试里用和生产相同的数据库管理系统。
  • 通过把非本质的部分抽到私有方法或辅助类来缩短测试：准备段用 Object Mother（或 Builder）；执行段用装饰方法；断言段用流式接口。
  • 测试读操作的门槛应比写操作高：只测最复杂或最重要的读操作。
  • 不要直接测试仓储，只把它作为整体集成测试的一部分。

自测

同事发现上周提交的一个迁移脚本里列名拼错了，想直接改那个脚本文件。该怎么做？

不要改已经提交的迁移 —— 可能已经有环境执行过它了。新建一个迁移来把列名改对。只有当错误的迁移会导致数据丢失时才破例修改它。

为什么「把每个测试包在事务里、最后回滚」不是最好的清理办法？

因为多出来的外层事务让测试环境和生产环境不一样（生产里没有这个事务），可能导致行为不一致 —— 比如被测代码自己的提交 / 回滚逻辑表现不同。在测试开始时用删除脚本清理更可靠。

生产用 PostgreSQL，为了快，测试里用 H2 / SQLite 内存库。有什么风险？

两种数据库在 SQL 方言、类型、约束、事务行为上都有差异。测试可能通过了但生产上失败（漏报），或者反过来（误报）。你得不到可靠的保护。应当在测试里也用 PostgreSQL。

动手练习

  1. 为你的 CRM 示例选一个迁移工具（Flyway / Alembic / Knex 等），写出创建 users 和 company 表的迁移，再写一个把参考数据（用户类型）插进去的迁移。
  2. 把集成测试改成「准备、执行、断言各用一个连接 / 会话」。然后故意让断言段复用执行段的会话，观察 ORM 缓存会不会让一个本该失败的测试通过。
  3. 写一个在每个测试开始时清库的基类 / fixture。故意在调试器里中途停掉一个测试，再跑下一个，确认它不受影响。
  4. 给你的集成测试写 createUser（带默认值）、execute、流式断言这三类辅助代码，对比改造前后测试的行数和可读性。
