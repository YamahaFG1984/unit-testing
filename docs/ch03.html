第 3 章

单元测试的结构

这一章是「基本功」：一个测试方法内部怎么分段、怎么命名、重复的准备代码怎么复用、 相似的测试怎么合并。这些规矩看着琐碎，却直接决定了三个月后你还读不读得懂自己写的测试。

本章目标

  • 用 AAA 模式（准备 — 执行 — 断言）组织每一个测试
  • 从「执行段有几行」看出被测代码的封装问题
  • 用工厂方法而不是构造函数 / setUp 来复用测试夹具
  • 给测试起一个业务人员也能看懂的名字
  • 会用参数化测试和流式断言

AAA 模式：准备、执行、断言

AAA（也叫 3A）主张把每个测试分成三段：Arrange（准备）、Act（执行）、Assert（断言）。 用一个只有加法的计算器来看： 

public class Calculator {
    public double sum(double first, double second) {
        return first + second;
    }
}

class CalculatorTests {
    @Test
    void sum_of_two_numbers() {
        // Arrange
        double first = 10;
        double second = 20;
        var calculator = new Calculator();

        // Act
        double result = calculator.sum(first, second);

        // Assert
        assertEquals(30, result);
    }
}

class Calculator:
    def sum(self, first: float, second: float) -> float:
        return first + second


def test_sum_of_two_numbers():
    # Arrange
    first = 10
    second = 20
    calculator = Calculator()

    # Act
    result = calculator.sum(first, second)

    # Assert
    assert result == 30

export class Calculator {
  sum(first: number, second: number): number {
    return first + second
  }
}

describe('Calculator', () => {
  test('sum of two numbers', () => {
    // Arrange
    const first = 10
    const second = 20
    const calculator = new Calculator()

    // Act
    const result = calculator.sum(first, second)

    // Assert
    expect(result).toBe(30)
  })
})

这个模式最大的好处是统一：整个测试集里的所有测试长得都一样。一旦习惯了，任何测试拿来就能读懂， 这直接降低了整个测试集的维护成本。

💡 先写哪一段？

先有生产代码再写测试：从 Arrange 写起，因为你已经知道行为是什么了。
做 TDD（先写测试）：可以从 Assert 写起。这时你对功能了解还不多， 先写下「我期望得到什么」，再去想怎么实现。这其实就是我们平常解决问题的思路 —— 先想目标，再想办法。

避免出现多个准备 / 执行 / 断言段

看到执行段被断言隔开、出现了好几次，就说明这个测试在验证多个行为单元。 按第 2 章的定义，它已经不是单元测试，而是集成测试了。把每个执行动作抽成一个独立的测试。

ⓘ 唯一的例外

已经很慢的集成测试，为了不让它更慢，可以把几个测试合并成一个带多次执行和断言的测试 —— 特别是当系统状态自然地一环扣一环（上一步的执行正好是下一步的准备）时。 单元测试和够快的集成测试不需要这种优化。

避免在测试里写 if

测试 —— 不管是单元测试还是集成测试 —— 应该是一串没有分支的简单步骤。 出现 if 同样说明测试一次验证了太多东西，应该拆开。 这一条没有例外：测试里的分支没有任何好处，只会让测试更难读。

每一段该有多大

执行段超过一行，说明什么

先看正常的版本 —— 执行段只有一行，这是 API 设计良好的标志：

// Act
boolean success = customer.purchase(store, Product.SHAMPOO, 5);

# Act
success = customer.purchase(store, Product.SHAMPOO, 5)

// Act
const success = customer.purchase(store, Product.Shampoo, 5)

再看有问题的版本 —— 完成一次购买要调两个方法：

// Act
boolean success = customer.purchase(store, Product.SHAMPOO, 5);
store.removeInventory(success, Product.SHAMPOO, 5);   // 调用方必须「记得」再调这一步

# Act
success = customer.purchase(store, Product.SHAMPOO, 5)
store.remove_inventory(success, Product.SHAMPOO, 5)   # 调用方必须「记得」再调这一步

// Act
const success = customer.purchase(store, Product.Shampoo, 5)
store.removeInventory(success, Product.Shampoo, 5)   // 调用方必须「记得」再调这一步

注意，问题不在测试，测试验证的还是同一个行为。问题在 Customer 的 API： 从业务角度看，一次成功的购买有两个结果 —— 顾客拿到商品、商店库存减少 —— 这两件事必须一起发生。

不变量被破坏（invariant violation）与封装（encapsulation）

「卖出去的数量必须从库存里扣掉」这种必须始终成立的条件叫不变量。 保护代码、不让它进入不一致状态的做法，叫封装。 不一致一旦写进数据库就很麻烦了：重启应用解决不了，只能逐条处理脏数据，甚至要联系客户。

「执行段只有一行」这条规矩对绝大多数包含业务逻辑的代码都成立，对工具类和基础设施代码则没那么严格。 所以不是「绝对不能」，而是每次遇到都要检查一下是不是封装出了漏洞。

断言段可以有几个断言

你可能听过「一个测试只能有一个断言」。这条规矩的出发点是「测试对象要尽可能小」—— 而第 2 章已经说过这个前提是错的：单元是行为单元，一个行为可以有多个结果，在一个测试里把它们都验证了完全没问题。

不过断言段太长也是个信号：可能生产代码少了一个抽象。比如与其逐个断言返回对象的每个属性， 不如给这个类定义好相等性比较，然后用一个断言和期望值整体比较。

那清理（teardown）阶段呢

有人会加上第四段：清理 —— 删除测试创建的文件、关闭数据库连接等。它通常是一个被全类测试共用的独立方法，所以不算在 AAA 里。 大多数单元测试不需要清理，因为它们不碰进程外依赖，不会留下需要收拾的副作用。清理是集成测试的事（第三部分）。

让测试更好读的两个小习惯

把被测系统统一命名为 sut

SUT 是你要触发的行为的入口。行为可以跨好几个类，但入口只有一个。 当依赖比较多时，一眼分清「谁是被测对象、谁是依赖」很重要 —— 所以，永远把它叫 sut。

用空行代替注释分隔三段

@Test
void sum_of_two_numbers() {
    double first = 10;
    double second = 20;
    var sut = new Calculator();                // 被测对象叫 sut

    double result = sut.sum(first, second);

    assertEquals(30, result);
}

def test_sum_of_two_numbers():
    first = 10
    second = 20
    sut = Calculator()                # 被测对象叫 sut

    result = sut.sum(first, second)

    assert result == 30

test('sum of two numbers', () => {
  const first = 10
  const second = 20
  const sut = new Calculator()                // 被测对象叫 sut

  const result = sut.sum(first, second)

  expect(result).toBe(30)
})

🔬 为什么原书作者喜欢「Fact」这个词

xUnit 用 [Fact]（事实）而不是 [Test] 来标记测试。作者很喜欢这一点，因为它强调： 每个测试都在讲一个故事 —— 一个关于问题领域的、不可再分的场景或事实，测试通过就证明这个事实成立。 测试失败，要么说明故事过时了需要重写，要么说明系统本身需要修。

测试不应该是「生产代码做了什么」的流水账，而应该是对应用行为的更高层的描述，最好业务人员也看得懂。

在测试之间复用夹具

测试夹具（test fixture）

测试运行时所依托的对象：可以是传给 SUT 的普通依赖，也可以是数据库里的数据、硬盘上的文件。 每次测试前它都得处于一个已知的、固定（fixed）的状态，这样测试才能每次得到相同结果 —— 所以叫 fixture。

准备段经常很长，把它抽出来复用很合理。但有两种抽法，只有一种是好的。

✗ 不好的方式：放进构造函数 / setUp

class CustomerTests {
    private Store store;      // 共享的夹具
    private Customer sut;

    @BeforeEach               // 每个测试之前都会运行
    void setUp() {
        store = new Store();
        store.addInventory(Product.SHAMPOO, 10);
        sut = new Customer();
    }

    @Test
    void purchase_succeeds_when_enough_inventory() {
        boolean success = sut.purchase(store, Product.SHAMPOO, 5);

        assertThat(success).isTrue();
        assertThat(store.getInventory(Product.SHAMPOO)).isEqualTo(5);
    }

    @Test
    void purchase_fails_when_not_enough_inventory() {
        boolean success = sut.purchase(store, Product.SHAMPOO, 15);

        assertThat(success).isFalse();
        assertThat(store.getInventory(Product.SHAMPOO)).isEqualTo(10);
    }
}

测试代码确实短了，但带来两个明显的问题：

🔗

测试之间高度耦合

有人为了自己的测试把 10 改成 15，其他测试关于「初始库存是 10」的假设就全错了，莫名其妙地失败。 修改一个测试不应该影响其他测试。

👁

可读性下降

只看测试方法本身，看不到全貌。你得去类里别的地方翻，才知道这个测试到底在什么前提下运行。

ⓘ 两种「独立」

第 2 章说的是测试要能独立运行（不共享运行时状态）。这里说的是测试要能独立修改（不共享准备代码里的假设）。 两者都是设计良好的测试应有的特性。

工厂方法同样缩短了测试，但保留了完整的上下文。 createStoreWithInventory(Product.SHAMPOO, 10) 这一行：

  • 可读 —— 不用点进工厂方法，就知道造出来的是「有 10 瓶洗发水的商店」。
  • 可复用 —— 别的测试可以用不同的参数调用它。只要工厂方法足够通用（让测试自己指定想要什么），它就不会把测试耦合在一起。
💡 Python 读者：pytest 的 fixture 算哪种？

pytest 的 fixture 是显式地通过参数名注入的，测试签名上看得见用了哪个，比隐式的 setUp 好。 但如果 fixture 直接返回一个固定状态的对象（store_with_10_shampoo），「改一处影响所有人」的问题依然存在。 想让每个测试自己指定参数，可以让 fixture 返回一个工厂函数，或者干脆像上面那样用普通函数。

ⓘ 例外：几乎所有测试都要用的夹具

如果一个夹具被类里全部（或几乎全部）测试使用，可以在构造函数 / setUp 里初始化。 最典型的是集成测试用的数据库连接。即便如此，更好的做法是抽一个基类，在基类里初始化，让各个测试类继承： 

abstract class IntegrationTests {
    protected Database database;

    @BeforeEach
    void openDatabase() { database = new Database(); }

    @AfterEach
    void closeDatabase() { database.close(); }
}

class CustomerTests extends IntegrationTests {
    @Test
    void purchase_succeeds_when_enough_inventory() {
        /* 在这里使用 database */
    }
}

给测试起名字

好名字能让你一眼看出测试在验证什么、系统是怎么表现的。最流行、但可能也最没用的一种命名规范是：

[被测方法]_[场景]_[期望结果]

例：Sum_TwoNumbers_ReturnsSum
    IsDeliveryValid_InvalidDate_ReturnsFalse

它没用的原因是：它引导你关注实现细节，而不是行为。对比一下：

✗ 死板的格式
Sum_TwoNumbers_ReturnsSum

为什么 Sum 出现了两次？Returns 是返回到哪儿？对不了解代码的人来说像天书。

✓ 一句大白话
Sum_of_two_numbers

「两个数的和」。对被测行为朴素、直接的描述。

有人会说：测试是程序员写给程序员看的，程序员本来就擅长解读晦涩的名字。这话只对了一部分。 晦涩的名字对每个人都是一笔认知税：你得多花脑力才能弄清它到底验证什么、和哪条业务需求有关。 单看一次不多，但日积月累，它会慢慢抬高整个测试集的维护成本。

命名的四条准则

  1. 不要遵循死板的命名格式。复杂行为的高层描述塞不进一个固定的模板，给表达留点自由。
  2. 像是在向一位熟悉业务、但不懂编程的人描述场景那样起名。比如领域专家或业务分析师。
  3. 用下划线分隔单词。名字长的时候可读性提升明显。（测试类的名字一般不长，不需要下划线。）
  4. 不要把被测方法的名字放进测试名。你测的是行为，不是代码。方法改名不影响行为，测试名就不该跟着改。
ⓘ 三种语言里怎么落实
  • Java：方法名允许下划线，void delivery_with_a_past_date_is_invalid() 完全合法；也可以配 @DisplayName("过去日期的配送无效")。
  • Python：本来就是蛇形命名，只是必须以 test_ 开头：test_delivery_with_a_past_date_is_invalid。
  • TypeScript：测试名是字符串，直接写句子：test('delivery with a past date is invalid', …)。

另外，测试类叫 CalculatorTests 并不代表里面只能测 Calculator 这一个类。 把它看成一个入口就好：通过这个 API 去验证某个行为单元，行为本身可以跨多个类。

这个测试验证「配送日期是过去的日期时，配送无效」：

⚠ 为什么不用 should be

测试陈述的是关于某个行为的一个事实。陈述事实时没有「愿望」的位置 —— 不是「应该无效」，而是「是无效的」。把 should be 换成 is。

ⓘ 准则 4 的例外

工具类代码没有业务逻辑，它的行为对业务人员没什么意义。给这类代码写测试时，在测试名里用被测方法名是可以的。

参数化测试

一个测试通常不足以完整描述一个行为。行为越复杂，需要的「事实」越多，测试数量会迅速膨胀。

假设配送规则是：最早只能选两天之后。那除了「过去的日期」，还得测今天、明天、后天。 四个测试方法只有日期不同 —— 用参数化测试合并： 

class DeliveryServiceTests {
    @ParameterizedTest
    @CsvSource({
        "-1, false",     // 每一行都是关于这个行为的一条独立事实
        " 0, false",
        " 1, false",
        " 2, true"
    })
    void can_detect_an_invalid_delivery_date(int daysFromNow, boolean expected) {
        var sut = new DeliveryService();
        var delivery = new Delivery(LocalDateTime.now().plusDays(daysFromNow));

        boolean isValid = sut.isDeliveryValid(delivery);

        assertThat(isValid).isEqualTo(expected);
    }
}

import pytest

小结

  • 所有单元测试都应遵循 AAA：准备、执行、断言。出现多个执行段，说明测试验证了多个行为，应拆开。
  • 测试里不要有 if。
  • 执行段超过一行是 SUT 的 API 有问题的信号：它要求调用方记得把几个动作一起做，可能导致不变量被破坏。防止这种情况的做法叫封装。
  • 把被测对象命名为 sut。用空行（简单测试）或注释（复杂测试）分隔三段。
  • 复用夹具初始化代码用工厂方法，不要放构造函数 / setUp。这样测试之间保持解耦，读起来也有完整上下文。
  • 不要用死板的命名格式。像给懂业务的非程序员讲故事那样起名；用下划线分词；不要包含被测方法名；用 is 不用 should be。
  • 参数化测试能减少相似测试的代码量，代价是名字变得更泛、更难读。
  • 断言库通过调整语序让断言读起来像自然语言。

自测

你的测试执行段有三行：先 order.addItem()，再 order.recalculateTotal()，最后 order.save()。这暗示了什么？

很可能是封装问题：调用方必须记得在加商品之后重算总价，否则订单总价和明细就不一致了（不变量被破坏）。addItem 应该自己负责更新总价。

把 GetDiscount_PremiumCustomer_Returns10Percent 改成符合本章准则的名字。

例如 Premium_customer_gets_a_10_percent_discount。去掉了方法名，是一句陈述事实的话，业务人员也读得懂。

什么时候可以在 setUp / 构造函数里初始化夹具？

当它被类里全部或几乎全部测试使用时，典型的是集成测试的数据库连接。更好的做法是放到基类（或共享的 fixture）里。
