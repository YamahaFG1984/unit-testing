异步与并发代码的测试

原书的例子全是同步代码。可你每天写的多半带着 async、回调、定时器或线程。 这类代码的测试有三种特有的坏法：该红的时候绿、要等真实的时间、时好时坏。这一章逐个讲怎么避开。

本章目标

  • 知道异步测试为什么会「明明错了却显示通过」，以及怎么杜绝
  • 把异步留在外壳，让决策逻辑保持同步
  • 测试里不等真实的时间：把「等待」变成可以替换的依赖
  • 等一个不受你控制的异步结果时，用「轮询 + 超时」代替固定的 sleep
  • 理解竞态条件，会为它写一个能稳定重现的测试
  • 知道测试「时好时坏」的常见原因和处理办法
ⓘ 这一章不是原书内容

本章是教程的补充，用的仍然是前面的框架：四大支柱（第 4 章）、函数式核心与外壳（第 6、7 章）、把时间当成显式依赖（第 11 章）。 本章的代码片段都在三种语言里实际运行过（Python 3.12 + pytest-asyncio、Vitest 3.2、Java 21 + JUnit 5），文中提到的「通过 / 失败」是实测结果。 不同版本的框架在细节上可能不同。

异步测试的三种坏法

先问一句：这段逻辑非得是异步的吗

异步几乎总是因为 I/O：读数据库、发请求、等消息。而做决定的代码 —— 算折扣、判断用户类型、校验规则 —— 不需要 I/O，也就不需要异步。 第 6、7 章讲的「核心 / 外壳」分离，在这里多了一层好处：

配套示例的 TypeScript 版就是这样：UserController.changeEmail 是 async 的（它要读写数据库）， 但 User.changeEmail 是普通的同步方法，它的 7 个单元测试里没有一个 await。

★ 本章最重要的一条

如果你发现需要为一段业务规则写异步测试，先别急着学技巧，回头看看这段规则能不能从异步代码里抽出来（第 7 章、第 12 章）。 下面的技巧是给真正躲不开异步的那部分代码准备的：重试、超时、调度、并发访问。

坏法一：测试结束了，断言还没执行

先看三个错误的测试。它们断言的期望值都是错的（或者根本没断言到东西），照理应该失败：

static CompletableFuture<String> loadEmail(int userId) { /* 异步读取 */ }

@Test
void loads_the_email() {
    loadEmail(1).thenAccept(email ->
        assertThat(email).isEqualTo("WRONG"));    // 在另一个线程里失败，没人接住
}                                                 // 测试方法已经返回：通过

async def load_user(user_id): ...                 # 异步读取


def test_loads_the_user():
    user = load_user(1)        # 忘了 await：拿到的是「协程对象」，不是用户
    assert user                # 协程对象恒为真：通过

async function loadUser(id: number) { /* 异步读取 */ }

test('loads the user', () => {
  loadUser(1).then((user) => {
    expect(user.email).toBe('WRONG')              // 测试函数返回之后才执行
  })
})

实测结果：

语言 / 框架上面那个错误的测试有没有东西提醒你
Java · JUnit 5通过没有。异常被 CompletableFuture 吞进了返回值里
Python · pytest 9通过有一条警告：coroutine 'load_user' was never awaited，但不影响结果
TypeScript · Vitest 3.2该测试显示通过有。整次运行会报 Unhandled Rejection 并以失败退出 —— 但并不是每个框架、每个版本都这样

正确的写法：等到结果，再在测试自己的执行流里断言

@Test
@Timeout(2)                                              // 兜底：卡住就判失败
void loads_the_email() throws Exception {
    String email = loadEmail(1).get(1, TimeUnit.SECONDS);    // 在测试线程里等结果

    assertThat(email).isEqualTo("user@mycorp.com");
}

// 或者用 AssertJ 的写法，等待和断言连在一起：
// assertThat(loadEmail(1))
//     .succeedsWithin(Duration.ofSeconds(1))
//     .isEqualTo("user@mycorp.com");

# pyproject.toml / pytest.ini 里配置：asyncio_mode = "auto"（来自 pytest-asyncio 插件）

async def test_loads_the_user():                 # 测试函数本身是 async 的
    user = await load_user(1)                    # 等到结果

    assert user["email"] == "user@mycorp.com"

test('loads the user', async () => {             // 测试函数本身是 async 的
  const user = await loadUser(1)                 // 等到结果

  expect(user.email).toBe('user@mycorp.com')
})

// 断言「会失败」也要 await：
// await expect(loadUser(-1)).rejects.toThrow('not found')

规则只有一条：断言必须发生在框架正在等的那条执行流里。各语言落到实处是：

要做的防呆措施
Java 在测试线程里 get(超时) / join() 拿到值再断言；不要把断言写进 thenAccept 之类的回调 给异步测试加 @Timeout。没有自动的检查，靠评审
Python 测试写成 async def，装 pytest-asyncio（或 anyio）；每个协程调用前都有 await pytest 配置 filterwarnings = ["error"]，把「协程从未被 await」的警告变成失败（实测有效）
TypeScript 测试写成 async，每个 Promise 前都有 await（或者把它 return 出去） 开启 typescript-eslint 的 no-floating-promises 规则，在写代码时就拦住没人等的 Promise
⚠ Python：没装插件的 async 测试

pytest 本身不会运行 async def 的测试。pytest 9 里它会直接失败并提示你装插件（实测）； 而较早的版本只是跳过并给一条警告 —— 一整个文件的测试都没跑，报告却是绿的。 看一眼测试报告里的 skipped 数量是个好习惯。

💡 怎么确认一个异步测试真的在验证东西

和第 12 章验收新安全网的办法一样：故意把期望值改错，看它会不会红。 一个从来没红过的异步测试，你并不知道它有没有在工作。第 14 章的变异测试就是把这件事自动化。

坏法二：等真实的时间

重试、超时、防抖、缓存过期、定时任务 —— 这些逻辑的行为就是「隔多久做什么」。如果测试真的去等，一个「重试三次、间隔翻倍」的测试就要花上几百毫秒甚至几十秒， 而且在一台繁忙的 CI 机器上，「等 100 毫秒」可能实际过了 180 毫秒，测试时红时绿。

第 11 章已经给出了思路：时间是一个依赖，把它显式地传进来。那一章处理的是「现在几点」，这里处理的是「等一会儿」。 例子是一个带指数退避的重试函数： 

public final class Retry {
    public interface Sleeper {                       // 「等一会儿」这个动作，做成接口
        void sleep(Duration duration);
    }

    public static class TransientException extends RuntimeException {}

    public static <T> T run(Supplier<T> operation, int attempts,
                            Duration baseDelay, Sleeper sleeper) {
        for (int attempt = 1; ; attempt++) {
            try {
                return operation.get();
            } catch (TransientException e) {
                if (attempt == attempts) throw e;
                sleeper.sleep(baseDelay.multipliedBy(1L << (attempt - 1)));   // 100、200、400……
            }
        }
    }
}

class TransientError(Exception):
    pass


async def retry(operation, attempts=3, base_delay=0.1, sleep=asyncio.sleep):
    #                                                   ↑ 「等一会儿」是一个参数，默认用真的
    for attempt in range(1, attempts + 1):
        try:
            return await operation()
        except TransientError:
            if attempt == attempts:
                raise
            await sleep(base_delay * 2 ** (attempt - 1))    # 0.1、0.2、0.4……

export class TransientError extends Error {}

export type Sleep = (ms: number) => Promise<void>

const realSleep: Sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms))

export async function retry<T>(
  operation: () => Promise<T>,
  { attempts = 3, baseDelayMs = 100, sleep = realSleep } = {},   // 「等一会儿」是一个参数
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await operation()
    } catch (error) {
      if (!(error instanceof TransientError) || attempt === attempts) throw error
      await sleep(baseDelayMs * 2 ** (attempt - 1))                // 100、200、400……
    }
  }
}

测试传进去一个不真的等、只把时长记下来的替身。整个测试在一毫秒内跑完，而且结果和机器快慢无关：

@Test
void retries_until_the_operation_succeeds() {
    Supplier<String> operation = failingThen(
        new Retry.TransientException(), new Retry.TransientException(), "ok");
    List<Duration> delays = new ArrayList<>();

    String result = Retry.run(operation, 3, Duration.ofMillis(100), delays::add);

    assertThat(result).isEqualTo("ok");
    assertThat(delays).containsExactly(Duration.ofMillis(100), Duration.ofMillis(200));
}

// 辅助：一个按顺序给出结果的操作，遇到异常对象就抛出
static <T> Supplier<T> failingThen(Object... outcomes) {
    Iterator<Object> remaining = List.of(outcomes).iterator();
    return () -> {
        Object outcome = remaining.next();
        if (outcome instanceof RuntimeException e) throw e;
        @SuppressWarnings("unchecked") T value = (T) outcome;
        return value;
    };
}

async def test_retries_until_the_operation_succeeds():
    operation = failing_then(TransientError(), TransientError(), "ok")
    delays = []

    async def fake_sleep(seconds):
        delays.append(seconds)

    result = await retry(operation, attempts=3, base_delay=0.1, sleep=fake_sleep)

    assert result == "ok"
    assert delays == [0.1, 0.2]


# 辅助：一个按顺序给出结果的操作，遇到异常对象就抛出
def failing_then(*outcomes):
    remaining = list(outcomes)

    async def operation():
        outcome = remaining.pop(0)
        if isinstance(outcome, Exception):
            raise outcome
        return outcome

    return operation

test('retries until the operation succeeds', async () => {
  const operation = failingThen(new TransientError(), new TransientError(), 'ok')
  const delays: number[] = []
  const fakeSleep = async (ms: number) => { delays.push(ms) }

  const result = await retry(operation, { attempts: 3, baseDelayMs: 100, sleep: fakeSleep })

  expect(result).toBe('ok')
  expect(delays).toEqual([100, 200])
})

// 辅助：一个按顺序给出结果的操作，遇到异常对象就抛出
function failingThen<T>(...outcomes: Array<Error | T>): () => Promise<T> {
  const remaining = [...outcomes]
  return async () => {
    const outcome = remaining.shift()
    if (outcome instanceof Error) throw outcome
    return outcome as T
  }
}
🔎 断言等待时长，算不算测了实现细节

看它对谁可见（第 5 章）。重试的间隔决定了你的系统以什么节奏去敲别人的服务 —— 对那个外部系统来说，这是可观察的行为，值得钉住。 如果只是内部某个缓存「大概隔一阵刷新一次」，具体是 100 还是 120 没人在乎，那就别断言具体数字，只断言最终结果。

另一种办法：假定时器

JavaScript 生态里更常见的做法是不改函数签名，而是让测试框架接管全局的定时器：setTimeout 不再真的计时，由测试手动把时钟往前拨。 下面的测试用的是没传 sleep 参数的 retry，也就是真实的 setTimeout 版本： 

import { afterEach, beforeEach, expect, test, vi } from 'vitest'

beforeEach(() => { vi.useFakeTimers() })
afterEach(() => { vi.useRealTimers() })           // 一定要还原，否则会影响别的测试

test('waits 100 ms, then 200 ms, between attempts', async () => {
  const operation = vi.fn(failingThen(new TransientError(), new TransientError(), 'ok'))

  const pending = retry(operation)                // 不 await：它会停在第一次等待上
  await vi.advanceTimersByTimeAsync(0)
  expect(operation).toHaveBeenCalledTimes(1)

  await vi.advanceTimersByTimeAsync(100)          // 把时钟拨快 100 毫秒
  expect(operation).toHaveBeenCalledTimes(2)

  await vi.advanceTimersByTimeAsync(200)
  expect(await pending).toBe('ok')
})
把等待作为参数传进来假定时器
要不要改生产代码要：多一个参数（有默认值）不用
测试读起来直白：结果 + 等了多久要一步步拨时钟，容易写错顺序
风险几乎没有改的是全局状态：忘了还原会污染别的测试；第三方库内部的定时器也一起被接管
适合你自己写的、以时间为核心的逻辑改不了签名的代码；防抖、轮询这类到处用 setTimeout 的界面代码

Python 和 Java 里也有类似的工具（比如能冻结时间的库、可以手动推进的调度器），取舍是一样的： 显式传入更啰嗦但更安全；全局接管更省事但副作用更大。

等一个你控制不了的异步结果

有时测试没法 await 到结果：被测系统在后台处理（消息消费者、后台线程、另一个进程），测试只能从外面看「它做完了没有」。 这通常出现在集成测试和端到端测试里。最常见的错误写法是「睡一会儿再看」： 

import { afterEach, beforeEach, expect, test, vi } from 'vitest'

beforeEach(() => { vi.useFakeTimers() })
afterEach(() => { vi.useRealTimers() })           // 一定要还原，否则会影响别的测试

test('waits 100 ms, then 200 ms, between attempts', async () => {
  const operation = vi.fn(failingThen(new TransientError(), new TransientError(), 'ok'))

  const pending = retry(operation)                // 不 await：它会停在第一次等待上

  expect(operation).toHaveBeenCalledTimes(1)

  await vi.advanceTimersByTimeAsync(100)          // 把时钟拨快 100 毫秒
  expect(operation).toHaveBeenCalledTimes(2)

  await vi.advanceTimersByTimeAsync(200)
  expect(await pending).toBe('ok')

// 依赖：org.awaitility:awaitility
import static org.awaitility.Awaitility.await;

@Test
void the_message_is_eventually_sent() {
    startBackgroundWork();                         // 结果会在后台某个时刻出现在 sent 里

    await().atMost(Duration.ofSeconds(2)).untilAsserted(
        () -> assertThat(sent).containsExactly("msg"));
}

async def eventually(predicate, timeout=2.0, interval=0.01):
    """反复检查，直到条件成立；超过 timeout 就失败。"""
    deadline = time.monotonic() + timeout
    while not predicate():
        if time.monotonic() > deadline:
            raise AssertionError(f"条件在 {timeout} 秒内没有成立")
        await asyncio.sleep(interval)


async def test_the_message_is_eventually_sent():
    start_background_work()                        # 结果会在后台某个时刻出现在 sent 里

    await eventually(lambda: len(sent) == 1)

    assert sent == ["msg"]

test('the message is eventually sent', async () => {
  startBackgroundWork()                            // 结果会在后台某个时刻出现在 sent 里

  await vi.waitFor(
    () => expect(sent).toEqual(['msg']),
    { timeout: 2000, interval: 10 })
})
⚠ 轮询是退路，不是首选

能 await 到结果就直接 await（上一节）；能把时间换成替身就换（再上一节）。 只有当异步发生在你插不进手的地方时才轮询。它仍然依赖真实时间，只是把「猜一个数」换成了「设一个宽松的上限」。 另外，轮询只能验证「某件事发生了」；要验证「某件事没有发生」，它帮不上忙 —— 那需要你能确定地知道处理已经结束。

坏法三：并发与竞态条件

竞态条件（race condition）

程序的结果取决于几个并发操作谁先谁后，而这个顺序不由你的代码决定。大多数时候顺序「碰巧」是对的，所以这类 Bug 在开发时不出现，在生产环境的高峰期出现。

最典型的是丢失更新：「先读、再判断、再写」这三步之间被别人插了进来。下面是一个取款操作：

public class Account {
    public interface Store {
        int read();
        void write(int balance);
    }

    private final Store store;

    public Account(Store store) { this.store = store; }

    public void withdraw(int amount) {
        int balance = store.read();                    // ① 读
        if (balance < amount) throw new InsufficientFunds();   // ② 判断
        store.write(balance - amount);                 // ③ 写
    }
}

class Account:
    def __init__(self, store) -> None:
        self._store = store

    async def withdraw(self, amount: int) -> None:
        balance = await self._store.read()             # ① 读
        if balance < amount:                           # ② 判断
            raise InsufficientFunds()
        await self._store.write(balance - amount)      # ③ 写

export class Account {
  constructor(private readonly store: Store) {}

  async withdraw(amount: number): Promise<void> {
    const balance = await this.store.read()            // ① 读
    if (balance < amount) throw new InsufficientFunds()    // ② 判断
    await this.store.write(balance - amount)           // ③ 写
  }
}

为它写一个能稳定重现的测试

先把期望说清楚 —— 这是业务规则，和并发技术无关：余额 100，同时来两笔各取 60 的请求，应该恰好一笔成功、一笔因余额不足被拒，最后余额 40。

怎么让测试「稳定地」撞上那个糟糕的顺序，取决于你的运行环境属于哪一种：

Python 和 TypeScript：给被测对象一个每次读写都让出一次控制权的内存存储（真实的 I/O 就是这样），再同时发起两笔取款。 交错顺序是确定的 —— 两个「读」一定都排在第一个「写」前面 —— 所以这个测试对上面那段有 Bug 的代码每次都红（实测）。

Java：线程的切换点不确定，这里用的是压力测试 —— 8 个线程同时起跑，各取 1000 次 1 块钱，总额正好是初始余额，最后应该归零。 只要有一次更新被覆盖，余额就不是 0。它对有 Bug 的代码实测每次都红，但要明白这是概率很高，不是保证。 

static class InMemoryStore implements Account.Store {
    volatile int balance;
    InMemoryStore(int balance) { this.balance = balance; }
    public int read() { int b = balance; Thread.yield(); return b; }   // 读完让一下，把竞争窗口撑大
    public void write(int balance) { this.balance = balance; }
}

@Test
void concurrent_withdrawals_never_lose_an_update() throws Exception {
    int threads = 8, withdrawalsPerThread = 1_000;
    InMemoryStore store = new InMemoryStore(threads * withdrawalsPerThread);
    Account account = new Account(store);
    ExecutorService pool = Executors.newFixedThreadPool(threads);
    CountDownLatch start = new CountDownLatch(1);

    List<Future<?>> jobs = new ArrayList<>();
    for (int t = 0; t < threads; t++) {
        jobs.add(pool.submit(() -> {
            start.await();                             // 所有线程在同一刻起跑
            for (int i = 0; i < withdrawalsPerThread; i++) account.withdraw(1);
            return null;
        }));
    }
    start.countDown();
    for (Future<?> job : jobs) job.get(10, TimeUnit.SECONDS);   // 在测试线程里等，异常也会在这里抛出
    pool.shutdown();

    assertThat(store.balance).isEqualTo(0);
}

class InMemoryStore:
    """像真实的 I/O 一样：每次读写都让出一次控制权。"""

    def __init__(self, balance: int) -> None:
        self.balance = balance

    async def read(self) -> int:
        await asyncio.sleep(0)
        return self.balance

    async def write(self, balance: int) -> None:
        await asyncio.sleep(0)
        self.balance = balance


async def test_two_concurrent_withdrawals_cannot_overdraw():
    store = InMemoryStore(balance=100)
    account = Account(store)

    results = await asyncio.gather(
        account.withdraw(60), account.withdraw(60), return_exceptions=True)

    failures = [r for r in results if isinstance(r, InsufficientFunds)]
    assert len(failures) == 1
    assert store.balance == 40

/** 像真实的 I/O 一样：每次读写都让出一次控制权。 */
export class InMemoryStore implements Store {
  constructor(public balance: number) {}

  async read(): Promise<number> {
    await Promise.resolve()
    return this.balance
  }

  async write(balance: number): Promise<void> {
    await Promise.resolve()
    this.balance = balance
  }
}

test('two concurrent withdrawals cannot overdraw', async () => {
  const store = new InMemoryStore(100)
  const account = new Account(store)

  const results = await Promise.allSettled([
    account.withdraw(60), account.withdraw(60)])

  const failures = results.filter(
    (r) => r.status === 'rejected' && r.reason instanceof InsufficientFunds)
  expect(failures).toHaveLength(1)
  expect(store.balance).toBe(40)
})

修复：让「读 — 判断 — 写」不可被打断

public class SafeAccount extends Account {
    public SafeAccount(Store store) { super(store); }

    @Override
    public synchronized void withdraw(int amount) {    // 同一时刻只让一个线程进来
        super.withdraw(amount);
    }
}

class SafeAccount:
    def __init__(self, store) -> None:
        self._store = store
        self._lock = asyncio.Lock()

    async def withdraw(self, amount: int) -> None:
        async with self._lock:                          # 同一时刻只让一个任务进来
            balance = await self._store.read()
            if balance < amount:
                raise InsufficientFunds()
            await self._store.write(balance - amount)

export class SafeAccount {
  private queue: Promise<unknown> = Promise.resolve()

  constructor(private readonly store: Store) {}

  withdraw(amount: number): Promise<void> {
    const run = this.queue.then(() => this.doWithdraw(amount))   // 排在上一笔后面
    this.queue = run.catch(() => undefined)        // 上一笔失败不影响下一笔排队
    return run
  }

  private async doWithdraw(amount: number): Promise<void> {
    const balance = await this.store.read()
    if (balance < amount) throw new InsufficientFunds()
    await this.store.write(balance - amount)
  }
}

同一个测试，换成修复后的类，三种语言都稳定通过（实测）。

⚠ 进程里的锁只管得住这一个进程

上面的锁保护的是内存里的状态。真实系统里余额存在数据库，而你的服务往往同时跑着好几个实例 —— 进程内的锁对别的实例毫无约束力。 这时要靠数据库来保证：把「判断并扣减」写成一条语句（UPDATE … SET balance = balance - 60 WHERE balance >= 60）、 行锁（SELECT … FOR UPDATE）、或者带版本号的乐观锁。

配套示例里就有这个隐患：控制器先读出公司的员工数，在内存里加减，再整个写回去。两个请求同时修改两个用户的邮箱，员工数可能只变一次。 原书没有处理这一点，示例也照原样保留了。

★ 数据库层面的并发，用集成测试来测

按第 8 章的分类，数据库是受管依赖，要用真的。验证「两个事务同时改同一行会怎样」的测试，就是一个开两个连接的集成测试： 事务甲读、事务乙读、甲提交、乙提交，然后断言结果。顺序由测试代码一步步安排，所以它是确定的，不需要压力测试。 用内存里的假仓储测不出这类问题 —— 假仓储没有事务隔离级别。

压力测试该不该进日常的测试集

办法确定吗适合放在哪
单线程事件循环 + 会让出控制权的替身确定普通单元测试，随时跑
两个数据库事务，由测试安排先后确定集成测试
多线程压力测试不确定：通过只说明「这次没撞上」可以进测试集，但要控制规模（几十毫秒级）；它红了一定是真问题，绿了不保证没问题
专门的并发测试工具（能系统地枚举线程交错顺序）确定无锁数据结构这类高风险代码；一般业务代码用不上

和核心 / 外壳的思路一样，最省事的并发测试是不需要写的那种：不共享可变状态（每个请求用自己的对象）、把状态的修改交给数据库的一条原子语句、 或者让所有修改排队经过同一个入口。能用设计消掉的竞态，就别留给测试去抓。

时好时坏的测试

不稳定测试（flaky test）

代码一行没改，同一个测试有时通过、有时失败。

它直接破坏第 4 章的第二根支柱。那一章说，假警报的代价是大家不再相信红色 ——「又是那个测试，重跑一下」。 一旦养成这个习惯，真正的回归也会被重跑掉。所以不稳定的测试不是「小毛病」，要当成缺陷处理。

发现了一个不稳定的测试，怎么办

  1. 先别当它是「测试的问题」。它可能正在告诉你生产代码里有一个真的竞态。上面取款的例子里，时红时绿的测试是对的，错的是代码。
  2. 想办法稳定地重现。单独跑一百遍；打乱测试顺序跑；在一台慢的机器上跑。能稳定重现，就成功了一大半。
  3. 修不了就先隔离，并留下记录。把它移出阻塞合并的那组测试，开一个工单。不要让它继续在主干上随机地红。
  4. 隔离不是终点。隔离区里的测试要么修好放回来，要么删掉。长期躺在隔离区里的测试和没有一样，还多了维护成本（第 1 章）。
⚠ 「失败自动重试三次」是止痛药

很多测试框架和 CI 都支持自动重试失败的测试。它能让流水线先绿起来，但也会把真正的竞态一起藏住：一个十次里出错一次的 Bug，重试三次后几乎永远是绿的。 如果要用，至少让「重试后才通过」的测试被单独统计出来，并且有人负责看。

小结

  • 异步测试有三种特有的坏法：该红却绿（伤防止回归）、等真实时间（伤快速反馈）、时好时坏（伤信任）。
  • 最好的办法在测试之外：把异步留在外壳，决策逻辑保持同步。业务规则的测试里不应该出现 await。
  • 断言必须发生在框架正在等的那条执行流里：测试函数写成异步的并 await 每个结果；Java 在测试线程里取到值再断言。
  • 确认一个异步测试有效的办法：故意把期望值改错，看它会不会红。
  • 时间是依赖。把「等一会儿」作为参数传进来，测试里换成只做记录的替身；或者用假定时器，但记得它改的是全局状态。
  • 等一个插不进手的后台结果时，用轮询 + 超时，不用固定的 sleep。这是退路，不是首选。
  • 竞态条件的期望要按业务规则来写（「恰好一笔成功」）。单线程事件循环里可以稳定重现；多线程下压力测试只能提高概率。
  • 进程里的锁管不了别的实例。跨实例的并发靠数据库保证，并用开两个事务的集成测试来验证。
  • 不稳定的测试是缺陷：先怀疑生产代码，再想办法重现，修不了就隔离并记录。自动重试只是把问题藏起来。

自测

一个异步测试从写出来那天起就一直是绿的。你怎么判断它是真的在验证，还是「断言根本没被执行」？

把它的期望值故意改错（或者把生产代码改错），再跑一遍。如果还是绿的，说明断言没有在框架等待的执行流里执行 —— 多半是少了 await，或者断言写在了回调里。

同事为了测「缓存 5 分钟后过期」，在测试里写了 sleep(300)，并把这个测试标成「夜间才跑」。有什么更好的做法？

把时间变成缓存的一个依赖（传入时钟，或者用假定时器）。测试里先把时钟设在某一刻、写入缓存，再把时钟拨到 5 分钟之后、断言已过期。测试只要一毫秒，可以随时跑，也不会因为机器慢而出错。

多线程压力测试连续跑了一千次都是绿的。能说明代码没有竞态条件吗？

不能。它只说明这一千次都没撞上那个顺序。压力测试红了一定有问题，绿了却不保证没问题。要更有把握，需要让顺序变得可控（单线程交错、由测试安排的两个事务），或者从设计上去掉共享的可变状态。

为什么「两个请求同时修改公司员工数」这种问题，用内存里的假仓储测不出来？

因为问题出在数据库的事务隔离上：两个事务各自读到旧值，再先后写回。假仓储没有事务、没有隔离级别，行为和真数据库不一样。这正是第 8 章坚持「受管依赖用真的」的原因之一。

动手练习

  1. 在你的项目里找一个异步测试，把它的期望值改错，确认它会红。再找找有没有把断言写在回调里的测试。
  2. 搜一下测试代码里的 sleep。每一处问自己：这里是在等一个能 await 的结果，还是在等时间流逝？分别改成 await、轮询或替身。
  3. 把本章的 Account 和它的并发测试敲一遍，亲眼看它在有 Bug 的版本上变红、在加锁的版本上变绿。然后把锁去掉，改用「让存储提供一个原子的扣减操作」来修复。
  4. 进阶：给配套示例写一个集成测试，开两个事务同时把两个客户改成员工，看公司的员工数是加了 2 还是加了 1。再想想该怎么修。
