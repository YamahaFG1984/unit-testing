为什么需要集成测试

你有没有遇到过这种情况：单元测试全绿，应用一跑就挂？各个零件单独验证过了，不代表装在一起能转。 这一章讲集成测试的定位：它该测什么、测多少，哪些外部依赖用真的、哪些用 Mock，以及几条顺带让代码更健康的实践。

本章目标

  • 知道集成测试负责四象限里的哪一块，以及它和单元测试的数量比例
  • 分清受管依赖和不受管依赖：前者用真的，后者用 Mock
  • 给第 7 章的 CRM 写出第一个集成测试
  • 知道什么时候该用接口，什么时候不该
  • 三条最佳实践：明确领域模型边界、减少分层、消除循环依赖
  • 知道日志该不该测、怎么测
💻 本章的代码可以直接运行

第 7–10 章的 CRM 示例在仓库的 examples/ 目录里有 Java / Python / TypeScript 三份完整实现 （本章结束时的状态请以那里为准）。怎么跑起来见第 0 章。

什么是集成测试

复习一下第 2 章：单元测试要同时满足三条 —— 验证一个行为单元、运行得快、与其他测试隔离。 不满足其中至少一条的测试，就是集成测试。换句话说：不是单元测试的测试，都是集成测试。

实践中，集成测试几乎总是在验证系统与进程外依赖的协同工作 —— 也就是第 7 章四象限里的控制器那一格：

再看测试金字塔：该写多少集成测试

单元测试集成测试
防止回归较弱更强 —— 执行的代码更多（包括库的代码）
抵抗重构好更好 —— 离生产代码更远
快速反馈快慢 —— 直接操作进程外依赖
可维护性好差 —— 要保持依赖可用，涉及的协作者多、测试更大
快乐路径（happy path）与边界情况（edge case）

快乐路径：一个业务场景成功执行的那条路。边界情况：业务场景的执行以错误告终的情况。

★ 分工的经验法则

用单元测试检查尽可能多的边界情况；用集成测试覆盖一条快乐路径，外加那些单元测试覆盖不了的边界情况。

金字塔的形状取决于项目复杂度。简单的应用在「领域模型与算法」那一格几乎没代码，测试就成了矩形（单元和集成一样多）， 极简单的情况下甚至没有单元测试。但集成测试始终有价值 —— 代码再简单，也得确认它和其他子系统配合得起来。

集成测试 vs. 快速失败

「单元测试覆盖不了的边界情况」也不是都要用集成测试去测。如果某个边界情况处理错了会让整个应用立刻崩溃，就没必要测它。

例子：第 7 章里控制器必须先调 user.canChangeEmail() 再调 changeEmail()。 「控制器忘了先检查」这个边界情况理论上可以用集成测试覆盖，但没什么价值： 如果控制器真忘了，changeEmail() 里的前置条件会让应用第一次执行就炸，很容易发现和修复，而且不会弄脏数据。

快速失败原则（Fail Fast）

一旦发生任何意料之外的错误，立刻停止当前操作（通常是抛异常）。它是集成测试的一个可行替代方案。

前置条件是快速失败的典型应用：前置条件不满足，说明对应用状态的某个假设错了，这一定是 Bug。 另一个例子是读配置文件：配置不完整或不正确就抛异常，并且把这段逻辑放在应用启动的地方 —— 配置有问题，应用干脆起不来。

💡 再说一遍

不写测试，也好过写一个坏测试。不能提供显著价值的测试就是坏测试。 （注意：User 里的前置条件本身应该测，但用单元测试就够了，不需要集成测试。）

哪些进程外依赖该用真的

集成测试验证的是系统与进程外依赖的集成。验证方式有两种：用真的依赖，或者用 Mock 替换。什么时候用哪种？

受管依赖（managed）不受管依赖（unmanaged）
定义你完全控制的进程外依赖：只能通过你的应用访问你无法完全控制的进程外依赖：别的应用也看得见
交互是否对外可见不可见可见
典型例子应用自己的数据库SMTP 服务器、消息总线
与它的通信属于实现细节可观察行为（契约）
集成测试里怎么办用真实实例用 Mock 替换

为什么不受管依赖要用 Mock？因为你必须保持与它们的通信模式不变（向后兼容），Mock 正好擅长这个：不管怎么重构，都能确认调用还在、参数没变。

为什么受管依赖要用真的？因为只有你的应用和它对话，没有向后兼容的负担。外部客户端不关心你的数据库怎么组织，只关心系统的最终状态。 用真实实例，测试就能从外部客户端的视角验证这个最终状态；而且做数据库重构（给列改名，甚至换一种数据库）时，这样的测试也能帮上忙。

既受管又不受管的依赖：共享数据库

典型的故事：系统一开始有自己专用的数据库；过了一阵，另一个系统也需要其中的数据，于是团队图省事，把几张表共享了出去。 数据库就成了「一半受管、一半不受管」。

用数据库做系统间集成是个糟糕的方式 —— 它把系统耦合在一起，让后续开发变得复杂。更好的方式是 API（同步通信）或消息总线（异步通信）。 但如果你已经有了共享数据库，短期内又改不了：

  • 别的应用看得见的表：当作不受管依赖。这些表实际上扮演着消息总线的角色，表里的行就是消息。用 Mock 确保与这些表的通信模式不变。
  • 其余的表：当作受管依赖。验证它们的最终状态，而不是和它们的交互。

如果集成测试里用不了真的数据库怎么办

有时出于你控制不了的原因（比如 IT 安全策略、成本），测试环境里就是没法部署那个遗留数据库。那要不要干脆 Mock 掉它？

⚠ 不要。那就别写集成测试了

Mock 受管依赖会损害集成测试的抵抗重构能力，防止回归的能力也大打折扣。如果数据库是项目里唯一的进程外依赖， 这样的「集成测试」比现有的单元测试多不出任何保护—— 它唯一多做的事，就是检查控制器调了仓储的哪些方法。 你费了一大堆功夫，换来的只是确认控制器里那三行代码没写错。

如果没法原样测试数据库，就完全不要写集成测试，把精力集中在领域模型的单元测试上。

实例：给 CRM 写集成测试

回到第 7 章的 CRM。「修改邮箱」这个用例里，控制器在数据库、消息总线和领域模型之间做协调：

测哪些场景

最长的快乐路径是「从公司邮箱改成非公司邮箱」—— 它产生的副作用最多：数据库里用户（类型、邮箱）和公司（员工数）都更新了，还往总线发了消息。

单元测试覆盖不了的边界情况只有一个：邮箱不能改的场景。但上面说过，控制器如果漏了这个检查应用会快速失败，所以不用测。 结论：只需要一个集成测试。

给两个依赖分类

  • 应用数据库 → 受管依赖 → 用真的。测试要：往数据库里插入用户和公司 → 执行改邮箱 → 验证数据库状态。
  • 消息总线 → 不受管依赖 → 用 Mock，事后验证控制器和 Mock 之间的交互。

那端到端测试呢

我们的示例项目不写端到端测试。大多数情况下，当集成测试已经把受管依赖纳入范围、只 Mock 不受管依赖时，它提供的保护已经很接近端到端测试了。 不过你仍然可以写一两个总览式的端到端测试，作为部署后的健全性检查：同样走最长的快乐路径；为了模拟外部客户端， 直接检查消息总线，但通过应用本身去验证数据库状态。

★ 断言时要独立于输入数据，重新读一遍数据库

测试在断言阶段单独查询了用户和公司的数据，创建新的 userFromDb 和 companyFromDb，再对它们断言。 这样测试同时走过了写和读两条路，防止回归的效果最好。读取要用控制器内部用的同一套代码（Database、UserFactory、CompanyFactory）。

这个测试能用，但还有改进空间：断言部分可以用辅助方法缩短；messageBusMock 提供的保护也还没到最好。 这两点分别留给第 10 章和第 9 章。

什么时候该用接口

很多人会给数据库、消息总线这类进程外依赖都配一个接口，哪怕这个接口只有一个实现： IMessageBus / MessageBus、IUserRepository / UserRepository…… 这种做法太普遍了，几乎没人质疑。常见的两个理由：

常见理由为什么站不住
「接口抽象了进程外依赖，实现了松耦合」 只有一个实现的接口不是抽象，它提供的松耦合并不比那个具体类更多。 真正的抽象是被发现的，不是被发明的 —— 发现总是事后的事：抽象已经存在了，只是代码里还没明确表达出来。 所以一个接口要成为真正的抽象，至少得有两个实现。
「以后加新功能不用改现有代码，符合开闭原则」 它违反了一个更基本的原则：YAGNI（You Aren't Gonna Need It，你用不上它）。不要为眼下不需要的功能投入时间。 一是机会成本：这些时间本可以花在现在就需要的功能上，而且等真需要时需求多半已经变了； 二是代码越少越好：「以防万一」的代码徒增拥有成本。
💡

写代码是一种昂贵的解决问题的方式。解决方案需要的代码越少、越简单，越好。

那为什么还要给进程外依赖用接口？

真正的原因非常实际：为了能 Mock，仅此而已。（在 Java / C# 这类静态语言里，没有接口就不方便创建测试替身。） 由此得出：

★ 只给不受管依赖用接口

除非你需要 Mock 某个进程外依赖，否则不要给它引入接口。而你只 Mock 不受管依赖。 受管依赖也要显式注入控制器，但用具体类就行。 

public class UserController {
    private final Database database;         // 具体类 —— 受管依赖
    private final IMessageBus messageBus;    // 接口 —— 不受管依赖，需要 Mock

    public UserController(Database database, IMessageBus messageBus) {
        this.database = database;
        this.messageBus = messageBus;
    }

    public String changeEmail(int userId, String newEmail) {
        /* 方法里使用 database 和 messageBus */
    }
}

class UserController:
    # Python 是鸭子类型，Mock(spec=MessageBus) 不需要接口也能造替身。
    # 但原则不变：两个依赖都显式注入；只有 message_bus 会在测试里被 Mock。
    def __init__(self, database: Database, message_bus: MessageBus) -> None:
        self._database = database            # 受管依赖：测试里传真的
        self._message_bus = message_bus      # 不受管依赖：测试里传 Mock

    def change_email(self, user_id: int, new_email: str) -> str:
        ...  # 方法里使用 _database 和 _message_bus

export class UserController {
  constructor(
    private readonly database: Database,         // 具体类 —— 受管依赖
    private readonly messageBus: IMessageBus,    // 接口 —— 不受管依赖，需要 Mock
  ) {}

  changeEmail(userId: number, newEmail: string): string {
    /* 方法里使用 database 和 messageBus */
  }
}

给进程内依赖用接口：危险信号

有的代码库连领域类都配接口：IUser / User。这种接口永远只有一个实现，是一个巨大的危险信号。 引入它的唯一理由还是为了 Mock —— 但和进程外依赖不同，你永远不该检查领域类之间的交互，那会让测试和实现细节耦合（第 5 章）。

集成测试的最佳实践

有三条通用准则。和往常一样，对测试有益的做法，往往也让整个代码库更健康。

① 让领域模型的边界明确

在代码库里给领域模型一个明确的、人尽皆知的位置。领域模型是关于你要解决的问题的领域知识的集合，给它划一条清晰的边界，有助于理解和推理这部分代码。 对测试也有帮助：单元测试针对领域模型，集成测试针对控制器，边界清楚了，两种测试也就好区分了。 边界可以是一个独立的模块 / 包 / 命名空间，形式不重要，重要的是所有领域逻辑都在同一把伞下，而不是散落各处。

② 减少分层

间接层太多会损害你推理代码的能力：每个功能在每一层都有一小块，你得费力把它们拼成完整的图景。 它对测试也没好处：这类代码库里控制器和领域模型的边界往往不清晰，而且大家会倾向于逐层单独验证 —— 结果是一大堆低价值的集成测试，每个只跑某一层的代码，把下面的层全 Mock 掉。防止回归不足，抵抗重构也差。

③ 消除循环依赖

循环依赖（circular dependency）

两个或多个类直接或间接地互相依赖才能正常工作。典型例子是回调。

循环依赖同样给读代码带来巨大的认知负担，也妨碍测试 —— 你往往不得不借助接口和 Mock 才能把类图拆开、隔离出一个行为单元， 而这在测试领域模型时是大忌。很少有代码库能消除所有循环依赖，但至少可以让剩下的那些互相依赖的类簇尽可能小。

④ 在一个测试里用多个执行段？

第 3 章说过，多个执行段是坏味道。比如把「注册用户」和「删除用户」放进同一个集成测试 —— 很诱人，因为第一步的执行正好是第二步的准备。但这样的测试会失去焦点、迅速膨胀。最好拆开。

ⓘ 唯一的例外

测试涉及很难摆到期望状态的进程外依赖时。例如注册用户会在外部银行系统里开户，银行给了你一个沙箱，但沙箱很慢，或者限制调用次数。 这时把多个执行动作合并到一个测试里、减少与它的交互次数，是划算的。

所以：单元测试永远不该有多个执行段（它们不碰进程外依赖）；集成测试也很少需要；多步骤的测试几乎都属于端到端测试。

日志该怎么测

日志是个灰色地带。把问题拆成四个：该不该测？怎么测？打多少日志合适？日志器怎么传递？

该不该测日志

归根结底还是那个问题：日志是应用的可观察行为，还是实现细节？ 日志最终会在进程外依赖（文本文件、数据库）里产生副作用。这些副作用如果是给客户、应用的使用方或开发者以外的任何人看的，那就是可观察行为，必须测； 如果读者只有开发者自己，那就是可以随意修改的实现细节，不该测。

怎么测支持日志

日志涉及进程外依赖，所以规则和其他涉及进程外依赖的功能一样：用 Mock 验证应用与日志存储的交互。 但别直接 Mock 通用的 ILogger。支持日志是业务需求，就在代码里明确地把这个需求表达出来： 建一个专门的 DomainLogger，把业务要求的每一种支持日志都列成一个方法。 

public interface IDomainLogger {
    void userTypeHasChanged(int userId, UserType oldType, UserType newType);
}

public class DomainLogger implements IDomainLogger {
    private final ILogger logger;

    public DomainLogger(ILogger logger) { this.logger = logger; }

    @Override
    public void userTypeHasChanged(int userId, UserType oldType, UserType newType) {
        logger.info("User " + userId + " changed type from " + oldType + " to " + newType);
    }
}

class DomainLogger:
    def __init__(self, logger: logging.Logger) -> None:
        self._logger = logger

    def user_type_has_changed(self, user_id: int, old_type: UserType,
                              new_type: UserType) -> None:
        self._logger.info(
            "User %s changed type from %s to %s", user_id, old_type, new_type)

export interface IDomainLogger {
  userTypeHasChanged(userId: number, oldType: UserType, newType: UserType): void
}

export class DomainLogger implements IDomainLogger {
  constructor(private readonly logger: ILogger) {}

  userTypeHasChanged(userId: number, oldType: UserType, newType: UserType): void {
    this.logger.info(`User ${userId} changed type from ${oldType} to ${newType}`)
  }
}

🔬 结构化日志

DomainLogger 的思路和结构化日志很像。传统日志先拼字符串再写入：logger.info("User Id is " + 12)， 得到的日志文件缺乏结构，很难分析（比如「某类消息有多少条、其中多少和某个用户有关」）。

结构化日志把「捕获日志数据」和「渲染这些数据」解耦：logger.info("User Id is {UserId}", 12) 会把消息模板和参数作为数据保存下来，再按配置渲染成纯文本、JSON 或 CSV。 可以把 userTypeHasChanged() 这个方法名看作消息模板，它的三个参数就是日志数据。

不过有个问题：DomainLogger 代表一个进程外依赖（日志存储）。如果让 User 直接调用它， 领域模型就又和进程外依赖扯上了，User 会滑回过度复杂象限。 解决办法和第 7 章通知外部系统时一样 —— 领域事件：

ⓘ 两点补充

如果支持日志是在控制器里打的（而不是领域类里），就不需要领域事件 —— 控制器本来就负责和进程外依赖打交道，直接用 DomainLogger 即可。

User 里的诊断日志没有改，仍然直接用 logger。这是故意的：诊断日志只给开发者看，不需要测，也就不必把它赶出领域模型。

打多少日志合适

支持日志是业务需求，没得选。你能控制的是诊断日志，而它不宜滥用：

  • 过多的日志让代码变得杂乱，在领域模型里尤其如此。
  • 日志的信噪比是关键。记得越多，越难找到有用的信息。

尽量完全不在领域模型里用诊断日志，多数情况下可以把它从领域类挪到控制器里。即便如此，也只在需要调试时临时使用，调完就删。 理想情况下，诊断日志只用于未处理的异常。

通过静态方法 / 全局变量获取依赖的方式叫环境上下文，这是反模式：依赖是隐藏的、难以替换，测试也更困难。 但作者认为它最大的坏处是掩盖了代码里潜在的问题：如果把 logger 显式注入领域类变得麻烦到你只好用环境上下文， 那说明要么日志打得太多，要么间接层太多。环境上下文不是解药，要去解决根本原因。

小结

  • 集成测试是任何「不是单元测试」的测试，验证系统与进程外依赖的集成。它覆盖控制器；单元测试覆盖算法和领域模型。
  • 集成测试在防止回归和抵抗重构上更好，单元测试在可维护性和反馈速度上更好。所以大部分测试应是单元测试，外加少量集成测试。
  • 用单元测试覆盖尽可能多的边界情况；用集成测试覆盖一条（最长的）快乐路径，以及单元测试覆盖不了的边界情况。
  • 快速失败原则让 Bug 尽早暴露，是集成测试的一个可行替代。
  • 受管依赖只能通过你的应用访问（如应用数据库），与它的通信是实现细节 → 用真实实例。不受管依赖对其他应用可见（如 SMTP、消息总线），与它的通信是可观察行为 → 用 Mock。
  • 共享数据库：对外可见的部分当作不受管依赖，其余当作受管依赖。
  • 集成测试必须穿过所有与受管依赖打交道的层：断言时独立于输入数据，重新查一遍数据库。
  • 只有一个实现的接口不是抽象，也不比具体类更松耦合；为未来假想的实现而设计违反 YAGNI。用这种接口的唯一正当理由是为了 Mock，所以只给不受管依赖用。给领域类配接口是危险信号。
  • 给领域模型一个明确的位置；间接层越少越好（通常三层就够）；消除循环依赖（让被调用方返回值）。
  • 测试里的多个执行段只在涉及难以摆布的进程外依赖时才合理，这几乎总是端到端测试。
  • 支持日志是可观察行为，要测：引入 DomainLogger 明确列出业务要求的日志，用领域事件追踪，在控制器里转成对 DomainLogger 的调用。诊断日志是实现细节，不测，而且要少用。
  • 所有依赖（包括 logger）都应该显式注入，不要用环境上下文。

自测

你的服务用到了：自己的 PostgreSQL、公司统一的 Kafka、一个只有你的服务读写的 Redis 缓存、第三方支付 API。集成测试里各该怎么处理？

自己的 PostgreSQL 和只有自己用的 Redis 是受管依赖 → 用真实实例，验证最终状态。Kafka 和支付 API 是不受管依赖 → 用 Mock，验证交互。

同事说：「我们的测试环境连不上数据库，所以我把 Repository 全 Mock 了，照样写了 200 个集成测试。」有什么问题？

Mock 受管依赖让这些测试既脆弱（和仓储的调用方式耦合）又没多少保护作用 —— 它们只是在确认控制器调了哪些仓储方法。如果确实用不了真数据库，更好的选择是不写这些集成测试，把精力放在领域模型的单元测试上。

运营团队要求「每次用户被封禁都必须记一条日志，他们要据此对账」。这条日志该测吗？怎么测？

该测。它是支持日志，是业务需求，属于可观察行为。在 DomainLogger 里加一个 userHasBeenBanned(...) 方法；领域模型产生一个 UserBannedEvent（单元测试检查事件），控制器把事件转成对 DomainLogger 的调用（集成测试用 Mock 验证）。
