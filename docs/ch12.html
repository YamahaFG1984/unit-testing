第 12 章 · 补充

给遗留代码补测试

前面十一章讲的都是「怎样把代码设计成好测的」。可你手上多半已经有一堆写好了、在线上跑着、一个测试都没有的代码。 这一章讲怎么从那里出发，一步一步、不出事故地走到第 7 章描述的那个样子。

本章目标

  • 理解遗留代码的「先有鸡还是先有蛋」困境，以及怎么打破它
  • 会写特征测试：先把现有行为钉住
  • 会找接缝：用最小、最安全的改动让代码变得可测
  • 把决策逻辑抽出来，换成真正有价值的单元测试，然后拆掉脚手架
  • 改不动的时候，用「新芽」和「包装」的办法加新功能
  • 知道该从哪里下手，以及哪里不值得碰
ⓘ 这一章不是原书内容

本章是教程的补充。其中「特征测试」「接缝」「新芽 / 包装」这些手法出自 Michael Feathers 的 《修改代码的艺术》（Working Effectively with Legacy Code），这里把它们和本教程的框架 （四大支柱、四象限、受管 / 不受管依赖）接了起来。本章的代码是示意性的片段，重构的终点就是仓库里可运行的 examples/。

遗留代码的两难

遗留代码（legacy code）

Feathers 的定义很干脆：没有测试的代码。和它有多老、是谁写的、用什么技术无关。

整个过程分四步。注意第一步写的测试到最后大部分会被删掉 —— 它们是脚手架，不是建筑本身。

起点：一段典型的遗留代码

还是那个「修改用户邮箱」的功能，但这次是它最糟糕的样子：一个方法从头干到尾，数据库和消息总线都通过静态调用直接访问， 用户类型是魔法数字，没有任何测试。它已经在线上跑了三年。

第一步：用特征测试钉住现有行为

特征测试（characterization test）

描述代码现在实际怎么表现的测试 —— 不是它「应该」怎么表现。 它的期望值不来自需求文档，而来自运行代码看到的结果。目的只有一个：之后你动代码时，任何行为变化都会被发现。

怎么写

  1. 从尽量靠外的入口调用。不要为了测试去改被测代码 —— 这一步的全部意义就在于「不改」。对上面的例子，就是直接调 UserService.changeEmail，连一个真的测试数据库。
  2. 先写一个肯定错的断言（比如断言邮箱等于 "???"），运行，让失败信息把实际值告诉你。
  3. 把实际值抄进断言，让测试变绿。
  4. 换一组输入，重复。直到你打算改动的那片代码的每条分支都被走到。
// 脚手架测试：粗、慢、直接对着数据库的行断言 —— 现在这样就对了

用四大支柱打分，这些测试并不好：慢、直接读数据库的行（和表结构耦合）、名字也没有业务含义。 没关系。它们此刻只需要在一件事上得高分：防止回归。等更好的测试就位，它们就退场。

💡 怎么知道钉够了没有

这是覆盖率工具最正当的用途（第 4 章：「分析测试时可以用白盒方法」）： 跑一遍特征测试，看你打算改动的那片代码里还有哪些分支没被走到，为它们补输入。 不需要覆盖整个系统，只需要覆盖你要动的地方。

⚠ 钉的时候发现了 Bug 怎么办

照原样钉住，不要顺手修。写个注释、开个工单。原因有二： 这个「Bug」可能早有别的代码或下游系统在依赖它；而且你现在的任务是重构， 重构和改行为必须分开做 —— 否则测试红了，你分不清是重构弄坏的，还是修 Bug 引起的。

ⓘ 输出很大的时候：黄金样本

如果被测代码产出的是一大段文本、报表或 JSON，逐字段断言太累。可以把当前输出整个存成文件（黄金样本，golden master）， 测试只比较「这次的输出和存下来的是否一模一样」。很多语言有现成的「快照测试」「approval testing」工具。 同样，它是脚手架：对任何格式变化都敏感，不适合长期保留。

这里卡住了：消息总线怎么办

数据库的最终状态可以直接查。但 MessageBus.sendEmailChangedMessage 是个静态调用，测试既拦不住它（跑测试会真的往总线发消息）， 也看不到它发了什么。要钉住这部分行为，必须先在代码上开一个小口子。

第二步：打开接缝

接缝（seam）

代码里这样的一个位置：你可以不修改那个位置本身，就改变那里发生的行为。构造函数参数、可被重写的方法、可被替换的模块，都是接缝。

开缝的改动要小到几乎不可能出错，因为这一步是在没有（或只有部分）测试保护的情况下做的。最稳妥的做法是「加参数，给默认值」—— 现有的调用方一行都不用改： 

public interface MessageSender {
    void sendEmailChangedMessage(int userId, String newEmail);
}

public class UserService {
    private final MessageSender messages;

    public UserService() {                                   // 原来的构造方式照旧可用
        this(MessageBus::sendEmailChangedMessage);
    }

    public UserService(MessageSender messages) {             // 新开的口子
        this.messages = messages;
    }

    public void changeEmail(int userId, String newEmail) {
        /* 前面一字不改 */
        messages.sendEmailChangedMessage(userId, newEmail);  // 只把这一行从静态调用换掉
    }
}

class UserService:
    def __init__(self, send_email_changed=None) -> None:
        # 不传就用原来的那个 —— 现有调用方 UserService() 不受影响
        self._send_email_changed = (
            send_email_changed or message_bus.send_email_changed_message)

    def change_email(self, user_id: int, new_email: str) -> None:
        ...  # 前面一字不改
        self._send_email_changed(user_id, new_email)     # 只把这一行从全局调用换掉

export type SendEmailChanged = (userId: number, newEmail: string) => void

export class UserService {
  constructor(
    // 不传就用原来的那个 —— 现有调用方 new UserService() 不受影响
    private readonly sendEmailChanged: SendEmailChanged =
      MessageBus.sendEmailChangedMessage,
  ) {}

  async changeEmail(userId: number, newEmail: string): Promise<void> {
    /* 前面一字不改 */
    this.sendEmailChanged(userId, newEmail)              // 只把这一行从静态调用换掉
  }
}

★ 接缝只开在不受管依赖上

按第 8 章的分类：消息总线是不受管依赖，需要替换，所以要开缝。 数据库是受管依赖，特征测试直接用真的测试库，不需要为它开缝、更不要 Mock 它。 少开一个缝，就少一处没有测试保护的改动。

ⓘ 实在不想动构造函数？

各语言都有在运行时替换模块 / 静态成员的手段（Python 的 unittest.mock.patch、Vitest 的 vi.mock、Mockito 的 mockStatic）。 它们可以完全不改生产代码就拦住那个静态调用，作为脚手架阶段的权宜之计完全可以。 但别停在那儿：第 11 章说过，隐藏的依赖是问题本身，最终还是要把它变成显式的。

第三步：把决策逻辑抽出来

有了安全网，可以开始真正的重构了。方向就是第 6、7 章讲的：把「做决定」和「动手」分开。 盯着那个方法看，哪几行是在做决定？

对遗留代码，最稳的第一步是抽成一个纯函数（第 6 章的函数式核心）：输入是值，输出也是值，不碰任何外部东西。 这比一上来就设计 User、Company 这些类风险小得多 —— 那可以等逻辑有了测试之后再做。 

public record EmailChangeDecision(boolean changed, int newType, int newNumberOfEmployees) {}

public final class EmailChangePolicy {
    public static EmailChangeDecision decide(
            String currentEmail, int currentType, String newEmail,
            String companyDomain, int numberOfEmployees) {

        if (currentEmail.equals(newEmail)) {
            return new EmailChangeDecision(false, currentType, numberOfEmployees);
        }

        int newType = newEmail.split("@")[1].equals(companyDomain) ? 2 : 1;
        int delta = currentType == newType ? 0 : (newType == 2 ? 1 : -1);

        return new EmailChangeDecision(true, newType, numberOfEmployees + delta);
    }
}

// UserService 变成了「读 — 决定 — 写」
public void changeEmail(int userId, String newEmail) {
    Object[] data = Database.getUserById(userId);
    Object[] companyData = Database.getCompany();

    EmailChangeDecision decision = EmailChangePolicy.decide(
        (String) data[1], (int) data[2], newEmail,
        (String) companyData[0], (int) companyData[1]);

    if (!decision.changed()) return;

    if (decision.newNumberOfEmployees() != (int) companyData[1]) {
        Database.saveCompany(decision.newNumberOfEmployees());
    }
    Database.saveUser(userId, newEmail, decision.newType());
    messages.sendEmailChangedMessage(userId, newEmail);
}

@dataclass(frozen=True)
class EmailChangeDecision:
    changed: bool
    new_type: int
    new_number_of_employees: int


def decide_email_change(current_email: str, current_type: int, new_email: str,
                        company_domain: str, number_of_employees: int) -> EmailChangeDecision:
    if current_email == new_email:
        return EmailChangeDecision(False, current_type, number_of_employees)

    new_type = 2 if new_email.split("@")[1] == company_domain else 1
    delta = 0 if current_type == new_type else (1 if new_type == 2 else -1)

    return EmailChangeDecision(True, new_type, number_of_employees + delta)


# UserService 变成了「读 — 决定 — 写」
def change_email(self, user_id: int, new_email: str) -> None:
    data = database.get_user_by_id(user_id)
    company_data = database.get_company()

    decision = decide_email_change(
        data[1], data[2], new_email, company_data[0], company_data[1])

    if not decision.changed:
        return

    if decision.new_number_of_employees != company_data[1]:
        database.save_company(decision.new_number_of_employees)
    database.save_user(user_id, new_email, decision.new_type)
    self._send_email_changed(user_id, new_email)

export interface EmailChangeDecision {
  readonly changed: boolean
  readonly newType: number
  readonly newNumberOfEmployees: number
}

export function decideEmailChange(
  currentEmail: string, currentType: number, newEmail: string,
  companyDomain: string, numberOfEmployees: number,
): EmailChangeDecision {
  if (currentEmail === newEmail) {
    return { changed: false, newType: currentType, newNumberOfEmployees: numberOfEmployees }
  }

  const newType = newEmail.split('@')[1] === companyDomain ? 2 : 1
  const delta = currentType === newType ? 0 : newType === 2 ? 1 : -1

  return { changed: true, newType, newNumberOfEmployees: numberOfEmployees + delta }
}

async changeEmail(userId: number, newEmail: string): Promise<void> {
  const data = await Database.getUserById(userId)
  const companyData = await Database.getCompany()

  const decision = decideEmailChange(
    data[1] as string, data[2] as number, newEmail,

⚠ 留意：这次抽取悄悄改了一个行为

原来的代码是「邮箱没变就不去读公司」；抽取后变成了无条件先读公司。最终状态和发出的消息都没变，特征测试照样全绿 —— 因为与受管依赖（自己的数据库）的交互次数本来就是实现细节，不该被钉住（第 5、8 章）。 这正是第 7 章讲的取舍：为了让决策集中，多付出一次查询。如果那次查询很贵，就用 CanExecute/Execute 模式把「要不要继续」先问出来。 关键是你得知道自己做了这个取舍。

每做一小步就跑一遍特征测试。它们全绿，说明行为没变。然后，给新抽出来的核心写真正的单元测试 —— 基于输出、毫秒级、没有任何准备工作：

@Test

        "user@mycorp.com", 2, "new@gmail.com", "mycorp.com", 1);

    assertThat(decision).isEqualTo(new EmailChangeDecision(true, 1, 0));

@Test

    EmailChangeDecision decision = EmailChangePolicy.decide(
        "user@mycorp.com", 2, "user@mycorp.com", "mycorp.com", 1);

到这里逻辑已经有了像样的保护。接下来的事就是第 7 章的内容了，可以从容地做： 把魔法数字换成 UserType，把这个纯函数演化成 User.changeEmail(newEmail, company) 和 Company， 引入领域事件，把静态的 Database 换成显式注入的仓储和事务……每一步都有测试罩着。 终点就是仓库里 examples/ 的样子。

第四步：拆掉脚手架

这一步最容易被忘掉。特征测试完成了使命，但它们慢、和表结构耦合、名字没有业务含义 —— 留着就是第 1 章说的「净价值为负的测试」。

  • 边界情况（邮箱相同、类型不变、公司 → 非公司……）现在都由单元测试覆盖了 → 对应的特征测试删掉。
  • 挑最长的那条成功路径，把它那个特征测试改写成第 8–10 章那样的集成测试：通过仓储读数据而不是直接查表，在系统边缘验证消息，起一个有业务含义的名字。
  • 删之前做一次检查：故意在生产代码里改错一个地方（比如把 +1 改成 -1），确认新测试会红。这是对新安全网的验收。

改不动的时候：新芽与包装

有时你没有时间做上面这一整套，只是要在一坨遗留代码里加一个新功能。这时至少可以做到：新写的代码有测试，并且不让遗留代码变得更糟。

例子：新需求是「已确认的邮箱不能再改」。不要把判断直接揉进那个长方法，而是把它写成一个独立的、有测试的小函数，再在遗留方法开头插一行： 

// 新芽：独立的、有测试的新逻辑
public final class EmailChangeRules {
    public static String canChangeEmail(boolean isEmailConfirmed) {
        return isEmailConfirmed ? "Can't change a confirmed email" : null;
    }
}

@Test
void a_confirmed_email_cannot_be_changed() {
    assertThat(EmailChangeRules.canChangeEmail(true))
        .isEqualTo("Can't change a confirmed email");
}

// 遗留方法里只加这两行（返回类型从 void 改成能带回错误信息的 String）
public String changeEmail(int userId, String newEmail) {
    Object[] data = Database.getUserById(userId);
    String error = EmailChangeRules.canChangeEmail((boolean) data[3]);   // ← 新增
    if (error != null) return error;                                     // ← 新增
    /* 其余不动 */
}

遗留方法还是那么糟，但没有变得更糟，而新规则有了自己的测试和自己的家。 攒够几个这样的新芽，你会发现「核心」已经悄悄长出来了，到时候再做第三步就轻松得多。

从哪里下手

不要试图给整个遗留系统补测试 —— 那是把覆盖率当目标的另一种形式（第 1 章）。测试的价值取决于它保护的是什么，所以要挑地方：

💡 怎么找「经常改」的代码

版本历史会告诉你。例如 git log --since="1 year ago" --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20 能列出过去一年被修改次数最多的 20 个文件。再对照缺陷记录看哪些文件老出 Bug，两份名单的交集就是起点。

最实用的触发时机是：当你正好要改某段遗留代码的时候。改之前先钉住，改的过程中抽出一点核心，改完比来时干净一点。日积月累，常改的地方会自然变好。

常见的坑

做法为什么是坑应该怎样
边重构边顺手修 Bug、加功能测试红了分不清原因；出了问题没法干净地回退一次只做一样，分开提交
为了能写单元测试，把所有依赖都 Mock 掉，包括数据库得到一堆和实现绑死的脆弱测试（第 5、8 章），而且给了你虚假的安全感钉行为时用真数据库；只替换不受管依赖
把特征测试当成最终成果留着慢、脆、不表达业务含义，长期是负资产单元测试就位后删掉，只留一个集成测试
先定一个覆盖率目标再开工大家会去挑最容易刷数字的代码，而不是最需要保护的按图 12-8 挑地方
开缝时顺便「整理一下」周围的代码开缝阶段的保护最弱，改动越多风险越大开缝只做最小改动，整理留到有测试之后
一上来就想重写遗留代码里沉淀了多年的边界情况处理，重写会把它们全丢掉钉住、抽取、逐步替换

小结

  • 遗留代码 = 没有测试的代码。它的困境是：改代码需要测试，写测试又需要改代码。
  • 打破困境靠两样东西：不用改代码就能写的特征测试，和小到几乎不会出错的接缝。
  • 特征测试记录的是代码「现在做什么」，期望值来自实际运行结果。它是脚手架：粗、慢都没关系，只求防止回归。
  • 钉的时候发现 Bug，照原样钉住，另开工单。重构和改行为一次只做一样。
  • 接缝只开在不受管依赖上；受管依赖（自己的数据库）在特征测试里直接用真的。
  • 有了安全网之后，把决策逻辑抽成没有协作者的代码（最稳妥的是纯函数），为它写基于输出的单元测试，再朝第 7 章的领域模型演进。
  • 单元测试就位后拆掉脚手架：删掉大部分特征测试，把最长的成功路径改写成一个集成测试。
  • 没条件重构时，用新芽和包装加功能：新代码有测试，旧代码不变糟。
  • 不要追求给整个系统补测试。从「又重要、又经常改」的地方开始，在每次要改它的时候顺手做。

自测

写特征测试时，你发现某种输入下系统算出的折扣明显是错的。这个测试的断言该写正确的值还是错误的值？

写系统现在实际给出的（错误的）值，并加注释、开工单。特征测试回答的是「行为变没变」而不是「对不对」。等重构完成、有了好的测试之后，再作为一次单独的行为变更去修它。

同事建议：「数据库太慢了，特征测试里把 Database 也 Mock 掉吧。」你怎么看？

不建议。自己的数据库是受管依赖，Mock 它会让测试和「调了哪些查询、调了几次」这种实现细节绑死，而重构恰恰会改变这些 —— 测试会在你没弄坏任何东西时变红。特征测试慢是可以接受的，它们是临时的。

第三步做完后，特征测试和新的单元测试都是绿的。为什么还要费事删掉特征测试？

因为它们现在的净价值是负的：同样的逻辑已经被更快、更稳定的单元测试覆盖，而它们继续拖慢测试集、继续在表结构变化时误报。测试也是代码，是负债（第 1 章）。

  2. 在你的项目里跑一下图 12-8 下面那条 git log 命令，找出改动最频繁的五个文件。它们有测试吗？
  3. 挑其中一个你下周正好要改的方法，改之前先给它写两三个特征测试。记录一下：有没有发现让你意外的行为？
