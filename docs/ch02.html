什么是单元测试

「单元测试」这四个字听起来人人都懂，但对其中一个词的不同理解，把整个社区分成了两派。 搞清楚这个分歧，你才能看懂后面关于 Mock 的所有讨论。

本章目标

  • 背下单元测试的三个特征，并知道哪一个有争议
  • 区分共享依赖、私有依赖、进程外依赖、易变依赖这几个容易混的词
  • 看懂同一个功能用经典学派和伦敦学派分别怎么测
  • 理解为什么本教程站在经典学派一边
  • 分清单元测试、集成测试、端到端测试

单元测试的定义

定义有很多版本，去掉枝节后都包含这三点。单元测试是一种自动化测试，它：

学派别名代表作
经典学派（Classical）底特律学派（Detroit）Kent Beck《测试驱动开发：实战与模式解析》
伦敦学派（London）Mockist（爱用 Mock 的人，不过他们自己不太喜欢这个叫法）Freeman & Pryce《测试驱动的面向对象软件开发》

贯穿本章的例子：网上商店

一个极简的场景：顾客在商店买东西。库存够，购买成功，库存减去购买数量； 库存不够，购买失败，库存不变。 

public enum Product { SHAMPOO, BOOK }

public class Store {
    private final Map<Product, Integer> inventory = new HashMap<>();

    public boolean hasEnoughInventory(Product product, int quantity) {
        return getInventory(product) >= quantity;
    }

    public void removeInventory(Product product, int quantity) {
        if (!hasEnoughInventory(product, quantity)) {
            throw new IllegalStateException("Not enough inventory");
        }
        inventory.merge(product, -quantity, Integer::sum);
    }

    public void addInventory(Product product, int quantity) {
        inventory.merge(product, quantity, Integer::sum);
    }

    public int getInventory(Product product) {
        return inventory.getOrDefault(product, 0);
    }
}

public class Customer {
    public boolean purchase(Store store, Product product, int quantity) {
        if (!store.hasEnoughInventory(product, quantity)) {
            return false;
        }
        store.removeInventory(product, quantity);
        return true;
    }
}

from enum import Enum


class Product(Enum):
    SHAMPOO = "shampoo"
    BOOK = "book"


class Store:
    def __init__(self) -> None:
        self._inventory: dict[Product, int] = {}

    def has_enough_inventory(self, product: Product, quantity: int) -> bool:
        return self.get_inventory(product) >= quantity

    def remove_inventory(self, product: Product, quantity: int) -> None:
        if not self.has_enough_inventory(product, quantity):
            raise ValueError("Not enough inventory")
        self._inventory[product] -= quantity

    def add_inventory(self, product: Product, quantity: int) -> None:
        self._inventory[product] = self.get_inventory(product) + quantity

    def get_inventory(self, product: Product) -> int:
        return self._inventory.get(product, 0)


class Customer:
    def purchase(self, store: Store, product: Product, quantity: int) -> bool:
        if not store.has_enough_inventory(product, quantity):
            return False
        store.remove_inventory(product, quantity)
        return True

export enum Product { Shampoo = 'shampoo', Book = 'book' }

export class Store {
  private inventory = new Map<Product, number>()

  hasEnoughInventory(product: Product, quantity: number): boolean {
    return this.getInventory(product) >= quantity
  }

  removeInventory(product: Product, quantity: number): void {
    if (!this.hasEnoughInventory(product, quantity)) {
      throw new Error('Not enough inventory')
    }
    this.inventory.set(product, this.getInventory(product) - quantity)
  }

  addInventory(product: Product, quantity: number): void {
    this.inventory.set(product, this.getInventory(product) + quantity)
  }

  getInventory(product: Product): number {
    return this.inventory.get(product) ?? 0
  }
}

export class Customer {
  purchase(store: Store, product: Product, quantity: number): boolean {
    if (!store.hasEnoughInventory(product, quantity)) {
      return false
    }
    store.removeInventory(product, quantity)
    return true
  }
}

先记住三个贯穿全书的缩写：

术语含义本例中
SUT（System Under Test，被测系统）这个测试要验证的那个类Customer
MUT（Method Under Test，被测方法）测试调用的 SUT 上的那个方法purchase()
协作者（Collaborator）SUT 要与之配合的、状态会变的依赖Store

伦敦学派：把被测代码和协作者隔开

伦敦学派对「隔离」的理解是：把被测系统和它的协作者隔离开。 一个类如果依赖别的类，测试时就把这些依赖全部换成测试替身。

测试替身（test double）

外表和行为都像真实依赖、但其实是简化版的对象，用来降低复杂度、方便测试。这个名字来自电影里的「特技替身」（stunt double）。

Mock

测试替身的一种，特点是可以让你检查 SUT 和协作者之间的交互（调没调、调了几次、传了什么参数）。 很多人把 Mock 和测试替身当同义词，严格来说 Mock 只是其中一类（第 5 章细讲）。

这样做有三个看起来很诱人的好处：

  • 定位精确。测试挂了，嫌疑人只有被测类自己。
  • 切断对象图。类依赖类、依赖又有依赖……用替身换掉直接依赖，后面那一长串就都不用管了，准备工作大大减少。
  • 结构简单。可以定一条全项目通用的规矩：一个生产类，对应一个测试类。

同一个功能，两种写法

经典风格：用真的 Store

测试没有替换协作者，用的是一个货真价实的 Store。于是这个测试实际上同时验证了 Customer 和 Store： 如果 Store 内部有 Bug，哪怕 Customer 完全正确，这些测试也会失败。

伦敦风格：把 Store 换成 Mock

要用 Mock，通常先给 Store 抽一个接口，让 Customer.purchase 接收接口而不是具体类 （Python 靠鸭子类型，不抽接口也行）。然后： 

@Test
void purchase_succeeds_when_enough_inventory() {
    // Arrange：不创建真的 Store，直接告诉替身「被问到时怎么回答」
    IStore storeMock = mock(IStore.class);
    when(storeMock.hasEnoughInventory(Product.SHAMPOO, 5)).thenReturn(true);
    var customer = new Customer();

    // Act
    boolean success = customer.purchase(storeMock, Product.SHAMPOO, 5);

    // Assert：检查的是「顾客对商店做了什么调用」
    assertThat(success).isTrue();
    verify(storeMock, times(1)).removeInventory(Product.SHAMPOO, 5);
}

@Test
void purchase_fails_when_not_enough_inventory() {
    IStore storeMock = mock(IStore.class);
    when(storeMock.hasEnoughInventory(Product.SHAMPOO, 5)).thenReturn(false);
    var customer = new Customer();

    boolean success = customer.purchase(storeMock, Product.SHAMPOO, 5);

    assertThat(success).isFalse();
    verify(storeMock, never()).removeInventory(Product.SHAMPOO, 5);
}

from unittest.mock import Mock


def test_purchase_succeeds_when_enough_inventory():
    # Arrange：不创建真的 Store，直接告诉替身「被问到时怎么回答」
    store_mock = Mock(spec=Store)
    store_mock.has_enough_inventory.return_value = True
    customer = Customer()

    # Act
    success = customer.purchase(store_mock, Product.SHAMPOO, 5)

    # Assert：检查的是「顾客对商店做了什么调用」
    assert success is True
    store_mock.remove_inventory.assert_called_once_with(Product.SHAMPOO, 5)


def test_purchase_fails_when_not_enough_inventory():
    store_mock = Mock(spec=Store)
    store_mock.has_enough_inventory.return_value = False
    customer = Customer()

    success = customer.purchase(store_mock, Product.SHAMPOO, 5)

    assert success is False
    store_mock.remove_inventory.assert_not_called()

import { vi } from 'vitest'

function createStoreMock(hasEnough: boolean): IStore {
  return {
    hasEnoughInventory: vi.fn().mockReturnValue(hasEnough),
    removeInventory: vi.fn(),
    addInventory: vi.fn(),
    getInventory: vi.fn(),
  }
}

test('purchase succeeds when enough inventory', () => {
  // Arrange：不创建真的 Store，直接告诉替身「被问到时怎么回答」
  const storeMock = createStoreMock(true)
  const customer = new Customer()

  // Act
  const success = customer.purchase(storeMock, Product.Shampoo, 5)

  // Assert：检查的是「顾客对商店做了什么调用」
  expect(success).toBe(true)
  expect(storeMock.removeInventory).toHaveBeenCalledOnce()
  expect(storeMock.removeInventory).toHaveBeenCalledWith(Product.Shampoo, 5)
})

test('purchase fails when not enough inventory', () => {
  const storeMock = createStoreMock(false)
  const customer = new Customer()

  const success = customer.purchase(storeMock, Product.Shampoo, 5)

  expect(success).toBe(false)
  expect(storeMock.removeInventory).not.toHaveBeenCalled()
})

经典学派：把测试和测试隔开

经典学派对「隔离」的理解完全不同：需要被隔离的不是代码，而是测试本身。 测试之间应该互不影响 —— 这样你可以并行跑、顺序跑、以任意顺序跑，结果都一样。

按这个理解，一次测试同时用到好几个类完全没问题，只要它们都待在内存里、不去碰共享状态。 测试正是通过共享状态互相干扰的。举个例子：测试 A 在准备阶段往数据库插入一个客户， 测试 B 在自己的准备阶段把它删了。两个测试并行跑，A 就会失败 —— 不是因为代码坏了，而是被 B 搅了局。

这也带来了对「单元」的不同理解：单元不必是一个类，可以是一组类，只要里面没有共享依赖。

几种依赖，一次分清

下面这几个词会在全书反复出现，值得现在就弄明白。

名称定义例子
共享依赖
shared		被多个测试共用，并且让它们有办法影响彼此结果的依赖静态可变字段、数据库、文件系统
私有依赖
private		不是共享的依赖测试里 new 出来的 Store
进程外依赖
out-of-process		运行在应用进程之外的依赖，是通往「还不在内存里的数据」的代理数据库、消息队列、第三方 API
易变依赖
volatile		需要额外搭建运行环境，或者行为不确定的依赖数据库、API 服务、随机数生成器、当前时间
ⓘ 单例一定是共享依赖吗？

不一定。「共享」是指在测试之间共享，不是在生产代码的类之间共享。 比如配置类在生产环境只有一个实例，但只要它是通过构造函数注入的，每个测试都可以 new 一个新的 —— 这时它就是私有依赖。而数据库和文件系统你没法每个测试新建一个，所以要么共享，要么用替身换掉。

🔬 共享依赖 vs. 易变依赖

两个概念有重叠，但不一样：

  • 数据库：既共享又易变。
  • 文件系统：共享但不易变 —— 每台开发机上都有，行为基本确定；但测试能通过它互相干扰。
  • 随机数生成器：易变但不共享 —— 每次结果不同，但可以给每个测试一个独立实例。

替换共享依赖还有一个好处：快。共享依赖几乎都在进程外，调用它们比调用内存里的对象慢得多。 而「运行得快」是单元测试的第二个特征，所以碰了共享依赖的测试会被划到集成测试那边去。

两个学派如何对待依赖

伦敦学派虽然到处用替身，但也不是所有依赖都换。判断标准是依赖是否可变： 永远不会变的对象（不可变对象）不用换。

回头看伦敦风格的测试：Store 换成了 Mock，但 Product.SHAMPOO 和数字 5 都是原样使用的。 你不会想给数字 5 造一个替身吧？因为它不可能被改。这种不可变对象叫值对象（value object）。

值对象（value object）

没有独立身份、完全由内容来标识的不可变对象。两个内容相同的值对象可以互相替换 —— 两个整数 5，用哪个都一样。

把目前为止的差别汇总成一张表：

隔离的对象一个「单元」是对什么使用测试替身
伦敦学派单元（类）之间一个类除不可变依赖以外的所有依赖
经典学派测试之间一个类，或一组类共享依赖
ⓘ 协作者 vs. 依赖

在 customer.purchase(store, Product.SHAMPOO, 5) 这个调用里有三个依赖。 store 是协作者（它的状态会变）；另外两个是值，不是协作者。

两个学派的优劣

本教程（和原书作者）偏向经典学派。理由是：它写出的测试质量更高，更适合实现「可持续增长」这个终极目标。 核心原因是脆弱性 —— 用 Mock 的测试比经典测试更容易在重构时莫名其妙地变红（第 5 章细讲）。 下面逐条看伦敦学派的三个卖点为什么站不住。

卖点一：粒度更细，一次只测一个类

做面向对象开发的人习惯把类当成最基本的积木，于是很自然地把类当成测试的基本单位。 这个倾向可以理解，但它把人带偏了。

★ 测试应该验证「行为单元」，而不是「代码单元」

一个行为单元是对问题领域有意义的东西 —— 最好是业务人员一听就觉得有用的东西。 实现它用了几个类根本不重要：可能跨好几个类，可能只有一个类，也可能只是一个小方法。

测试应该在讲一个故事，而且这个故事要让不懂编程的人也觉得连贯、有意义：

✓ 一个连贯的故事（测行为）

我叫我的狗，它就跑到我身边来。

✗ 一堆动作（测类）

我叫我的狗，它先迈左前腿，再迈右前腿，头转过来，尾巴开始摇……

右边那个故事让人摸不着头脑：这些动作是要干什么？狗是朝我来，还是在逃跑？看不出来。 当你把测试对准一个个单独的类（狗的腿、头、尾巴），而不是真正的行为（狗回到主人身边）时，测试就是这个样子。

卖点二：更容易测试一大张互相关联的类图

没错，用 Mock 可以切断依赖图，省掉大量准备工作。但这条理由找错了问题。 你该关心的不是「怎么测一大团纠缠的类」，而是「怎么一开始就别有这么一大团」。大而复杂的类图通常是设计出了问题。

测试把这个问题暴露出来其实是好事 —— 还记得第 1 章说的吗？「很难测」是代码质量差的可靠信号。 如果为了测一个类，准备阶段长得离谱，这就是在报警。Mock 只是把警报捂住了，并没有解决根本问题。

卖点三：测试失败时能精确定位 Bug

伦敦风格下，一个 Bug 通常只让包含它的那个类的测试失败；经典风格下，用到这个类的其他测试也会跟着失败，产生连锁反应。 这确实是个问题，但不大：

  • 如果你经常跑测试（最好每次改动后都跑），你知道是什么引起的 —— 就是你刚刚改的那个地方。
  • 不用挨个看失败的测试，修好一个，其他的自动就好了。
  • 连锁失败本身也是信息：一个改动让一大片测试变红，说明你刚碰的那段代码非常关键，整个系统都依赖它。

其他差别：TDD 的方向，和过度指定

ⓘ 什么是测试驱动开发（TDD）

一种靠测试来推动开发的流程。每个测试用例都重复三步：

伦敦学派经典学派
TDD 方向由外向内（outside-in）：从高层测试开始，用 Mock 指定它该和哪些协作者交谈，再一层层往里实现由内向外（inside-out）：从领域模型开始，一层层往外加，直到用户能用
过度指定更容易把测试和实现细节绑死相对不容易
⚠ 最关键的区别：过度指定（over-specification）

过度指定就是测试和被测系统的实现细节耦合在了一起。伦敦风格比经典风格更容易写出这种测试 —— 这是反对「到处用 Mock」最主要的理由。从第 4 章开始会逐步展开。

集成测试和端到端测试

两派对「集成测试」的定义也不一样。伦敦学派认为：只要用了真实的协作者对象，就是集成测试。 按这个标准，上面那两个经典风格的测试在伦敦学派眼里都算集成测试。

本教程采用经典学派的定义。把单元测试的三个特征按经典学派的理解重新表述一遍：

★ 单元测试的最终定义（经典学派）
  • 验证一个行为单元，
  • 运行得快，
  • 并且与其他测试相互隔离。

集成测试，就是至少不满足其中一条的测试。

不满足哪条典型情况
不能与其他测试隔离访问了共享依赖（如数据库）。并行跑会互相干扰，只能排队顺序执行
不够快访问了进程外依赖。一次数据库调用就是几百毫秒，测试多了每一秒都很要紧
验证了不止一个行为单元为了提速把两个慢测试合并成一个；或者验证两个团队开发的模块如何协同工作

端到端测试是集成测试的子集

端到端测试（end-to-end，E2E）也是检查代码和进程外依赖如何协同工作，区别在于它包含的进程外依赖更多： 集成测试通常只带一两个，端到端测试带上全部或绝大多数，从最终用户的角度验证整个系统。 UI 测试、GUI 测试、功能测试这些说法，基本可以看作它的同义词。

假设你的应用有三个进程外依赖：数据库、文件系统、支付网关。典型的集成测试会把数据库和文件系统纳入范围， 用替身换掉支付网关。因为前两者你能完全控制，很容易在测试里摆成需要的状态；支付网关则不行 —— 你可能得联系支付公司开一个专门的测试账号，还要时不时手动清理以前测试留下的扣款记录。

💡 端到端测试该什么时候跑

它的维护成本最高，所以适合放在构建流程的后段：等所有单元测试和集成测试都过了再跑， 甚至只在构建服务器上跑，不在开发者自己的机器上跑。 另外，即使是端到端测试，也未必能带上所有依赖（有的依赖根本没有测试版本）， 所以集成测试和端到端测试之间并没有一条清晰的界线。

小结

  • 单元测试的定义（经典版）：验证一个行为单元、运行得快、与其他测试隔离。
  • 「隔离」的含义是争议焦点，由此分出两个学派，它们对「单元是什么」「怎么处理依赖」的看法也跟着不同。
  • 伦敦学派：隔离的是被测单元；单元 = 类；除不可变依赖外全部换成测试替身。
  • 经典学派：隔离的是测试；单元 = 行为；只把共享依赖换成测试替身。
  • 共享依赖是让测试能互相影响的依赖。它和进程外依赖、易变依赖有重叠但不等同。
  • 伦敦学派的三个好处（粒度细、易测大类图、定位准）各有问题：该测的是行为不是类；难测是设计问题，Mock 只是掩盖它；Bug 多半就在你刚改的地方。
  • 伦敦学派最大的问题是过度指定 —— 测试和实现细节耦合。
  • 集成测试 = 至少不满足单元测试三条标准之一的测试。端到端测试是它的子集，包含全部或几乎全部进程外依赖。

自测

一个测试 new 了三个不同的类并让它们协作，没有访问数据库或文件。按经典学派它是单元测试吗？按伦敦学派呢？

经典学派：是。只要它验证的是一个行为单元、跑得快、不和别的测试共享状态。伦敦学派：不是，它用了真实的协作者，会被归为集成测试。

文件系统是共享依赖吗？是易变依赖吗？

是共享依赖（测试可以通过文件互相干扰），但不是易变依赖（每台机器都有，行为确定）。

为什么伦敦风格的测试里没有给 Product.SHAMPOO 造一个 Mock？

因为它是不可变的值对象。伦敦学派只替换可变的依赖（协作者）；值对象没有可被改变的状态，原样使用即可。

动手练习

  1. 把本章的 Store 和 Customer 敲出来，先写经典风格的两个测试并跑通。
  2. 再写伦敦风格的两个测试。然后做个实验：把 Customer.purchase 的实现改成 不调用 hasEnoughInventory，而是直接比较 store.getInventory(product) >= quantity。 行为完全没变 —— 哪种风格的测试挂了？为什么？
  3. 列出你当前项目里的五个依赖，给每个标上：共享 / 私有？进程内 / 进程外？可变 / 值对象？
  4. 找一个你写过的测试，试着用「我叫我的狗，它就跑过来」那样的一句话描述它在验证什么。说不出来的话，它测的可能是代码而不是行为。
