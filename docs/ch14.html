变异测试与属性测试

第 1 章留下了一个问题：覆盖率只能说明代码被执行过，不能说明它被验证过。那用什么来衡量？ 这一章介绍两种工具。变异测试回答「代码要是错了，测试会发现吗」；属性测试回答「有没有哪种输入是我没想到的」。

本章目标

  • 理解变异测试的原理，会在三种语言里把它跑起来
  • 会读变异测试的报告：哪些「幸存者」值得补测试，哪些不值得
  • 理解属性测试和举例测试的区别，会写出不照抄实现的属性
  • 看懂「收缩」后的最小反例，并知道拿它怎么办
  • 知道这两种工具各自的代价，以及它们测不出什么
ⓘ 这一章不是原书内容

本章是教程的补充。文中所有数字和输出都是在配套示例 examples/ 上实际运行得到的（mutmut 3.8、PIT 1.17、Stryker 10；Hypothesis 6、jqwik 1.9、fast-check 4）。 变异测试的配置已经放进了示例，你可以照着命令重现；属性测试的代码没有放进示例，但文中的每一段都运行过。 工具版本不同，具体数字会有出入。

覆盖率回答不了的两个问题

变异测试：故意把代码改错，看测试红不红

变异测试（mutation testing）

工具自动对生产代码做一处很小的修改（比如把 + 改成 -），得到一个变异体，然后跑一遍测试。 有测试变红，说明这个错误会被发现，变异体被杀死；测试全绿，说明这处错误没人管，变异体幸存。对每一处可改的地方重复这个过程。

工具会做哪些修改？各家略有不同，但大致是这几类：

变异类型原来改成没被杀死说明什么
算术 / 符号a + b、1a - b、-1算出来的结果没被断言
比较边界x >= 0x > 0没有恰好踩在边界上的测试
条件取反 / 写死if (a == b)if (a != b)、if (true)这个分支的两个方向没有都被验证
删掉一次调用check(x);（整行删掉）这次调用的效果没被任何测试观察到
替换返回值return result;return null;、return "";返回值没被断言
替换字面量"Precondition failed"""没有测试关心这段文本

一个实验：把断言全删掉

第 1 章说过，没有断言的测试照样能把覆盖率刷满。我们拿配套示例的 Python 版实际试一下： 把 10 个单元测试里的 assert 语句全部换成 pass（保留了 pytest.raises 那几处），然后分别看覆盖率和变异测试的结果。

⚠ 三个工具的数字不能互相比

同一份逻辑，mutmut 造了 86 个变异体，PIT 造了 39 个，Stryker 造了 56 个 —— 因为它们各自会做的修改种类不一样。 得分分别是 83%、74%、87.5%，这并不说明 TypeScript 版的测试比 Java 版好。 变异得分只能和同一个项目、同一个工具的过去比。

读报告：幸存者要一个一个看

变异测试的价值不在那个百分比，而在没被杀死的名单。它们分两大类，处理办法不同：

拿示例上的真实结果走一遍：

没被杀死的变异体（实测）属于哪种情况怎么处理
CompanyFactory.create 里的全部变异体（三个工具都报了「没有覆盖」） 单元测试没执行到。它只在集成测试里被用到，而变异测试没有跑集成测试 补一个单元测试。它和 UserFactory 是同一类代码（把数据库的一行还原成对象，没有协作者），而 UserFactory 有单元测试、它没有 —— 这是个真实的不一致
UserFactory.create 里删掉 Precondition.requires(…)（PIT、Stryker 报「幸存」） 执行到了，行为也变了：一行残缺的数据不再被拒绝 值得补：加一个「数据不完整时立即失败」的测试，成本很低
把 "Precondition failed" 改成 "" 或别的文本（mutmut 报了 4 个，Stryker 报了 1 个） 执行到了，行为严格说也变了：异常里的文字不同 不补。这段文字是给开发者看的，没有调用方依赖它。为它写断言，只会让测试在有人改措辞时变红（第 4 章：假警报）
User.isEmailConfirmed() 的返回值被换成恒为 true（PIT 报「幸存」） 一个只被持久化代码使用的取值方法 不补单元测试。琐碎代码（第 7 章）；保存用户时的集成测试会间接验证它
等价变异体（equivalent mutant）

代码被改了，但程序的行为在任何输入下都没有变化，所以不可能有测试能杀死它。 例如循环条件 i < n 被改成 i != n，而 i 每次只加 1、从不会跳过 n。 工具无法自动识别这种情况，只能靠人看。这也是变异得分几乎不可能、也不应该追求 100% 的原因之一。

代价，以及怎么用才划算

变异测试很贵：每个变异体都要跑一遍测试。示例的领域模型只有一百来行，三个工具分别跑了 39 到 86 轮测试； 因为单元测试是毫秒级的，整个过程只要几秒到十几秒。但如果让它去变异控制器、再用需要数据库的集成测试来检验，时间会涨上几个数量级。

建议为什么
只对领域模型和算法做变异，只用单元测试检验这里的逻辑最密、最值得保护，而单元测试又足够快（第 7 章的左上象限）
不放进每次提交都跑的那一步太慢会拖累快速反馈（第 4 章）。放在夜间任务里，或者只对本次改动的文件跑
不要把变异得分设成指标和覆盖率一样（第 1 章）：一旦成为目标，大家就会去写「为了杀变异体」的断言，比如断言异常的措辞
把它当成体检，不是考试隔一段时间跑一次，看幸存者名单里有没有让你意外的东西
★ 变异测试只衡量四大支柱里的一根

它衡量的是防止回归：代码错了，测试会不会红。它完全看不出第二根支柱 —— 抗重构。 一个把所有内部调用都用 Mock 验证了一遍的测试（第 5 章），变异得分会很高，因为你动任何一行它都会红； 可它恰恰是最糟糕的那种测试，重构时也一样会红。高变异得分不等于好测试。第 15 章会再遇到这一点。

属性测试：不举例子，描述规律

前面所有章节写的都是举例测试：我挑一个输入，写下期望的输出。它的盲区在于，例子是我想出来的 —— 我没想到的情况，既不会出现在代码里，也不会出现在测试里。

属性测试（property-based testing）

你不写具体的输入和输出，而是写一条对所有合法输入都应该成立的规律（属性），并描述「合法输入长什么样」。 框架自动生成成百上千组输入去试；一旦找到让规律不成立的输入，就把它收缩成最简单的反例交给你。

语言常用的库安装
Javajqwik（一个 JUnit 5 平台上的测试引擎）依赖 net.jqwik:jqwik，test 作用域
PythonHypothesis（和 pytest 直接配合）pip install hypothesis
TypeScriptfast-check（在任何测试框架里都能用）npm install -D fast-check

给「修改邮箱」写三条属性

先想规律，不想例子。关于 User.changeEmail，不管具体输入是什么，下面三件事都应该成立：

  1. 改完之后，用户是员工，当且仅当新邮箱属于公司域名。
  2. 公司员工数的变化量，等于「这个用户现在是不是员工」减去「他原来是不是员工」。
  3. 把同一个修改再做一遍，什么都不会发生：不产生新事件，员工数不变。
package crm.domain;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.List;
import net.jqwik.api.*;
import net.jqwik.api.constraints.IntRange;

class UserPropertyTests {
    static final String COMPANY_DOMAIN = "mycorp.com";

    static String emailAt(String local, boolean corporate) {
        return local + "@" + (corporate ? COMPANY_DOMAIN : "gmail.com");
    }

    static User aUser(String local, boolean isEmployee) {
        UserType type = isEmployee ? UserType.EMPLOYEE : UserType.CUSTOMER;
        return new User(1, emailAt(local, isEmployee), type, false);
    }

    // 生成器：描述「合法的输入长什么样」
    @Provide
    Arbitrary<String> localParts() {
        return Arbitraries.strings().withCharRange('a', 'z').ofMinLength(1).ofMaxLength(8);
    }

    @Property
    void a_user_is_an_employee_exactly_when_the_new_email_is_corporate(
            @ForAll("localParts") String local, @ForAll boolean wasEmployee,
            @ForAll @IntRange(min = 1, max = 1000) int employees,
            @ForAll("localParts") String newLocal, @ForAll boolean corporate) {
        User user = aUser(local, wasEmployee);
        Company company = new Company(COMPANY_DOMAIN, employees);

        user.changeEmail(emailAt(newLocal, corporate), company);

        assertThat(user.getType() == UserType.EMPLOYEE).isEqualTo(corporate);
    }

    @Property
    void the_number_of_employees_follows_the_user_type(
            @ForAll("localParts") String local, @ForAll boolean wasEmployee,
            @ForAll @IntRange(min = 1, max = 1000) int employees,
            @ForAll("localParts") String newLocal, @ForAll boolean corporate) {
        User user = aUser(local, wasEmployee);
        Company company = new Company(COMPANY_DOMAIN, employees);

        user.changeEmail(emailAt(newLocal, corporate), company);

        assertThat(company.getNumberOfEmployees() - employees)
            .isEqualTo((corporate ? 1 : 0) - (wasEmployee ? 1 : 0));
    }

    @Property
    void repeating_the_same_change_does_nothing(
            @ForAll("localParts") String local, @ForAll boolean wasEmployee,
            @ForAll @IntRange(min = 1, max = 1000) int employees,
            @ForAll("localParts") String newLocal, @ForAll boolean corporate) {
        User user = aUser(local, wasEmployee);
        Company company = new Company(COMPANY_DOMAIN, employees);
        String newEmail = emailAt(newLocal, corporate);
        user.changeEmail(newEmail, company);
        List<DomainEvent> events = user.getDomainEvents();
        int number = company.getNumberOfEmployees();

        user.changeEmail(newEmail, company);

        assertThat(user.getDomainEvents()).isEqualTo(events);
        assertThat(company.getNumberOfEmployees()).isEqualTo(number);
    }
}

from hypothesis import given, strategies as st

from crm.domain import Company, User, UserType

COMPANY_DOMAIN = "mycorp.com"


def email_at(local: str, corporate: bool) -> str:
    return f"{local}@{COMPANY_DOMAIN if corporate else 'gmail.com'}"


def a_user(local: str, is_employee: bool) -> User:
    user_type = UserType.EMPLOYEE if is_employee else UserType.CUSTOMER
    return User(1, email_at(local, is_employee), user_type, False)


# 生成器：描述「合法的输入长什么样」
local_parts = st.from_regex(r"[a-z]{1,8}", fullmatch=True)
users = st.builds(a_user, local_parts, st.booleans())
companies = st.builds(Company, st.just(COMPANY_DOMAIN), st.integers(1, 1000))


@given(users, companies, local_parts, st.booleans())
def test_user_is_an_employee_exactly_when_the_new_email_is_corporate(
        user, company, new_local, corporate):
    user.change_email(email_at(new_local, corporate), company)

    assert (user.type == UserType.EMPLOYEE) == corporate


@given(users, companies, local_parts, st.booleans())
def test_number_of_employees_follows_the_user_type(
        user, company, new_local, corporate):
    was_employee = user.type == UserType.EMPLOYEE
    before = company.number_of_employees

    user.change_email(email_at(new_local, corporate), company)

    assert company.number_of_employees - before == int(corporate) - int(was_employee)


@given(users, companies, local_parts, st.booleans())
def test_repeating_the_same_change_does_nothing(
        user, company, new_local, corporate):
    new_email = email_at(new_local, corporate)
    user.change_email(new_email, company)
    events = list(user.domain_events)
    number = company.number_of_employees

    user.change_email(new_email, company)

    assert user.domain_events == events
    assert company.number_of_employees == number

import fc from 'fast-check'
import { expect, test } from 'vitest'
import { Company, User, UserType } from '../../src/domain.js'

const COMPANY_DOMAIN = 'mycorp.com'

const emailAt = (local: string, corporate: boolean) =>
  `${local}@${corporate ? COMPANY_DOMAIN : 'gmail.com'}`

// 生成器：描述「合法的输入长什么样」
const localPart = fc.stringMatching(/^[a-z]{1,8}$/)
const scenario = fc.record({
  local: localPart,
  wasEmployee: fc.boolean(),
  employees: fc.integer({ min: 1, max: 1000 }),
  newLocal: localPart,
  corporate: fc.boolean(),
})
type Scenario = typeof scenario extends fc.Arbitrary<infer T> ? T : never

function arrange(s: Scenario) {
  const type = s.wasEmployee ? UserType.Employee : UserType.Customer
  return {
    user: new User(1, emailAt(s.local, s.wasEmployee), type, false),
    company: new Company(COMPANY_DOMAIN, s.employees),
    newEmail: emailAt(s.newLocal, s.corporate),
  }
}

test('a user is an employee exactly when the new email is corporate', () => {
  fc.assert(fc.property(scenario, (s) => {
    const { user, company, newEmail } = arrange(s)

    user.changeEmail(newEmail, company)

    expect(user.type === UserType.Employee).toBe(s.corporate)
  }))
})

test('the number of employees follows the user type', () => {
  fc.assert(fc.property(scenario, (s) => {
    const { user, company, newEmail } = arrange(s)

    user.changeEmail(newEmail, company)

    expect(company.numberOfEmployees - s.employees)
      .toBe(Number(s.corporate) - Number(s.wasEmployee))
  }))
})

test('repeating the same change does nothing', () => {
  fc.assert(fc.property(scenario, (s) => {
    const { user, company, newEmail } = arrange(s)
    user.changeEmail(newEmail, company)
    const events = [...user.domainEvents]
    const employees = company.numberOfEmployees

    user.changeEmail(newEmail, company)

    expect(user.domainEvents).toEqual(events)
    expect(company.numberOfEmployees).toBe(employees)
  }))
})

每条属性默认会被检查一百到一千次（jqwik 默认 1000 次，Hypothesis 和 fast-check 默认 100 次），三条在示例的领域模型上全部通过，耗时不到一秒。

★ 关键技巧：让输入「自带答案」

第 11 章警告过「把领域知识泄漏进测试」：如果测试里写 expected = email.split("@")[1] == domain，那只是把生产代码抄了一遍，两边会一起错。 属性测试尤其容易掉进这个坑，因为你手上没有具体的期望值。

上面的写法绕开了它：不是先生成一个邮箱、再去算它是不是公司邮箱，而是先生成一个布尔值 corporate， 再用它拼出一个邮箱。这样期望的答案在构造输入时就已经知道了，测试里不需要任何判断逻辑。

它真的能抓到 Bug 吗

拿第 0 章练习里的那个错误来验收：把生产代码里 delta 的正负号写反。实测 Hypothesis 立刻让第二条属性失败，并给出了一个收缩到最简的反例：

E       Failing test case: test_number_of_employees_follows_the_user_type(

E               'a',  # or any other generated value

读法：一个客户（False）把邮箱改成公司邮箱（corporate=True），员工数本该加 1，结果减了 1。 注释 or any other generated value 是在告诉你：邮箱前缀和初始员工数取什么都一样会失败 —— 问题只和「客户变员工」有关。

拿到反例之后

反例不一定意味着生产代码有 Bug。先回答一个问题：这个输入是合法的吗？

结论该做什么
合法，代码处理错了 修代码。并且把这个反例抄成一个普通的举例测试永久留下 —— 它有名字、好读，而且不依赖随机数还能不能再撞到它
不合法，系统本就不该收到它 收窄生成器，让它只产生合法输入；同时确认「不合法的输入在哪里被挡住」。这里的答案是：目前没有任何地方在校验邮箱格式 —— 属性测试顺带暴露了一个缺失的校验

这也是属性测试的一个副作用：它逼你把「合法输入」的定义明明白白写出来（就是那个生成器）。很多时候，写不出生成器，说明需求本身就没想清楚。

常见的属性长什么样

「我想不出属性」是最常见的卡点。下面是几种现成的套路：

套路说的是例子
不变式不管怎么操作，某个条件始终成立员工数永远不为负；用户类型永远和邮箱域名一致
往返做一次再反着做一次，回到原样序列化再反序列化；把邮箱改掉再改回来，员工数复原
幂等做两次和做一次效果一样上面的第三条属性；重复投递同一条消息
对照和一个简单但明显正确的实现比结果优化过的排序 vs. 标准库的排序；新实现 vs. 被替换的旧实现（第 12 章）
输入变，输出跟着变不知道正确答案，但知道输入变化时答案该怎么变给购物车多加一件商品，总价不会变少
不崩溃对任何合法输入都不抛出意料之外的异常解析器对任意字符串要么成功、要么给出明确的格式错误
⚠ 单独一条属性往往很弱

「往返」属性就是个例子：把 delta 的正负号写反，客户变员工时减 1、员工变客户时加 1，改过去再改回来，员工数照样复原。这条属性完全发现不了那个 Bug。 属性要成组地写，互相补位；而且不要用它取代举例测试 —— 那几个具体的例子是最好读的文档（第 3 章）。

几个要留意的地方

问题怎么办
输入是随机的，失败了下次还能重现吗能。失败时框架会打印种子（见上面 jqwik 和 fast-check 的输出），用它可以原样重跑；Hypothesis 和 jqwik 还会把失败的输入存到本地，下次优先重试。但最稳妥的仍然是把反例抄成举例测试
它算不算「不稳定测试」（第 13 章）如果它时红时绿，说明存在让属性不成立的输入 —— 那是真问题，不是测试不稳定。修掉它，而不是减少运行次数
生成器写得太窄只生成了「我想到的」那些输入，等于白写。看一眼框架的统计信息，确认生成的值够分散
生成器写得太宽大量输入不合法，反例全是噪音。宽一点起步是好的（像上面那样能发现缺失的校验），但最终要收敛到「合法输入」
Java：属性测试没有被执行实测踩到的坑：类名叫 UserProperties 时，Maven 默认只运行名字以 Test / Tests 等结尾的类，于是整个类被悄悄跳过，构建照样成功。改名为 UserPropertyTests，或者在 Surefire 里配置包含规则

属性测试最适合的对象，和基于输出的测试一样（第 6 章）：没有协作者的纯逻辑 —— 领域模型、计算、解析、转换。 对一个要读写数据库的控制器跑一千次随机输入，既慢，也很难说清规律是什么。

两种工具放在一起看

它们可以互相检验：给示例加上那三条属性之后再跑变异测试，可以看看有没有哪个原先幸存的变异体被属性杀死了； 反过来，一条新写的属性到底有没有用，把生产代码改错一处、看它红不红，就知道了（上面验收 delta 时做的正是这件事）。

小结

  • 覆盖率回答「哪些代码被执行过」。它回答不了「代码错了测试会不会发现」和「有没有没想到的输入」。
  • 变异测试自动把生产代码改错一处，看有没有测试变红。变红 = 被杀死；全绿 = 幸存，说明这里没被验证。
  • 实测：把断言全删掉，覆盖率保持 97% 不变，杀死的变异体却从 71 个掉到 33 个（共 86 个）。
  • 报告的价值在幸存者名单，不在百分比。逐个判断：是真漏洞就补测试；是琐碎代码、等价变异体、或不值得钉住的行为（比如异常的措辞）就放过。
  • 不同工具的变异得分不能互相比；也不要把它设成指标 —— 理由和覆盖率一样。
  • 变异测试只衡量防止回归。和实现绑死的脆弱测试得分反而高，它看不出来。
  • 属性测试写的是对所有合法输入都成立的规律，由框架生成大量输入去找反例，并把反例收缩到最简。
  • 写属性时不要把实现抄一遍。让输入「自带答案」：先定答案，再据此构造输入。
  • 拿到反例先问「这个输入合法吗」。合法就修代码，并把反例抄成举例测试留下；不合法就收窄生成器，并检查不合法的输入在哪里被挡住。
  • 两者都最适合用在领域模型上：逻辑密集，测试又足够快。属性测试随单元测试每次都跑；变异测试定期跑。

自测

团队决定「变异得分必须达到 90% 才能合并」。这和第 1 章批评的覆盖率指标有什么相同和不同？

相同：一旦成为目标，大家会去优化数字本身 —— 给异常措辞、日志文本、琐碎的取值方法补断言，换来更多假警报。不同：变异得分比覆盖率更难「刷」，因为没有断言的测试杀不死变异体。但它仍然只衡量四根支柱里的一根，而且等价变异体让 100% 在原理上就达不到。把它当体检，别当门槛。

一个变异体把 logger.debug("loaded user " + id) 整行删掉了，测试全绿。要补测试吗？

不要。这是给开发者看的诊断日志（第 8 章），不是可观察行为。为它写断言会把测试和实现细节绑在一起。更好的做法是在变异测试的配置里把日志调用排除掉。

同事写的属性是：assert is_email_corporate(email) == (email.split("@")[1] == domain)。问题在哪？

它把生产代码的算法原样抄进了测试（第 11 章：泄漏领域知识）。两边用的是同一个有缺陷的切分方式，所以对 @@mycorp.com 这样的输入会「一起错」，属性照样成立。应该让输入自带答案：先决定「这是不是公司邮箱」，再据此拼出地址。

属性测试找到一个反例并且你已经修好了代码。为什么还建议把这个反例另外写成一个普通的举例测试？

因为属性测试下次不一定还会生成到这个输入；举例测试则永远在那儿，有一个说明业务含义的名字，失败时一眼就知道是哪种情况回归了。
