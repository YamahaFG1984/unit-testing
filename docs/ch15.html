第 15 章 · 补充

评审 AI 生成的测试

现在让 AI 助手「给这个类写测试」，几秒钟就能得到几十个全绿的测试。写测试的成本几乎归零了， 可第 1 章说的那笔账没变：每个测试都要有人读、有人维护，坏测试的净价值是负的。 于是瓶颈从「写」挪到了「判断」。这一章把前面的标尺整理成一份评审清单。

本章目标

  • 理解为什么「照着代码生成的测试」天然容易出某几类毛病
  • 认得出四种最常见的坏测试，并能说出它伤的是哪根支柱
  • 有一份可以照着走的评审清单，半分钟判断一个测试：留、改、删
  • 知道怎么提要求，能让 AI 一开始就写得更好
  • 知道哪些测试工作适合交给 AI，哪些判断必须自己做
ⓘ 关于这一章

本章不是原书内容，是把原书的标尺用到一个原书出版时还不存在的场景上。几点说明：

  • 文中的「坏测试」是为了演示这几种模式而写的典型样本，不是某个工具某一次的原始输出。它们都在配套示例上实际运行过，文中的数字是实测结果。
  • AI 工具变化很快，「它现在容易犯什么错」会过时。本章想留下的是评审的标准 —— 这些标准对人写的测试同样适用，只是现在更用得上。
  • 这里的建议是作者的经验之谈，没有对照实验的数据支撑。

成本挪到了哪里

为什么照着代码生成的测试容易出问题

最常见的用法是：选中一段代码，说「给它写测试」。这时 AI 手上唯一的信息来源就是这段代码。 它不知道需求是什么，只能从实现反推「这段代码应该做什么」—— 反推出来的结论当然是：它应该做它现在做的事。

这种测试有个正式的名字，第 12 章已经见过：特征测试 —— 记录代码「现在做什么」，而不是「应该做什么」。 在给遗留代码搭脚手架时它正合适；但把它当成新功能的正式测试留下来，就会带来下面这些毛病。

四种最常见的毛病

下面四个测试针对的都是配套示例里的 User.changeEmail。它们全都通过，乍一看也都像模像样。

① 把实现抄进测试

@Test
void changeEmail_updates_type_and_employee_count() {
    Company company = new Company("mycorp.com", 5);
    User user = new User(1, "user@gmail.com", UserType.CUSTOMER, false);
    String newEmail = "new@mycorp.com";
    UserType expectedType = newEmail.split("@")[1].equals(company.getDomainName())
        ? UserType.EMPLOYEE
        : UserType.CUSTOMER;
    int delta = expectedType == UserType.EMPLOYEE ? 1 : -1;
    int expectedCount = company.getNumberOfEmployees() + delta;

    user.changeEmail(newEmail, company);

    assertThat(user.getType()).isEqualTo(expectedType);
    assertThat(company.getNumberOfEmployees()).isEqualTo(expectedCount);
}

def test_change_email_updates_type_and_employee_count():
    company = Company("mycorp.com", 5)
    user = User(1, "user@gmail.com", UserType.CUSTOMER, False)
    new_email = "new@mycorp.com"
    expected_type = (UserType.EMPLOYEE
                     if new_email.split("@")[1] == company.domain_name
                     else UserType.CUSTOMER)
    delta = 1 if expected_type == UserType.EMPLOYEE else -1
    expected_count = company.number_of_employees + delta

    user.change_email(new_email, company)

    assert user.type == expected_type
    assert company.number_of_employees == expected_count

test('changeEmail updates type and employee count', () => {
  const company = new Company('mycorp.com', 5)
  const user = new User(1, 'user@gmail.com', UserType.Customer, false)
  const newEmail = 'new@mycorp.com'
  const expectedType = newEmail.split('@')[1] === company.domainName
    ? UserType.Employee
    : UserType.Customer
  const delta = expectedType === UserType.Employee ? 1 : -1
  const expectedCount = company.numberOfEmployees + delta

  user.changeEmail(newEmail, company)

  expect(user.type).toBe(expectedType)
  expect(company.numberOfEmployees).toBe(expectedCount)
})

怎么认：准备阶段里出现了条件判断、字符串处理或算术，而且长得和生产代码很像。期望值是算出来的，不是写出来的。
问题：这是第 11 章的「把领域知识泄漏进测试」。测试和代码用的是同一套算法，算法有错就一起错 —— 第 14 章发现的那个 split("@")[1] 的缺陷，在这个测试里被原样复制了一份。它读起来也费劲：读者得在脑子里把算法跑一遍才知道期望的是什么。
改法：把期望值直接写成字面量：类型是 EMPLOYEE，员工数是 6。

② 断言什么都没验证

@Test
void changeEmail_works() {
    Company company = new Company("mycorp.com", 5);
    User user = new User(1, "user@gmail.com", UserType.CUSTOMER, false);

    user.changeEmail("new@mycorp.com", company);

    assertThat(user).isNotNull();
    assertThat(user.getEmail()).isNotNull();
    assertThat(user.getDomainEvents()).isNotEmpty();
}

def test_change_email_works():
    company = Company("mycorp.com", 5)
    user = User(1, "user@gmail.com", UserType.CUSTOMER, False)

    user.change_email("new@mycorp.com", company)

    assert user is not None
    assert user.email is not None
    assert len(user.domain_events) > 0

test('changeEmail works', () => {
  const company = new Company('mycorp.com', 5)
  const user = new User(1, 'user@gmail.com', UserType.Customer, false)

  user.changeEmail('new@mycorp.com', company)

  expect(user).toBeDefined()
  expect(user.email).toBeTruthy()
  expect(user.domainEvents.length).toBeGreaterThan(0)
})

怎么认：断言是「不为空」「不为 null」「长度大于 0」「没有抛异常」这一类；测试名里是 works、success、test1。
问题：第 1 章的「没有断言的测试」的变体。代码被执行了，覆盖率有了，但邮箱改成了什么、类型对不对、员工数变没变，一样都没验证。
改法：断言具体的结果。如果说不出该断言什么，说明还没想清楚这个测试要验证哪个行为。

③ 测试琐碎的代码

@Test
void user_constructor_sets_fields() {
    User user = new User(1, "user@gmail.com", UserType.CUSTOMER, false);

    assertThat(user.getUserId()).isEqualTo(1);
    assertThat(user.getEmail()).isEqualTo("user@gmail.com");
    assertThat(user.getType()).isEqualTo(UserType.CUSTOMER);
    assertThat(user.isEmailConfirmed()).isFalse();
}

def test_user_constructor_sets_fields():
    user = User(1, "user@gmail.com", UserType.CUSTOMER, False)

    assert user.user_id == 1
    assert user.email == "user@gmail.com"
    assert user.type == UserType.CUSTOMER
    assert user.is_email_confirmed is False

test('User constructor sets fields', () => {
  const user = new User(1, 'user@gmail.com', UserType.Customer, false)

  expect(user.userId).toBe(1)
  expect(user.email).toBe('user@gmail.com')
  expect(user.type).toBe(UserType.Customer)
  expect(user.isEmailConfirmed).toBe(false)
})

怎么认：被测的是构造函数、取值方法、一行的转发。测试的数量和类里方法的数量差不多 —— 「每个方法一个测试」。
问题：第 7 章四象限的右下角：琐碎代码，不值得测。它几乎不可能出错，这个测试也就几乎没有防止回归的价值，却要你一直维护。 AI 生成的测试集里，这一类往往占了大头，把真正重要的那几个淹没在里面。
改法：删掉。这些字段会被真正验证行为的测试顺带用到。

④ 把领域对象也 Mock 掉，然后验证内部调用

@Test
void changeEmail_calls_company() {
    Company company = mock(Company.class);
    when(company.isEmailCorporate("new@mycorp.com")).thenReturn(true);
    User user = new User(1, "user@gmail.com", UserType.CUSTOMER, false);

    user.changeEmail("new@mycorp.com", company);

    verify(company).isEmailCorporate("new@mycorp.com");
    verify(company).changeNumberOfEmployees(1);
}

def test_change_email_calls_company():
    company = Mock(spec=Company)
    company.is_email_corporate.return_value = True
    user = User(1, "user@gmail.com", UserType.CUSTOMER, False)

    user.change_email("new@mycorp.com", company)

    company.is_email_corporate.assert_called_once_with("new@mycorp.com")
    company.change_number_of_employees.assert_called_once_with(1)

test('changeEmail calls company', () => {
  const company = new Company('mycorp.com', 5)
  const isEmailCorporate = vi.spyOn(company, 'isEmailCorporate').mockReturnValue(true)
  const changeNumberOfEmployees = vi.spyOn(company, 'changeNumberOfEmployees')
  const user = new User(1, 'user@gmail.com', UserType.Customer, false)

  user.changeEmail('new@mycorp.com', company)

  expect(isEmailCorporate).toHaveBeenCalledExactlyOnceWith('new@mycorp.com')
  expect(changeNumberOfEmployees).toHaveBeenCalledExactlyOnceWith(1)
})

怎么认：被 Mock 的是你自己的类（领域对象、仓储），断言是「某某方法被调用了一次」。
问题：第 5 章的核心：User 和 Company 之间怎么配合是系统内部的通信，是实现细节。 这个测试钉住的不是「员工数变成了多少」，而是「User 通过哪两个方法去找 Company」。它伤的是第二根支柱，抗重构。
改法：用真的 Company，断言最终状态。Mock 只留给不受管的进程外依赖（第 8 章）。

其他常见的

毛病怎么认对应章节
把 Bug 钉成了期望期望值看着别扭，像是「代码就是这么算的」而不是「业务上应该这样」本章图 15-2
Mock 掉数据库或仓储来测控制器测试里没有真实的存储，全是 when(repo.get…).thenReturn(…)第 8 章：受管依赖用真的
测私有方法、读私有字段用了反射，或者访问下划线开头的成员第 11 章
为了测试改生产代码生产代码里多出了只有测试才用的开关、构造函数或公开方法第 11 章：代码污染
一个测试验证好几件事，或者有分支和循环测试里出现 if / for；「执行」和「断言」交替出现好几轮第 3 章：AAA
名字照抄方法名testChangeEmail、changeEmail_works —— 读不出是哪条业务规则第 3 章：命名
大量近似重复十个测试只差一个参数，其中一半走的是同一条路径第 3 章：参数化；第 4 章：可维护性
异步测试没有真的等结果少了 await，或断言写在回调里第 13 章
调用了不存在的方法或用错了框架的写法编译不过或运行就报错 —— 这是最不需要担心的一类，因为它自己会暴露—

实测：这四个测试到底有多少保护力

在配套示例的 Python 版上做两个实验，把上面四个测试和示例自带的 10 个手写单元测试放在一起比。

实验一：代码改错了，它们会红吗

上面四个测试示例自带的 10 个
运行结果4 个全部通过10 个全部通过
领域模型的行覆盖率89%97%
杀死的变异体（共 86 个，第 14 章）35 个71 个
其中只留 ②、③ 两个测试时覆盖率仍是 89%，只杀死 23 个—

覆盖率只差 8 个百分点，看起来「差不多」；被验证到的行为却差了一倍。 最后一行尤其说明问题：把 ① 和 ④ 拿掉，覆盖率一点没降，杀死的变异体却又少了三分之一 —— ② 和 ③ 贡献的几乎只有覆盖率。

实验二：代码没错，它们会红吗

做一次不改变任何行为的重构：User.changeEmail 里不再调用 company.is_email_corporate(...)， 而是直接比较邮箱的结尾和公司域名。对所有合法的邮箱，结果完全一样。然后把 14 个测试全跑一遍： 

E               AttributeError: Mock object has no attribute 'domain_name'
FAILED tests/unit/test_ai.py::test_change_email_calls_company - AttributeErro...
1 failed, 13 passed

红的正是 ④ —— 一个假警报。行为没变，它却要求你去改测试。另外 13 个测试（包括手写的 10 个）都不受影响。

★ 两个实验对应两根支柱，而工具只能帮你做第一个

实验一可以自动化（变异测试），它能把 ②、③ 这类空洞的测试揪出来。 实验二不行：④ 在实验一里表现并不差 —— 实测它一个测试就杀死了 19 个变异体，因为它盯着每一次调用，相应的代码一改它就红。 「和实现绑得太紧」这种毛病，目前没有工具能替你判断，只能靠评审的人对照第 5 章去看：这个断言钉住的，是可观察行为，还是实现细节？

一份评审清单

面对几十个生成出来的测试，不需要逐行细读。按下面的顺序过，大多数测试在前两步就能决定去留：

注意顺序是有意安排的：最省力、淘汰最多的检查放在最前面。① 只要看一眼被测的是什么；② 只要看断言是 verify(...) 还是 assertEquals(...)。 需要动手的 ⑤ 放在后面，只对通过了前四步的测试做。

改完是什么样

把 ① 的期望值换成字面量，把 ② 的断言补具体，把 ④ 换回真的 Company、改成断言状态 —— 三个测试会收敛成同一个。 它就是配套示例里手写的那个：

四个测试变成了一个，行数更少，保护力更强。评审 AI 生成的测试，结果通常是测试变少，而不是变多。

怎么提要求，让它一开始就写得好些

图 15-2 已经指出了根源：AI 只看得到代码。所以最有效的办法不是事后挑错，而是给它第二个信息来源。

一个可以直接改着用的要求

为 User.changeEmail 写单元测试。

要验证的行为（按业务规则，不要从实现反推）：
1. 客户把邮箱改成公司域名的邮箱 → 变成员工，公司员工数 +1
2. 员工把邮箱改成非公司域名的邮箱 → 变成客户，公司员工数 -1
3. 新旧邮箱类型相同 → 用户类型和员工数都不变
4. 新邮箱和旧邮箱相同 → 什么都不发生，不产生事件
5. 邮箱已确认的用户 → 不允许修改

约定：
- 这是领域模型，没有进程外依赖：不要使用任何 Mock，Company 用真的对象
- 断言最终状态和领域事件；期望值写字面量，不要在测试里计算
- 每个测试只验证上面的一条；名字用一句话描述这条规则
- 结构：准备 / 执行 / 断言，三段之间空一行
- 不要测构造函数和取值方法

先只把你打算写的测试名列出来给我确认，不要写代码。

这段话里起作用的是这几处：

写了什么防的是哪种毛病
行为清单，带期望结果测试有了独立于实现的依据；顺带防住「每个方法一个测试」和琐碎测试
说明这是哪一类代码、哪些依赖可以换防 ④。AI 的默认倾向是见到协作者就 Mock；你得告诉它第 7、8 章的结论
「期望值写字面量」防 ①
「先列测试名」在生成几百行代码之前，用半分钟评审测试清单 —— 这是成本最低的评审点
💡 把约定写进仓库，别每次都重说

大多数 AI 编程工具都会读仓库里的某个说明文件。把团队的测试约定写在那里： 「领域模型不用 Mock」「数据库用真的，只替换消息总线」「测试名是一句业务上的话」「集成测试只走最长的成功路径」…… 这些正是本教程各章的结论。写一次，之后生成的每个测试都会照着来。

⚠ 「让测试通过」是一个危险的指令

让 AI 去修一个失败的测试时，它有两条路：修代码，或者改测试。后者往往更容易 —— 放宽断言、改掉期望值、甚至把测试跳过。 测试变绿了，保护也没了。所以：测试文件的任何改动都要单独看一眼，特别留意被删掉的断言、被改动的期望值和新出现的「跳过」标记。 一个之前是红的、现在变绿的测试，要确认绿的原因是代码对了。

哪些交给它，哪些自己来

适合交给 AI为什么
把你列好的行为清单写成测试代码判断已经做完，剩下的是打字
把一组近似重复的测试合并成参数化测试（第 3 章）机械的改写，容易核对
写造数据的辅助代码：工厂方法、构建器、断言辅助（第 3、10 章）枯燥、模式固定，出错了测试自己会暴露
给遗留代码写特征测试（第 12 章）这里要的就是「照着现有行为写」—— 它的弱点在这个场景下正好是需要的
帮你想边界情况：「这条规则还有哪些情况我没列到？」它提出候选，你来决定哪些成立。和属性测试（第 14 章）的作用类似
解释一个失败的测试、定位原因结论可以马上验证
必须自己做为什么
决定测什么：哪些行为重要，哪些代码不值得测这取决于业务，代码里读不出来
确认每个期望值符合业务规则AI 给出的期望值来自代码或来自猜测，两者都不是需求
判断一个断言钉住的是行为还是实现细节目前没有工具能查，而它决定了测试会不会拖累重构
决定测试的边界：单元还是集成，哪些依赖用真的这是架构上的决定（第 7、8 章）
决定删掉哪些测试生成是免费的，所以「多留几个也无妨」的诱惑很大；可维护成本是真的

小结

  • AI 把写测试的成本降到接近零，但运行、排查、修改、阅读的成本没变，还因为数量增加而放大。瓶颈从「写」变成了「判断哪些值得留」。
  • 「照着代码生成测试」得到的是代码的镜像，不是独立的核对。它天然倾向于记录「代码现在做什么」。
  • 四种最常见的毛病：照抄实现、断言空洞、测琐碎代码、Mock 内部对象并验证调用。它们都能通过，都能贡献覆盖率。
  • 实测：四个这样的测试覆盖率 89%、杀死 35 个变异体；手写的十个覆盖率 97%、杀死 71 个。一次不改变行为的重构让其中一个测试红了。
  • 「代码错了会不会红」可以用变异测试自动检查；「代码没错会不会红」只能靠人对照第 5 章来判断。
  • 评审清单按淘汰效率排序：值得测吗 → 验证的是行为吗 → 期望值是字面量吗 → 只替换了不受管依赖吗 → 改错代码会红吗 → 读得懂吗。
  • 评审的结果通常是测试变少。
  • 想让它写得好，就给它代码之外的信息：行为清单、这是哪类代码、哪些依赖可以换。先评审测试清单，再生成代码。
  • 决定测什么、核对期望值、判断是行为还是实现细节、决定删什么 —— 这些留给自己。

自测

AI 为一个类生成了 40 个测试，全部通过，覆盖率 95%。在读任何一个测试之前，你能从这些数字里得出什么结论？

几乎什么都得不出。全部通过是必然的 —— 测试是照着现有代码写的。覆盖率只说明代码被执行了。要知道它们有没有在验证，需要看断言（或者跑变异测试）；要知道它们会不会拖累重构，需要看它们钉住的是什么。

一个生成的测试断言 calculateDiscount(100) 返回 7。你去看需求，规则是「满 100 减 10」。测试是绿的。发生了什么？

代码里有 Bug，而测试把 Bug 的结果当成期望值记了下来（图 15-2 右边的情况）。这时不能只改测试或只改代码：先确认需求，把期望值改成 10，看测试变红，再修代码让它变绿。这也是为什么期望值必须由人对照业务规则核对。

为什么说「把所有协作者都 Mock 掉」的测试在变异测试里得分可能很高，却仍然是坏测试？

因为它验证了每一次内部调用，生产代码里任何一处改动 —— 包括改错 —— 都会让它变红，所以变异体被杀得很干净。但出于同样的原因，任何不改变行为的重构也会让它变红。变异测试只衡量防止回归，看不出抗重构这根支柱。

同事说：「反正生成测试不花钱，多多益善，万一哪个能抓到 Bug 呢。」你怎么回应？

生成不花钱，拥有要花钱。每多一个测试，测试集就慢一点，重构时要改的地方就多一处，假警报就多一种可能。第 1 章的结论没有变：测试是负债，目标是用最少的测试换最大的保护，而不是测试的数量。

动手练习

  1. 把本章四个「坏测试」放进配套示例跑一遍，确认它们都通过。然后做一次实验二那样的重构，看哪个会红。
  2. 让你常用的 AI 工具「给 UserController 写单元测试」，不加任何别的说明。按图 15-4 的清单评审结果：有几个能留下？它 Mock 了什么？
  3. 换成本章「可以直接改着用的要求」那种写法再试一次（先列行为，说明约定，先要测试名）。对比两次的结果。
  4. 把你团队的测试约定写成十行以内的说明，放进仓库里 AI 工具会读的那个文件。
  5. 回头看你项目里最近合并的一批测试（不管是谁写的），随机抽五个按清单过一遍。
