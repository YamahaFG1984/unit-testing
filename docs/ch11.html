单元测试反模式

反模式是这样一种东西：它是某个常见问题的常见解法，表面上看很合理，往后走却会带来麻烦。 这一章收集了六个最常见的。它们大多可以从第二部分的基本原理直接推出来，但值得一个个挑明 —— 你很可能已经踩过其中几个了。

本章目标

  • 知道为什么不该测私有方法，以及「私有方法太复杂」时真正该做什么
  • 不为了测试而暴露私有状态
  • 不把领域知识（算法实现）泄漏到测试里
  • 识别代码污染，并用更干净的方式替代
  • 理解为什么「Mock 具体类」是单一职责被破坏的信号
  • 在测试里正确地处理时间

反模式一：测试私有方法

「怎么测私有方法？」是最常被问到的问题之一。简短的回答是：根本不该测。不过里面有不少细节。

私有方法与测试脆弱性

为了测试而把本该私有的方法公开，违反了第 5 章的基本原则：只测可观察行为。 这会让测试和实现细节耦合，最终损害抵抗重构 —— 四根支柱里最重要的那根。 不要直接测私有方法，而是通过它所服务的可观察行为间接地测。

私有方法与覆盖率不足

有时私有方法太复杂，通过可观察行为去测达不到足够的覆盖。假设可观察行为本身已经有合理的测试覆盖，那么可能有两种情况：

  • 这是死代码。没被覆盖的代码如果根本没被用到，多半是重构后留下的残余。删掉它。
  • 缺少一个抽象。私有方法太复杂、很难通过类的公开 API 去测，说明这里藏着一个应该被抽成独立类的抽象。

什么时候可以测私有方法

回顾第 5 章那张表：

可观察行为实现细节
公开好坏
私有不适用（？）好

测私有方法本身并不坏，它之所以坏，是因为私有方法通常就是实现细节。而在极少数情况下，一个方法可以既是私有的，又属于可观察行为 （所以左下角那格其实不完全是「不适用」）。

例子：一个管理信贷查询的系统。新的查询每天批量直接导入数据库，管理员随后逐个审批。Inquiry 类的构造函数是私有的 —— 因为对象由 ORM 从数据库还原（ORM 通过反射调用私有构造函数），而系统本身不负责创建查询。 

public class Inquiry {
    private boolean isApproved;
    private LocalDateTime timeApproved;

    private Inquiry(boolean isApproved, LocalDateTime timeApproved) {   // 私有构造函数
        if (isApproved && timeApproved == null) {
            throw new IllegalArgumentException();
        }
        this.isApproved = isApproved;
        this.timeApproved = timeApproved;
    }

    public void approve(LocalDateTime now) {
        if (isApproved) return;

        isApproved = true;
        timeApproved = now;
    }
}

class Inquiry:
    # Python 没有真正的私有构造函数；常见做法是约定「只由 ORM / 工厂创建」，
    # 或者提供一个带下划线的类方法供 ORM 使用。
    def __init__(self, is_approved: bool, time_approved: datetime | None) -> None:
        if is_approved and time_approved is None:
            raise ValueError()
        self.is_approved = is_approved
        self.time_approved = time_approved

    def approve(self, now: datetime) -> None:
        if self.is_approved:
            return

        self.is_approved = True
        self.time_approved = now

export class Inquiry {
  private constructor(                                  // 私有构造函数
    public isApproved: boolean,
    public timeApproved: Date | null,
  ) {
    if (isApproved && timeApproved === null) {
      throw new Error()
    }
  }

  approve(now: Date): void {
    if (this.isApproved) return

    this.isApproved = true
    this.timeApproved = now
  }
}

审批逻辑显然很重要，应该测；可你连一个 Inquiry 对象都创建不出来。 这个构造函数就是「既私有又属于可观察行为」的例子：它履行的是与 ORM 之间的契约，私有并不让这个契约变得不重要 —— 没有它，ORM 就没法从数据库还原对象。

所以在这个特定情况下，把构造函数改成 public 不会导致测试脆弱。只要确保构造函数里有维持封装所需的全部前置条件 （这里是：已审批的查询必须有审批时间）。如果你想让公开 API 尽量小，也可以在测试里用反射创建对象 —— 看着像黑科技，但你只是在做 ORM 做的事。

反模式二：暴露私有状态

public class Customer {
    private CustomerStatus status = CustomerStatus.REGULAR;     // 私有状态

    public void promote() {
        status = CustomerStatus.PREFERRED;
    }

    public BigDecimal getDiscount() {
        return status == CustomerStatus.PREFERRED
            ? new BigDecimal("0.05") : BigDecimal.ZERO;
    }
}

public enum CustomerStatus { REGULAR, PREFERRED }

class CustomerStatus(Enum):
    REGULAR = 1
    PREFERRED = 2


class Customer:
    def __init__(self) -> None:
        self._status = CustomerStatus.REGULAR                   # 私有状态

    def promote(self) -> None:
        self._status = CustomerStatus.PREFERRED

    def get_discount(self) -> Decimal:
        return Decimal("0.05") if self._status == CustomerStatus.PREFERRED else Decimal("0")

export enum CustomerStatus { Regular, Preferred }

export class Customer {
  private status = CustomerStatus.Regular                       // 私有状态

  promote(): void {
    this.status = CustomerStatus.Preferred
  }

  getDiscount(): number {
    return this.status === CustomerStatus.Preferred ? 0.05 : 0
  }
}

怎么测 promote()？它的副作用是改了 status 字段，可字段是私有的。 很诱人的做法是把它改成 public —— 毕竟，「状态变了」不正是调用 promote() 的最终目的吗？

★ 测试不应该有任何特权

测试与被测系统交互的方式，应该和生产代码完全一样。 status 对生产代码是隐藏的，所以它不属于可观察行为；暴露它就是让测试和实现细节耦合。

那怎么办？看生产代码是怎么用这个类的。生产代码不关心客户的状态（否则这个字段就该是公开的）， 它唯一关心的是客户升级后能拿到的折扣。所以测试该验证的是： 

@Test

    var sut = new Customer();

    assertThat(sut.getDiscount()).isEqualByComparingTo("0");
}

@Test
void a_promoted_customer_gets_a_5_percent_discount() {
    var sut = new Customer();

    sut.promote();

    assertThat(sut.getDiscount()).isEqualByComparingTo("0.05");
}

以后如果生产代码开始使用客户状态字段了，测试也就可以用它了 —— 因为那时它正式成了可观察行为的一部分。 为了可测试性而扩大公开 API 的范围，是坏做法。

反模式四：代码污染

代码污染（code pollution）

在生产代码里添加只有测试才需要的代码。常见形式是各种开关。

public class Logger {
    private final boolean isTestEnvironment;

    public Logger(boolean isTestEnvironment) {       // 开关
        this.isTestEnvironment = isTestEnvironment;
    }

    public void log(String text) {
        if (isTestEnvironment) return;               // 开关

        /* 记录日志 */
    }
}

@Test
void some_test() {
    var logger = new Logger(true);                   // 传 true 表示测试环境
    var sut = new Controller();

    sut.someMethod(logger);

    /* 断言 */
}

class Logger:
    def __init__(self, is_test_environment: bool) -> None:   # 开关
        self._is_test_environment = is_test_environment

    def log(self, text: str) -> None:
        if self._is_test_environment:                        # 开关
            return

        ...  # 记录日志


def test_something():
    logger = Logger(True)                                    # 传 True 表示测试环境
    sut = Controller()

    sut.some_method(logger)

    ...  # 断言

export class Logger {
  constructor(private readonly isTestEnvironment: boolean) {}   // 开关

  log(text: string): void {
    if (this.isTestEnvironment) return                          // 开关

    /* 记录日志 */
  }
}

test('some test', () => {

  const sut = new Controller()

代码污染的问题在于它把测试代码和生产代码搅在一起，抬高了后者的维护成本。出路是：让测试代码留在生产代码库之外。 

public interface ILogger {
    void log(String text);
}

public class Logger implements ILogger {             // 属于生产代码
    public void log(String text) {
        /* 记录日志 */
    }
}

public class FakeLogger implements ILogger {         // 属于测试代码
    public void log(String text) {
        /* 什么都不做 */
    }
}

public class Controller {
    public void someMethod(ILogger logger) {
        logger.log("SomeMethod is called");
    }
}

class LoggerProtocol(Protocol):
    def log(self, text: str) -> None: ...


class Logger:                                        # 属于生产代码
    def log(self, text: str) -> None:
        ...  # 记录日志


class FakeLogger:                                    # 属于测试代码
    def log(self, text: str) -> None:
        pass  # 什么都不做


class Controller:
    def some_method(self, logger: LoggerProtocol) -> None:
        logger.log("SomeMethod is called")

ⓘ 那个接口本身不也是一种污染吗？

严格说是的：ILogger 待在生产代码库里，却只是为了测试才需要。但这种污染危害小得多、也好处理得多：

  • 你不可能意外执行到一条「本来不打算在生产环境走」的代码路径。
  • 接口里没有代码，只是契约，所以接口里不可能有 Bug。和布尔开关不同，它不增加潜在 Bug 的面积。

反模式六：把时间当作环境上下文

很多功能需要当前日期和时间。测试依赖时间的功能容易出现误报：执行阶段取到的时间和断言阶段取到的可能不一样。 有三种稳定这个依赖的办法 —— 一种是反模式，另外两种里有一种更好。

💡 一个好的折中

你不一定总能把时间作为普通值注入，因为依赖注入框架和值对象配合得不太好。 折中做法是：在业务操作的起点把时间作为服务注入，然后在这次操作的剩余部分把它当作值往下传。 上面的例子就是这样：控制器接收时钟服务，但传给领域类 Inquiry 的是一个时间值。

ⓘ 那用框架「冻结时间」呢？

各语言都有在测试里替换全局时钟的工具（Python 的 freezegun、Vitest 的 vi.useFakeTimers() 等）。 它们本质上就是一种环境上下文：能解一时之急（比如测不好改的遗留代码），但依赖仍然是隐藏的。 对于你能掌控的代码，把时间显式传进去更干净，测试也不需要任何「魔法」。

小结

  • 为了测试而公开私有方法，会让测试和实现耦合，损害抵抗重构。通过可观察行为间接地测私有方法。
  • 如果私有方法复杂到没法通过使用它的公开 API 来测，说明缺少一个抽象。把它抽成独立的类，而不是把私有方法改成公开的。
  • 极少数情况下，私有方法确实属于类的可观察行为 —— 通常是实现了类与 ORM 或工厂之间的非公开契约。
  • 不要仅仅为了单元测试而暴露本该私有的状态。测试与被测系统交互的方式应该和生产代码完全一样，不该有任何特权。
  • 写测试时不要暗示任何特定的实现。从黑盒视角验证生产代码，避免把领域知识泄漏到测试里；把期望结果写死。
  • 代码污染是在生产代码里添加只有测试才需要的代码。它把测试代码和生产代码混在一起，抬高了后者的维护成本。
  • 需要 Mock 具体类来保留其部分功能，是违反单一职责原则的结果。把那个类拆成两个：一个放领域逻辑，另一个负责与进程外依赖通信。
  • 把当前时间表示成环境上下文会污染生产代码、让测试更难。把时间作为显式依赖注入 —— 服务或普通值，能用普通值就用普通值。

💡 接下来怎么用

一下子应用所有准则可能让人不知所措，现实情况也未必像书里的例子那么干净。不妨从小处开始： 下次写测试或评审别人的测试时，只问一个问题 —— 「如果我重构这段代码但不改变它的行为，这个测试会红吗？」 会的话，想想它绑在了什么实现细节上。这一个问题，就能把你带到书里大部分结论那里去。

自测

团队规定「覆盖率必须 90%」，于是有人用反射去调私有方法来补覆盖率。问题出在哪？更好的做法是什么？

两个问题：把覆盖率当成了目标（第 1 章）；测私有方法让测试和实现细节耦合。更好的做法是看那些没被覆盖的私有方法 —— 要么是死代码（删掉），要么藏着一个该抽出来的抽象（抽成独立的类再测）。

测试里有这样一行：expected = price * (1 - discountRate) * (1 + taxRate)，然后和 SUT 的返回值比较。这是哪个反模式？

向测试泄漏领域知识。测试重复了生产代码的计算公式。应该把具体输入对应的结果预先算好、写死在测试里，比如 (100, 0.1, 0.2) → 108。

代码里到处是 if (Environment.isTest()) { … }。这是什么？怎么改？

代码污染。把因环境而异的行为抽到接口后面，生产环境注入真实实现，测试注入假实现；生产代码里不再需要知道「自己是不是在测试里」。
