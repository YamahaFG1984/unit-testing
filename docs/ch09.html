Mock 最佳实践

「Mock 只用于不受管依赖」—— 守住这一条，你已经走完了三分之二的路。 这一章讲剩下的三分之一：Mock 该打在调用链的哪个位置、为什么手写的 Spy 有时比框架生成的 Mock 更好，以及另外几条让 Mock 物尽其用的规矩。

本章目标

  • 在系统的最边缘验证与不受管依赖的交互
  • 用 Spy（手写的 Mock）让断言更简洁，并让测试成为独立的「审计员」
  • 记住五条 Mock 最佳实践

回顾：我们停在哪里

CRM 的控制器现在把领域事件交给 EventDispatcher，由它转成对两个不受管依赖的调用：消息总线和领域日志。

public class UserController {
    private final Database database;
    private final EventDispatcher eventDispatcher;

    public UserController(Database database, IMessageBus messageBus, IDomainLogger domainLogger) {
        this.database = database;
        this.eventDispatcher = new EventDispatcher(messageBus, domainLogger);
    }

    public String changeEmail(int userId, String newEmail) {
        Object[] userData = database.getUserById(userId);
        User user = UserFactory.create(userData);

        String error = user.canChangeEmail();
        if (error != null) return error;

        Object[] companyData = database.getCompany();
        Company company = CompanyFactory.create(companyData);

        user.changeEmail(newEmail, company);

        database.saveCompany(company);
        database.saveUser(user);
        eventDispatcher.dispatch(user.getDomainEvents());

        return "OK";
    }
}

class UserController:
    def __init__(self, database: Database, message_bus: MessageBus,
                 domain_logger: DomainLogger) -> None:
        self._database = database
        self._event_dispatcher = EventDispatcher(message_bus, domain_logger)

    def change_email(self, user_id: int, new_email: str) -> str:
        user_data = self._database.get_user_by_id(user_id)

        self._database.save_user(user)

在系统的边缘验证交互

★ 准则

使用 Mock 时，始终在系统的最边缘验证与不受管依赖的交互。

IMessageBus 的问题在于：它并不在系统边缘。看它的实现：

public interface IMessageBus {
    void sendEmailChangedMessage(int userId, String newEmail);
}

public class MessageBus implements IMessageBus {
    private final IBus bus;

    public MessageBus(IBus bus) { this.bus = bus; }

    @Override
    public void sendEmailChangedMessage(int userId, String newEmail) {
        bus.send("Type: USER EMAIL CHANGED; " +
                 "Id: " + userId + "; " +
                 "NewEmail: " + newEmail);
    }
}

public interface IBus {
    void send(String message);
}

class Bus(Protocol):
    def send(self, message: str) -> None: ...


class MessageBus:
    def __init__(self, bus: Bus) -> None:
        self._bus = bus

    def send_email_changed_message(self, user_id: int, new_email: str) -> None:
        self._bus.send(
            "Type: USER EMAIL CHANGED; "
            f"Id: {user_id}; "
            f"NewEmail: {new_email}")

export interface IMessageBus {
  sendEmailChangedMessage(userId: number, newEmail: string): void
}

export class MessageBus implements IMessageBus {
  constructor(private readonly bus: IBus) {}

  sendEmailChangedMessage(userId: number, newEmail: string): void {
    this.bus.send(
      'Type: USER EMAIL CHANGED; ' +
      `Id: ${userId}; ` +
      `NewEmail: ${newEmail}`)
  }
}

export interface IBus {
  send(message: string): void
}

这里有两层包装，职责不同，最好分开：

  • IBus：包在消息总线厂商的 SDK 外面，隐藏连接凭据之类的技术细节，只暴露一个干净的「发送任意文本消息」的接口。
  • IMessageBus：包在 IBus 外面，定义你的领域里有哪些消息，把它们集中在一处、方便复用。

（这和第 8 章 ILogger 与 IDomainLogger 的关系一模一样。）

这一改，两根支柱同时受益：

🛡

防止回归 ↑

防止回归取决于测试执行的代码量。Mock 打在离不受管依赖最近的那个类型上，集成测试走过的类更多 —— MessageBus 里拼消息的那段代码现在也被测到了。

🔨

抵抗重构 ↑

外部系统期待的是文本消息，而不是「对 MessageBus 类的一次调用」。文本消息才是唯一对外可见的副作用；参与生成消息的那些类只是实现细节。只要消息结构不变，随你怎么重构，测试都不会红。

ⓘ 顺手删掉一个接口

IMessageBus 是只有一个实现的接口，而它存在的唯一正当理由是为了 Mock（第 8 章）。现在不再 Mock 它了， 这个接口可以删掉，所有用到它的地方换成具体的 MessageBus。

💡

对不受管依赖的一次调用在离开你的应用之前会经过好几个阶段。挑最后一个阶段。 这是保证与外部系统向后兼容的最好办法 —— 而这正是 Mock 要帮你达到的目的。

用 Spy 代替 Mock

第 5 章提过：Spy 和 Mock 作用相同，区别只在于 Spy 是手写的，所以也叫「手写的 Mock」。 对于位于系统边缘的类，Spy 比 Mock 更好：它能让断言阶段的代码得到复用，测试更短、更好读。 

public class BusSpy implements IBus {
    private final List<String> sentMessages = new ArrayList<>();

    @Override
    public void send(String message) {
        sentMessages.add(message);                 // 把所有发出的消息存在本地
    }

    public BusSpy shouldSendNumberOfMessages(int number) {
        assertThat(sentMessages).hasSize(number);
        return this;
    }

    public BusSpy withEmailChangedMessage(int userId, String newEmail) {
        String message = "Type: USER EMAIL CHANGED; " +
                         "Id: " + userId + "; " +
                         "NewEmail: " + newEmail;
        assertThat(sentMessages).contains(message);   // 断言这条消息确实发出去了
        return this;
    }
}

class BusSpy:
    def __init__(self) -> None:
        self._sent_messages: list[str] = []

    def send(self, message: str) -> None:
        self._sent_messages.append(message)        # 把所有发出的消息存在本地

    def should_send_number_of_messages(self, number: int) -> "BusSpy":
        assert len(self._sent_messages) == number
        return self

    def with_email_changed_message(self, user_id: int, new_email: str) -> "BusSpy":
        message = (
            "Type: USER EMAIL CHANGED; "
            f"Id: {user_id}; "
            f"NewEmail: {new_email}")
        assert message in self._sent_messages      # 断言这条消息确实发出去了
        return self

export class BusSpy implements IBus {
  private readonly sentMessages: string[] = []

  send(message: string): void {
    this.sentMessages.push(message)                // 把所有发出的消息存在本地
  }

  shouldSendNumberOfMessages(number: number): this {
    expect(this.sentMessages).toHaveLength(number)
    return this
  }

  withEmailChangedMessage(userId: number, newEmail: string): this {
    const message =
      'Type: USER EMAIL CHANGED; ' +
      `Id: ${userId}; ` +
      `NewEmail: ${newEmail}`
    expect(this.sentMessages).toContain(message)   // 断言这条消息确实发出去了
    return this
  }
}

💡 可以改名叫 BusMock

Mock 和 Spy 的区别只是实现细节，而很多程序员不熟悉「Spy」这个词。把 BusSpy 叫作 BusMock 可以免去同事的困惑。

这不是绕了一圈又回到原点吗？

busSpy.withEmailChangedMessage(userId, email) 看起来和最初 Mock IMessageBus 时的 verify(messageBusMock).sendEmailChangedMessage(userId, email) 很像 —— 因为 BusSpy 和 MessageBus 都是 IBus 上面的包装。 但有一个关键区别：

★ 把测试想象成审计员

好的审计员不会被审计对象说什么就信什么，他会独立地再核对一遍。 断言时不要依赖生产代码。在测试里使用一套独立的字面量和常量，必要时宁可把它们从生产代码里复制一份。 否则你写出来的可能是同义反复测试 —— 什么都没验证。

那 IDomainLogger 呢？

DomainLogger 也是包在 ILogger 外面的一层。测试要不要也改成 Mock 更靠边的 ILogger？多数项目里没必要。

消息总线日志
谁在消费其他系统（程序）支持人员、系统管理员（人）
对格式的敏感度很高 —— 你不知道外部系统对结构变化会作何反应较低 —— 重要的是日志存在以及它携带的信息，而非确切的文本格式
Mock 打在哪最边缘（IBus），验证确切文本IDomainLogger 就够了

都是不受管依赖，都需要向后兼容，但对兼容的精确程度要求不同。

五条 Mock 最佳实践

③ Mock 只用于集成测试

这条来自第 7 章的基本原则：代码要么和进程外依赖通信，要么复杂，不能两样都占。 于是自然形成两层 —— 处理复杂度的领域模型，和处理通信的控制器。 领域模型的测试是单元测试，控制器的测试是集成测试。Mock 只用于不受管依赖，而只有控制器和这种依赖打交道， 所以 Mock 只该出现在测试控制器的集成测试里。

不是「一个测试只能有一个 Mock」

有人说一个测试里超过一个 Mock 就说明测了太多东西。这是误解，根源还是第 2 章那个误解 —— 以为「单元」是代码单元。 单元是行为单元，实现它用多少代码不重要；同理，验证一个行为单元需要几个 Mock 也不重要。 我们的例子就用了两个（日志和消息总线），还可能更多。

④ 验证调用次数

与不受管依赖通信时，两件事都要确保：

  • 期望的调用确实发生了 —— 应用不能漏发外部系统期待的消息。
  • 没有意料之外的调用 —— 应用也不能发出多余的消息。

向后兼容是双向的。

// 不够：只确认「发过」
verify(messageBusMock).sendEmailChangedMessage(user.getUserId(), "new@gmail.com");

// 更好：确认「恰好发了一次」
verify(messageBusMock, times(1))
    .sendEmailChangedMessage(user.getUserId(), "new@gmail.com");

// 最好：再确认这个 Mock 上没有任何别的调用

// Spy 的 shouldSendNumberOfMessages(1) 一步涵盖了后两项

⑤ 只 Mock 你自己拥有的类型

这条准则来自 Freeman 和 Pryce：永远在第三方库外面写一层自己的适配器，然后 Mock 这个适配器，而不是 Mock 底层的第三方类型。

为什么不直接 Mock 第三方库提供的接口？

  • 你对第三方代码的工作方式往往没有深入了解。Mock 它的接口有风险：你得确保你 Mock 出来的行为和库的真实行为一致。
  • 适配器屏蔽了第三方代码里不重要的技术细节，用你的应用自己的语言定义了与那个库的关系。
ⓘ 这条准则不适用于进程内依赖和受管依赖

Mock 只用于不受管依赖，所以没必要给内存里的依赖或受管依赖包适配器。 比如某个库提供日期时间 API，直接用就行，它不涉及不受管依赖。 同样，只要 ORM 访问的是外部应用看不到的数据库，也没必要给它再包一层。 当然你可以给任何库都包一层，但除了不受管依赖，很少值得这么做。

小结

  • 在系统的最边缘验证与不受管依赖的交互：Mock 控制器到不受管依赖之间那串类型里的最后一个。 这样既增强了防止回归（集成测试验证了更多代码），又增强了抵抗重构（Mock 脱离了代码的实现细节）。
  • Spy 是手写的 Mock。对于系统边缘的类，Spy 优于 Mock：它让断言阶段的代码可以复用，测试更短、更好读。
  • 断言时不要依赖生产代码。在测试里用一套独立的字面量和常量，必要时从生产代码复制。测试应当是独立于生产代码的检查点，否则可能写出同义反复测试。
  • 不是所有不受管依赖都需要同等精度的向后兼容。如果消息的确切结构不重要，你只想验证它存在以及它携带的信息，可以不必追到最边缘。典型例子是日志。
  • Mock 只用于不受管依赖，而只有控制器和这类依赖打交道，所以只在集成测试里用 Mock，单元测试里不要用。
  • 一个测试里用几个 Mock 无关紧要，数量只取决于参与操作的不受管依赖有几个。
  • 既要确保期望的调用存在，也要确保没有意料之外的调用。
  • 只 Mock 你自己拥有的类型。给访问不受管依赖的第三方库写适配器，Mock 适配器而不是底层类型。

自测

你的代码调用链是：OrderController → NotificationService → SmsGateway（你写的，包装了厂商 SDK）→ 厂商短信 SDK。集成测试里该 Mock 哪个？

SmsGateway。它是你自己拥有的、离不受管依赖最近的类型。不要 Mock NotificationService（不在边缘），也不要直接 Mock 厂商 SDK（不是你的类型）。

为什么说在 BusSpy 里把消息格式字符串「又写一遍」是好事，而不是违反 DRY？

因为测试需要一个独立于生产代码的检查点。如果测试复用了生产代码里的格式常量，有人改错格式时测试也会跟着「改对」，永远是绿的 —— 成了同义反复。

测试只写了 verify(bus).send(expectedMessage)，没验证次数。可能漏掉什么 Bug？

重复发送（同一条消息发了两次），或者额外发了别的消息。对下游系统来说，这些都可能是严重问题（比如重复扣款、重复发货）。

动手练习

  1. 在你的 CRM 实现里引入 IBus / MessageBus 两层，把集成测试的 Mock 从 IMessageBus 挪到 IBus，然后删掉 IMessageBus 接口。
  2. 手写一个 BusSpy，用流式接口重写断言。然后故意把 MessageBus 里的 "NewEmail" 改成 "Email"，确认测试变红。
  3. 在你的项目里找一处直接 Mock 第三方库类型的地方（HTTP 客户端、云存储 SDK、短信 SDK 等）。给它包一层只暴露你所需功能的适配器，改成 Mock 适配器。
  4. 检查项目里现有的 Mock 断言：有多少验证了调用次数？有多少确认了「没有其他调用」？
