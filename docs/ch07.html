第 7 章

重构出有价值的单元测试

前几章教你识别好测试，这一章教你写出好测试。结论可能出乎意料： 想让测试变好，多半要先动被测代码。我们会拿一个接近真实的 CRM 系统，一步步把「难测的一坨」拆成「好测的核心」和「不用怎么测的胶水」。

本章目标

  • 用四象限给任何一段代码分类，并知道每一类该怎么测
  • 理解 Humble Object（谦卑对象）模式：把逻辑从难测的代码里抽出来
  • 跟着 CRM 的例子完成四步重构
  • 处理「控制器里的条件逻辑」这个难题：CanExecute/Execute 模式和领域事件
💻 本章的代码可以直接运行

第 7–10 章的 CRM 示例在仓库的 examples/ 目录里有 Java / Python / TypeScript 三份完整实现 （本章结束时的状态请以那里为准）。怎么跑起来见第 0 章。

四种代码

所有生产代码都可以沿两个维度分类：

维度含义对测试意味着什么
复杂度或领域重要性复杂度 = 代码里决策点（分支）的数量。领域重要性 = 这段代码对项目所解决的问题有多重要越高，测试的防止回归价值越大
协作者的数量协作者 = 可变的或进程外的依赖（第 2 章）。显式传入的和隐式引用的都算；不可变的值不算越多，测试越大、维护成本越高
ⓘ 圈复杂度怎么算

圈复杂度 = 1 + 分支点的数量。没有任何 if / 循环的方法，圈复杂度是 1。 它也等于「从入口到出口的独立路径数」，或者说「达到 100% 分支覆盖需要的测试数」。 注意分支点按最简谓词计：if (a && b) 相当于两层 if，复杂度是 1 + 2 = 3。

复杂度和领域重要性是相互独立的：一个计算订单价格的方法可能一个 if 都没有（复杂度 1）， 但它是业务关键功能，照样值得测。

★ 一条值得贴在墙上的规则

代码越重要、越复杂，它的协作者就应该越少。

消灭过度复杂的代码、只对领域模型和算法做单元测试 —— 这是通往高价值、易维护测试集的路。 这样做你不会有 100% 的覆盖率，但你也不需要。你的目标是：测试集里的每一个测试都在为项目贡献明显的价值。 记住：不写测试，也好过写一个坏测试。

Humble Object 模式

代码难测，往往是因为它和某个难测的依赖绑在了一起：异步或多线程执行、用户界面、与进程外依赖的通信，等等。 Gerard Meszaros 提出的 Humble Object（谦卑对象）模式是这样解决的：

看着眼熟？因为你已经见过它两次了：六边形架构和函数式架构实现的都是这个模式。

  • 六边形架构把业务逻辑和「与进程外依赖的通信」分开 —— 分别由领域层和应用服务层负责。
  • 函数式架构更进一步，把业务逻辑和「与所有协作者的通信」分开。函数式核心没有任何协作者，所以它紧贴着四象限图的纵轴。

代码要么「深」，要么「宽」，不能两样都占

也可以把 Humble Object 看作单一职责原则的应用。我们关心的是把业务逻辑和编排这两种职责分开。 很多耳熟能详的模式其实都是 Humble Object 的变体： MVC / MVP 里的 Controller / Presenter 是谦卑对象，负责把视图和模型粘起来； 领域驱动设计里的聚合（Aggregate）通过把类分组成簇来减少类之间的连接。

实战：重构一个 CRM 系统

示例是一个管理用户注册的 CRM，所有用户存在数据库里。目前只有一个用例：修改用户的邮箱。涉及三条业务规则：

起点：一个「什么都干」的 User 类

public class User {
    private int userId;
    private String email;
    private UserType type;

    public void changeEmail(int userId, String newEmail) {
        Object[] data = Database.getUserById(userId);          // 从数据库取出用户当前的邮箱和类型
        this.userId = userId;
        this.email = (String) data[1];
        this.type = (UserType) data[2];

        if (email.equals(newEmail)) return;

        Object[] companyData = Database.getCompany();          // 从数据库取出公司域名和员工数
        String companyDomainName = (String) companyData[0];
        int numberOfEmployees = (int) companyData[1];

        String emailDomain = newEmail.split("@")[1];
        boolean isEmailCorporate = emailDomain.equals(companyDomainName);
        UserType newType = isEmailCorporate                    // 根据新邮箱的域名决定用户类型
            ? UserType.EMPLOYEE : UserType.CUSTOMER;

        if (type != newType) {
            int delta = newType == UserType.EMPLOYEE ? 1 : -1;
            Database.saveCompany(numberOfEmployees + delta);   // 必要时更新员工数
        }

        this.email = newEmail;
        this.type = newType;

        Database.saveUser(this);                               // 把用户存回数据库
        MessageBus.sendEmailChangedMessage(userId, newEmail);  // 往消息总线发通知
    }
}

用四象限分析一下：

  • 复杂度 / 领域重要性：高。决策点不多（用户算员工还是客户、员工数怎么变），但这些正是应用的核心业务逻辑。
  • 协作者：多。两个显式依赖 userId 和 newEmail 是值，不算；但两个隐式依赖 Database 和 MessageBus 是进程外协作者 —— 而前面说过，领域重要性高的代码不应该碰进程外协作者。

结论：过度复杂的代码，右上角。

ⓘ Active Record 模式

这种「领域类自己负责从数据库读取和保存自己」的做法叫 Active Record。在简单或短命的项目里没问题， 但代码库一大就撑不住 —— 原因正是业务逻辑和进程外通信这两种职责没有分开。

第 1 步：把隐式依赖变成显式依赖（不够）

常规思路：给 Database 和 MessageBus 抽接口，注入 User，测试时 Mock。第 6 章审计系统的「Mock 版」就是这么做的。 这有帮助，但不够。

从四象限的角度看，领域模型是直接引用进程外依赖还是通过接口引用，没有区别 —— 它们仍然是进程外的， 你仍然要维护一套复杂的 Mock 机制来测这个类。而且给数据库用 Mock 还会让测试变脆弱（下一章讲）。 更干净的做法是：领域模型完全不依赖进程外协作者，直接的、间接的都不要。

第 2 步：引入应用服务层

把「与外部系统通信」的职责移到另一个类 —— 一个谦卑的控制器（六边形架构里叫应用服务）。 领域类只依赖进程内的东西：其他领域类，或者普通的值。 

public class UserController {
    private final Database database = new Database();
    private final MessageBus messageBus = new MessageBus();

    public void changeEmail(int userId, String newEmail) {
        Object[] data = database.getUserById(userId);
        String email = (String) data[1];
        UserType type = (UserType) data[2];
        var user = new User(userId, email, type);

        Object[] companyData = database.getCompany();
        String companyDomainName = (String) companyData[0];
        int numberOfEmployees = (int) companyData[1];

        int newNumberOfEmployees = user.changeEmail(
            newEmail, companyDomainName, numberOfEmployees);

        database.saveCompany(newNumberOfEmployees);
        database.saveUser(user);
        messageBus.sendEmailChangedMessage(userId, newEmail);
    }
}

User 现在很好测了 —— 它不再和任何进程外依赖通信，事实上它一个协作者都没有。但控制器还有四个问题：

  1. 进程外依赖是直接 new 出来的，不是注入的 —— 以后写集成测试会碍事。
  2. 控制器从数据库原始数据重建 User 对象。这是有一定复杂度的逻辑，不该放在只负责编排的应用服务里。
  3. 公司数据同理。而且 User 现在要返回更新后的员工数 —— 这很别扭：公司员工数和某个具体用户有什么关系？这个职责放错了地方。
  4. 不管邮箱变没变，控制器都无条件地保存数据、发消息。

第 3 步：把复杂度从应用服务里拿走

重建对象的逻辑，如果用了 ORM 就交给 ORM 的映射配置；没用的话，在领域模型里建一个工厂： 

public class UserFactory {
    public static User create(Object[] data) {
        Precondition.requires(data.length >= 3);

        int id = (int) data[0];
        String email = (String) data[1];
        UserType type = (UserType) data[2];

        return new User(id, email, type);
    }
}

🔬 只有一个分支，凭什么说它「复杂」？

还记得第 1 章说的吗？代码调用的库里藏着很多看不见的分支。按下标取数组元素（data[0]）、类型转换， 运行时内部都在做决定：是正常返回，还是抛越界 / 类型转换异常？这些隐藏分支让重建逻辑值得测试，尽管它表面上没什么决策点。

不过注意：这段逻辑有一定复杂度，却没有领域重要性 —— 它和「改邮箱」这个客户目标没有直接关系。它是前面说的工具类代码。

第 4 步：引入 Company 类

「User 返回更新后的员工数」这种别扭，是职责放错位置的信号，而这又是缺少一个抽象的信号。 补上它：一个把公司相关的数据和逻辑捆在一起的 Company 领域类。 

public class Company {
    private final String domainName;
    private int numberOfEmployees;

    public Company(String domainName, int numberOfEmployees) {
        this.domainName = domainName;
        this.numberOfEmployees = numberOfEmployees;
    }

    public void changeNumberOfEmployees(int delta) {
        Precondition.requires(numberOfEmployees + delta >= 0);
        numberOfEmployees += delta;
    }

    public boolean isEmailCorporate(String email) {
        String emailDomain = email.split("@")[1];
        return emailDomain.equals(domainName);
    }

    public int getNumberOfEmployees() { return numberOfEmployees; }
}

Company 的两个方法体现了第 5 章提到的 Tell-Don't-Ask：User 是告诉公司「把员工数改一下」 「判断一下这个邮箱是不是公司的」，而不是把原始数据要过来自己算。

ⓘ 和第 6 章的函数式架构比一比

相同点：审计系统的函数式核心和 CRM 的领域层都不和进程外依赖通信；应用服务层负责取原始数据、交给核心 / 领域模型、再把结果存回去。

不同点：函数式核心完全没有副作用。CRM 的领域模型有副作用（改了用户邮箱、改了员工数）， 但这些副作用一直留在内存里，直到控制器把 User 和 Company 存进数据库的那一刻才越过领域模型的边界。

副作用直到最后一刻都留在内存里，这对可测试性帮助极大：测试不用检查进程外依赖，也不用基于通信的测试， 全部验证都可以对内存中的对象用基于输出和基于状态的方式完成。

要不要测前置条件

changeNumberOfEmployees 里有个前置条件：员工数不能变成负数。这种防护只在异常情况（通常是代码有 Bug）下才会触发， 目的是让软件快速失败，不让错误扩散并写进数据库。这种东西要测吗？

前置条件有领域意义吗测不测
Company：员工数不能为负有 —— 它是 Company 的不变量测
UserFactory：data.length >= 3没有 —— 纯技术性检查不测

CanExecute / Execute 模式

给 CRM 加一个新需求：用户确认邮箱之后，就不能再改了。试图修改已确认的邮箱，应该看到一条错误信息。 这个检查放在哪儿？

放哪结果
放进 User.changeEmail()，让它返回错误控制器保持简单，但损失性能：即使邮箱已确认、根本改不了，Company 也已经无条件从数据库读出来了（这就是方案 A）
放进控制器：先判断 user.isEmailConfirmed 再去读 Company性能好，但决策被拆成了两半（「能不能改」在控制器，「怎么改」在 User），而且现在不检查标志也能改邮箱 —— 封装被破坏了

第三种办法：在 User 里加一个 canChangeEmail() 方法，并把「它返回成功」作为 changeEmail() 的前置条件：

这带来两个好处：

  • 控制器不需要了解改邮箱的任何规则，只管问一句 canChangeEmail()。这个方法里可以有很多条校验，全都封装在领域层。
  • changeEmail() 里的前置条件保证了：不先确认「能改」，邮箱就绝不会被改。

于是所有决策都集中回了领域层。控制器里虽然还有一个 if，但它没有不检查的选项，所以这个 if 不算新的决策点，也不需要专门测 —— 对 User 里的前置条件做单元测试就够了。

用领域事件追踪领域模型里的变化

现在的实现有个 Bug：即使邮箱没变（新旧相同），控制器照样会往消息总线发消息。 把「新旧是否相同」的检查挪到控制器里？又是业务逻辑碎片化。放进 canChangeEmail()？不行 —— 新旧相同不该算错误。

领域事件（domain event）

描述应用中发生的、对领域专家有意义的事件（这是它和按钮点击之类普通事件的区别）。 常用来把系统里发生的重要变化通知给外部应用。从实现上看，它就是一个携带通知所需数据的类。 领域事件是值 —— 不可变、可互换；命名一律用过去时，因为它表示已经发生的事。 

public record EmailChangedEvent(int userId, String newEmail) {}

// User
private final List<EmailChangedEvent> emailChangedEvents = new ArrayList<>();

public void changeEmail(String newEmail, Company company) {
    Precondition.requires(canChangeEmail() == null);

    if (email.equals(newEmail)) return;

    UserType newType = company.isEmailCorporate(newEmail)
        ? UserType.EMPLOYEE : UserType.CUSTOMER;

    if (type != newType) {
        int delta = newType == UserType.EMPLOYEE ? 1 : -1;
        company.changeNumberOfEmployees(delta);
    }

    email = newEmail;
    type = newType;
    emailChangedEvents.add(new EmailChangedEvent(userId, newEmail));   // 记下「邮箱变了」
}

// UserController
public String changeEmail(int userId, String newEmail) {

    User user = UserFactory.create(userData);

ⓘ 为什么数据库还是无条件保存？

因为数据库的变更和总线上的消息性质不同。假设只有 CRM 能访问这个数据库，那么与数据库的通信是实现细节 —— 只要最终状态正确，调多少次都无所谓。而与消息总线的通信是可观察行为，为了遵守和外部系统的契约，只有邮箱真的变了才能发消息。

无条件保存有一点性能影响，但很小；而且大多数 ORM 在对象状态没变时根本不会访问数据库。

结语：像剥洋葱一样测试

这一章反复出现的主题是：把「对外部系统施加副作用」这件事抽象起来，让副作用留在内存里直到业务操作的最后一刻， 这样就能用普通的单元测试去验证，而不必牵扯进程外依赖。

★ 测抽象，比测它所抽象的东西容易

领域事件是「即将发到总线的消息」的抽象。
领域对象的状态变化是「即将写进数据库的修改」的抽象。

不过别指望把所有决策都收进领域模型，有些碎片化是避免不了的：

  • 校验邮箱唯一性：不把进程外依赖引入领域模型，就只能在控制器里做。
  • 进程外依赖调用失败时该怎么办：这个决定没法放在领域层，因为调用那些依赖的不是领域层。

这类逻辑只能放在控制器里，然后用集成测试覆盖。同样，领域类也很少能做到一个协作者都没有 —— 有一两个、两三个都没关系，只要它们不涉及进程外依赖。

测试控制器时，验证它的入口方法和它对消息总线的调用（绿线），不要验证它对 User 的调用。 往下一层，控制器成了客户端：测 User.changeEmail()（蓝线），但不要验证 User 调了 Company 的哪些方法。 再往下一层，从 User 的视角去测 Company 的两个方法（橙线）。 每剥一层就换一次视角：刚才还是实现细节的东西，现在成了可观察行为，由另一组测试覆盖。

⚠ 不要用 Mock 验证领域类之间的交互

只有从控制器到领域类的第一个调用和控制器的目标直接相关。领域类在同一个操作里对相邻领域类的后续调用，全都是实现细节。

小结

  • 复杂度由决策点的数量决定，包括显式的（代码自己做的）和隐式的（所用的库做的）。领域重要性表示代码对项目问题领域的重要程度。
  • 复杂的或有领域重要性的代码最值得单元测试（防止回归价值高）；协作者多的代码测试成本高。
  • 四种代码：领域模型与算法（重点单元测试）、琐碎代码（不测）、控制器（少量集成测试）、过度复杂的代码（拆成前两者）。
  • 代码越重要或越复杂，协作者应该越少。
  • Humble Object 模式把业务逻辑从过度复杂的代码里抽到单独的类中，剩下的代码成为围绕业务逻辑的一层薄薄的、谦卑的包装 —— 控制器。六边形架构和函数式架构都实现了这个模式。
  • 把业务逻辑和编排想成「深」与「宽」：代码可以深，可以宽，但不能既深又宽。
  • 有领域意义的前置条件要测，没有的不用测。
  • 分离业务逻辑和编排时，有三个属性最多只能同时保住两个：领域模型可测性、控制器简单性、性能。「把决策拆成更细的步骤」是利弊最均衡的选择。
  • CanExecute/Execute 模式：为每个 do() 配一个 canDo()，并让后者成功成为前者的前置条件，从而消除控制器里的决策。
  • 领域事件追踪领域模型里的重要变化，再把这些变化转成对进程外依赖的调用，从而把追踪的职责从控制器里拿走。
  • 测抽象比测它所抽象的东西容易。领域事件是对「即将发生的进程外调用」的抽象；领域对象的变化是对「即将发生的存储修改」的抽象。

自测

一个方法有 200 行，里面有 15 个 if，同时直接调用了数据库、邮件服务和支付网关。它在哪个象限？怎么办？

过度复杂的代码（右上角）。用 Humble Object 模式拆开：把那 15 个 if 的决策逻辑抽成不依赖任何进程外东西的领域类 / 纯函数；原方法只剩「读数据 → 调用领域逻辑 → 写数据 / 发通知」的编排。

为什么说「给 Database 抽个接口再注入 User」解决不了根本问题？

因为不管是直接引用还是通过接口，User 仍然有进程外协作者，在四象限里的位置没变。测试仍然需要复杂的 Mock 设置，而且 Mock 数据库还会让测试变脆弱。

领域事件为什么要用过去时命名（EmailChanged 而不是 ChangeEmail）？

因为它描述的是已经发生的事实，而不是一条待执行的命令。它是不可变的值。
