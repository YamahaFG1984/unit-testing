单元测试：原则、实践与模式

这套教程整理自 Vladimir Khorikov 的《Unit Testing: Principles, Practices, and Patterns》（Manning, 2020）。 原书回答的不是「怎么写测试」，而是一个更难的问题：什么样的测试才值得写。 教程保留了原书的全部章节和推理过程，把例子从 C# 改写成了三种语言，并为每个关键概念配了图。

这套教程解决什么问题

你可能已经会写单元测试了，甚至写过很多。但你大概也遇到过这些情况：

🔴

改个方法名，红了一片

功能明明没坏，测试却挂了。修测试花的时间比写功能还多。

🟢

测试全绿，线上照样出 Bug

覆盖率 90%，可真正的问题一个都没拦住。

🧱

测试比被测代码还长

准备阶段一屏 Mock 设置，就为了验证控制器里的三行代码。

🤔

说不清一个测试好不好

凭感觉觉得不对劲，但评审时讲不出道理。

这本书给出了一套可以推导、可以讲清楚的标准。读完之后，对任何一个测试，你都能说出它值不值得留、问题出在哪、该怎么改。

学习路线

怎么用这套教程

  • 按顺序读。这本书是一步步推导出来的，后面的结论依赖前面的定义。尤其不要跳过第 4 章和第 5 章。
  • 代码块可以切换语言。带标签的代码块有 Java / Python / TypeScript 三个版本，点一下标签，全站都会切换并记住你的选择。三个版本表达的是同一件事，只是写法各自遵循该语言的习惯。
  • 每章末尾有自测和练习。自测题点开就能看答案；练习建议真的动手 —— 看懂和写出来之间的差距，比想象的大。
  • 想对照原书代码？每段示例下面都标了对应的原书 Listing 编号和仓库里 code/Book/ChapterN/ 下的 C# 文件。

试试切换语言（下面三个版本做的是同一件事）：

@Test
void delivery_with_a_past_date_is_invalid() {
    var sut = new DeliveryService();
    var delivery = new Delivery(LocalDateTime.now().minusDays(1));

    boolean isValid = sut.isDeliveryValid(delivery);

    assertThat(isValid).isFalse();
}

def test_delivery_with_a_past_date_is_invalid():
    sut = DeliveryService()
    delivery = Delivery(date=datetime.now() - timedelta(days=1))

    is_valid = sut.is_delivery_valid(delivery)

    assert is_valid is False

test('delivery with a past date is invalid', () => {
  const sut = new DeliveryService()
  const delivery = new Delivery(addDays(new Date(), -1))

  const isValid = sut.isDeliveryValid(delivery)

  expect(isValid).toBe(false)
})
ⓘ 需要什么前置知识

会用三种语言中的任意一种写类和函数，知道「测试框架」大概是什么就够了。 Mock、六边形架构、领域事件这些概念都会在第一次出现时从头解释。

先混个眼熟：十个高频术语

术语一句话解释详见
SUT（被测系统）这个测试要验证的那个类 / 对象第 2 章
回归原本好用的功能，改代码之后不好用了第 1 章
误报（假阳性）功能没坏，测试却红了第 4 章
可观察行为帮助调用方达成目标的操作或状态；与之相对的是实现细节第 5 章
Mock / StubMock 检查「往外发」的调用；Stub 提供「往里拿」的数据第 5 章
共享依赖能让测试互相干扰的依赖，如数据库、文件、静态可变字段第 2 章
受管 / 不受管依赖只有你的应用能访问的（如自己的库）/ 别的系统也看得见的（如消息总线）第 8 章

💡 如果只记住一件事

写完一个测试，问自己：「如果我重构这段代码但不改变它的行为，这个测试会红吗？」 会的话，它测的是实现而不是行为。这套教程剩下的全部内容，都是在解释怎样让答案变成「不会」，同时还能抓住真正的 Bug。
