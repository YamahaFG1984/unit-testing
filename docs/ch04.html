好测试的四大支柱

第 1 章说「要一个一个地评估测试」，但拿什么评估？这一章给你一把尺子：四个属性。 有了它，任何一个自动化测试 —— 单元的、集成的、端到端的 —— 你都能说清楚它好在哪、差在哪。 后面每一章都在用这把尺子。

本章目标

  • 记住四大支柱：防止回归、抵抗重构、快速反馈、可维护性
  • 分清误报（假阳性）和漏报（假阴性），知道哪根支柱对付哪个
  • 理解为什么「理想的测试」不存在，以及该在哪里做取舍
  • 用四大支柱解释测试金字塔和黑盒 / 白盒测试

四大支柱一览

支柱一：防止回归

回归就是 Bug：某次改代码之后，原本好用的功能不好用了。功能越多，新版本弄坏旧功能的机会就越多 —— 代码库越大，暴露给潜在 Bug 的面积越大。没有好的回归防护，项目迟早会被越来越多的 Bug 埋掉。

一个测试在这项上得分多少，看三样东西：

📏

执行的代码量

测试跑过的代码越多，发现回归的机会越大（当然前提是有对应的断言，不是光执行）。

🧩

代码的复杂度

复杂的业务逻辑比样板代码更容易出错，也就更值得保护。

💰

代码的业务重要性

业务关键功能出 Bug 损失最大。

反过来，测琐碎代码几乎没有意义。比如一个只有一行的属性读写 —— 它太简单了，几乎没有出错的余地， 测它也就几乎不可能发现回归。

💡 别忘了不是你写的代码

库、框架、外部系统对软件行为的影响几乎和你自己的代码一样大。要获得最好的防护， 测试范围应该把它们也包括进来，以验证你对这些依赖所做的假设是正确的。 想把「防止回归」做到最大，就让测试执行尽可能多的代码。

支柱二：抵抗重构

重构（refactoring）

在不改变可观察行为的前提下修改现有代码。目的通常是改善非功能特性：更好读、更简单。例如给方法改名、把一段代码抽到新类里。

想象这个场景：新功能做完了，一切正常，测试全绿。你决定整理一下代码 —— 这里重构一下，那里调整一下，看起来比之前更好了。 只有一个问题：测试红了。你仔细查了半天到底哪里弄坏了，结果发现什么都没坏，功能和之前一模一样。 是测试写得有问题：只要底层代码有任何改动它就变红，不管功能有没有真的坏。

误报 / 假阳性（false positive）

一次假警报：测试失败了，但它覆盖的功能其实工作正常。误报通常发生在重构时 —— 你改了实现，但行为没变。 一个测试产生的误报越少，它的「抵抗重构」得分越高。

为什么误报这么要命

测试之所以能支撑项目的可持续增长，靠的是两件事：

  • 早期预警：你一弄坏现有功能，测试马上告诉你，远在代码上生产之前。
  • 信心：你确信自己的改动不会引入回归，所以敢重构。

误报把这两件事都毁了：

误报从哪里来

★ 本章最重要的一句话

一个测试产生多少误报，直接取决于它的结构：测试和被测系统的实现细节耦合得越紧，误报越多。 减少误报的唯一办法，是把测试和实现细节解耦 —— 让测试验证 SUT 交付的最终结果（可观察行为）， 而不是它为此采取的步骤。

看一个例子。MessageRenderer 把一条消息（标题、正文、页脚）渲染成 HTML，它内部把工作分给了三个子渲染器：

public record Message(String header, String body, String footer) {}

public interface Renderer {
    String render(Message message);
}

public class HeaderRenderer implements Renderer {
    public String render(Message m) { return "<h1>" + m.header() + "</h1>"; }
}
public class BodyRenderer implements Renderer {
    public String render(Message m) { return "<b>" + m.body() + "</b>"; }
}
public class FooterRenderer implements Renderer {
    public String render(Message m) { return "<i>" + m.footer() + "</i>"; }
}

public class MessageRenderer implements Renderer {
    private final List<Renderer> subRenderers = List.of(
        new HeaderRenderer(), new BodyRenderer(), new FooterRenderer());

    public List<Renderer> getSubRenderers() { return subRenderers; }

    public String render(Message message) {
        return subRenderers.stream()
            .map(r -> r.render(message))
            .collect(Collectors.joining());
    }
}

  • 把 BodyRenderer 换成一个功能相同的 BoldRenderer —— 输出不变，测试红了。

🔬 最离谱的脆弱测试

原书作者见过一个测试：它读取 MessageRenderer 的源代码文件，然后和一段写死在测试里的「正确实现」做字符串比较。 改一个空格它都会挂。听起来很可笑，但它和上面那个测试本质上是一回事： 都坚持某一种特定的实现，都不关心 SUT 的可观察行为。区别只是挂得更频繁而已。

瞄准最终结果，而不是实现细节

问自己一个问题：你从 MessageRenderer 那里最终得到的是什么？ 是消息的 HTML 表示。这是这个类唯一的可观察结果，也是唯一值得检查的东西。只要 HTML 不变，它是怎么生成的根本不重要。

新测试把 MessageRenderer 当成黑盒，只关心它的可观察行为。它验证的是对最终用户唯一有意义的结果 —— 消息在浏览器里显示成什么样。这种测试一旦失败，总是切中要害：它在告诉你应用的行为变了，可能会影响客户。

ⓘ 为什么说「很少误报」而不是「没有误报」

比如你给 render() 加了一个参数，测试会编译不过。严格说这也算误报（行为没变，测试却过不了）。 但这种误报很好修 —— 跟着编译器的提示改就行。真正难缠的是不会引起编译错误的误报： 它们看起来像是真 Bug，要花很多时间去排查。

前两根支柱的内在联系：准确度

「功能对不对」和「测试过没过」两两组合，一共四种情况：

💡 用流感检测来记「阳性 / 阴性」

「阳性」听起来像好事，其实是指检测所针对的那个条件成立了。流感检测阳性 = 得了流感；测试「阳性」= 测试失败（发现了问题）。

  • 假阳性（误报）：没得流感，却检测出阳性。→ 代码没坏，测试却红了。
  • 假阴性（漏报）：得了流感，却检测出阴性。→ 代码坏了，测试却是绿的。

支柱三和四：快速反馈、可维护性

⚡

③ 快速反馈

测试越快，测试集里能放的测试越多，你也越愿意经常跑。跑得快，你一弄坏代码它就提醒你，修复成本几乎为零； 跑得慢，你就不爱跑，Bug 潜伏的时间变长，朝错误方向浪费的时间也更多。

🔧

④ 可维护性

读懂它有多难：和测试的大小有关，代码行数越少越好读（但别为了压行数而牺牲质量 —— 测试代码是一等公民）。
运行它有多难：如果涉及进程外依赖，你得花时间让它们保持可用：重启数据库、解决网络问题等等。

寻找理想的测试

四个属性相乘，决定一个测试的价值：

理想的测试不存在

理想的测试 = 四项全拿满分。可惜做不到，因为前三项 —— 防止回归、抵抗重构、快速反馈 —— 是互斥的： 你只能牺牲其中一项，来把另外两项拉满。来看三个「两项拉满、一项归零」的极端例子。

极端一：端到端测试

端到端测试从用户视角走过系统的所有组件（UI、数据库、外部应用），执行的代码最多 —— 包括你写的和你没写的 —— 所以防止回归最强。它也几乎不会误报：正确的重构不改变可观察行为，而端到端测试只看行为，离实现细节最远，所以抵抗重构也很好。 但它慢。只靠端到端测试的系统很难获得快速反馈，这对很多团队是不可接受的。

测试关注的是「怎么做」而不是「做了什么」，把 SUT 的实现细节固化了下来，堵死了后续重构的路。

结论：在哪里做取舍

既然三项不能全拿，是不是每项都让一点？不是。

★ 抵抗重构没得商量

一个测试有没有抵抗重构的能力，基本上是二元的：要么有，要么没有，几乎没有中间状态。 你没法「只让出一点点」—— 一让就全没了。而防止回归和快速反馈则是连续可调的。

所以：抵抗重构和可维护性尽量拉满；真正的取舍只发生在防止回归和快速反馈之间。 消灭测试的脆弱性（误报），是通往可靠测试集的第一要务。

🔬 类比：分布式系统的 CAP 定理

CAP 定理说，分布式数据存储无法同时保证一致性（C）、可用性（A）、分区容错性（P）三者，最多取其二。 相似之处有两点：一是「三选二」；二是其中一项没得选 —— 大型分布式系统不可能放弃分区容错 （数据多到一台机器装不下），所以实际的选择只剩「一致性 vs. 可用性」。 测试里那个没得选的，就是抵抗重构。

用四大支柱解释测试金字塔

为什么端到端测试该是少数？还是乘法规则：它在「快速反馈」上得分极低，「可维护性」也差（体积大，还要维护一堆进程外依赖）。 所以只有对最关键的功能（绝对不能出 Bug 的那种），而且单元测试和集成测试给不了同等防护时，才值得用它。

金字塔的例外

黑盒测试与白盒测试

是什么防止回归抵抗重构
黑盒测试不了解内部结构，围绕需求和规格来测：应用应该做什么较差好
白盒测试验证内部工作方式，测试是从源代码推导出来的：应用是怎么做的好差

白盒测试更彻底 —— 分析源码能发现很多只看规格发现不了的错误。但它写出来的测试往往很脆弱，和具体实现绑得很紧， 而且常常追溯不到任何一条对业务人员有意义的行为。

既然抵抗重构没得商量，结论就很清楚了：

★ 默认选黑盒

让所有测试 —— 单元、集成、端到端 —— 都把系统看成黑盒，验证对问题领域有意义的行为。 如果一个测试追溯不到任何业务需求，这就是它脆弱的迹象：要么重写，要么删掉。 （唯一的例外是算法复杂度很高的工具类代码，见第 7 章。）

写测试时用黑盒方法；分析测试时可以用白盒方法 —— 用覆盖率工具看看哪些分支没被执行到，然后转过身来，像完全不了解内部结构那样去为它们写测试。两者结合效果最好。

小结

  • 好测试有四个基础属性，可用来分析任何自动化测试：防止回归、抵抗重构、快速反馈、可维护性。
  • 防止回归衡量测试发现 Bug 的能力。执行的代码越多（包括库和框架的代码），越可能发现 Bug。
  • 抵抗重构衡量测试在代码重构时不产生误报的能力。
  • 误报是假警报。它让你对失败麻木，也让你不再信任测试集。
  • 误报源于测试与 SUT 的实现细节紧耦合。测试应验证 SUT 产出的最终结果，而不是它采取的步骤。
  • 前两项共同决定测试的准确度：信号强（能发现 Bug）、噪音少（不乱报）。
  • 误报在项目初期影响不大，但随着项目增长会变得和漏报一样重要。
  • 快速反馈衡量测试执行得有多快。可维护性包括读懂测试的难度和运行测试的难度。
  • 测试的价值是四项得分的乘积，任何一项为零则价值为零。
  • 前三项互斥，最多拉满两项。抵抗重构不可妥协（它基本是二元的），取舍发生在防止回归和快速反馈之间。
  • 测试金字塔：端到端最少、单元最多、集成居中。不同层在「防止回归 vs. 快速反馈」上做了不同选择。
  • 写测试用黑盒方法，分析测试用白盒方法。

自测

你把一个私有方法改了名，功能完全没变，结果有 5 个测试红了。这是哪种错误？哪根支柱出了问题？

误报（假阳性，第一类错误）。「抵抗重构」这根支柱出了问题 —— 这些测试和实现细节耦合了。

一个测试在三项上得分 0.9、0.9、0.9，在「抵抗重构」上得分 0。它的价值大约是多少？

0。四项是相乘的关系。它就是一个脆弱测试，每次重构都会制造噪音。

为什么不能把所有测试都写成端到端测试？它在前两根支柱上得分都很高。

因为它在「快速反馈」上得分极低，「可维护性」也差。乘法规则下，这会把总价值拉得很低。只有最关键的功能才值得这个代价。
