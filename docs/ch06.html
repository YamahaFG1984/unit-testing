第 6 章

单元测试的三种风格

测试验证结果的方式只有三种：看返回值、看状态、看调用。 三种方式质量并不相等。这一章用四大支柱给它们排个序，然后通过一个完整的重构案例， 演示怎么把代码改造成能用最好的那种方式来测。

本章目标

  • 认识三种风格：基于输出、基于状态、基于通信
  • 知道为什么基于输出的测试质量最高
  • 理解纯函数和函数式架构（函数式核心 + 可变外壳）
  • 跟着审计系统的例子走完「直接读写文件 → 用 Mock → 函数式架构」三步重构
  • 了解函数式架构的代价，知道什么时候不值得用

三种风格

ⓘ 风格与学派

经典学派偏好基于状态胜过基于通信；伦敦学派正好相反。两派都使用基于输出的测试。

用四大支柱比较三种风格

防止回归、快速反馈：差别不大

防止回归取决于执行的代码量、复杂度和业务重要性，和风格无关 —— 哪种风格都能写出覆盖多或少的测试。 唯一要小心的是基于通信的风格：滥用时会写出只验证薄薄一层、其余全部 Mock 掉的「浅」测试。但这是滥用的问题，不是风格固有的。

快速反馈也差不多。只要不碰进程外依赖，三种风格的速度基本一样。Mock 在运行时会有一点额外开销，除非你有几万个测试，否则可以忽略。

抵抗重构：输出最好，通信最差

要说明的是，脆弱并不是基于通信风格的必然特征 —— 只要保持好封装、只验证可观察行为，误报可以降到最低。 区别在于需要付出多少小心：基于输出几乎不用操心，另外两种要时刻留神。

可维护性：差别最大，而且没法弥补

可维护性 = 读懂测试有多难（取决于测试大小）+ 运行测试有多难（取决于进程外依赖）。

基于输出：只做两件事 —— 给输入、验输出，通常几行代码就完事。被测代码不改状态，也就不涉及进程外依赖。两项都是最好的。

⚠ 办法二不能乱用

只有当这个类本质上就是一个值时，才适合把它改成值对象。否则你就是为了简化测试而往生产代码里塞东西 —— 这叫代码污染，是第 11 章要讲的反模式。

基于通信：最差。要设置替身、要写交互断言，都很占地方。如果出现 Mock 链 （Mock 返回另一个 Mock，它又返回 Mock，套好几层），测试会更大、更难维护。

比较结果

基于输出基于状态基于通信
为保持抵抗重构需要付出的小心低中中
维护成本低中高
★ 结论：永远优先选择基于输出的测试

问题是，这种风格只适用于以函数式方式编写的代码，而在面向对象语言里这种代码不多。 好在有办法把更多的代码改造成这样 —— 这就是本章后半部分的内容。

理解函数式架构

什么是函数式编程

函数式编程就是用数学函数来编程。数学函数（也叫纯函数）是没有任何隐藏的输入或输出的函数： 所有输入和输出都明明白白写在方法签名（方法名、参数、返回类型）里。给它同样的输入，不管调用多少次，都得到同样的输出。

显式的输入输出让纯函数极其好测：测试短小、简单、好读。纯函数是唯一能用基于输出风格来测的代码。 反过来，隐藏的输入输出让代码难测，也难读。隐藏的输入输出有三种：

💡 判断是不是纯函数：引用透明

看能不能把对这个方法的调用直接换成它的返回值，而程序行为不变。能换，就是纯函数。 

// ✓ 纯函数：increment(4) 和 5 可以互相替换
public int increment(int x) {
    return x + 1;
}

// ✗ 不是纯函数：返回值没有体现它的全部输出，x 被改了（副作用）
int x = 0;
public int increment() {
    x++;
    return x;
}

public Comment addComment(String text) {
    var comment = new Comment(text);
    comments.add(comment);        // 副作用

什么是函数式架构

完全没有副作用的应用是不存在的 —— 更新用户信息、往购物车加一行，这些副作用正是你写应用的目的。 函数式编程的目标不是消灭副作用，而是把处理业务逻辑的代码和产生副作用的代码分开。 两件事各自已经够复杂了，混在一起复杂度会成倍增长。

函数式架构（functional architecture）

把副作用推到业务操作的边缘，让以纯函数（不可变）方式编写的代码尽可能多，处理副作用的代码尽可能少。

🔬 封装与不可变性

封装通过「缩小能改数据的 API 面积、并严格把关剩下的 API」来保护不变量。 不可变性从另一个角度解决同一个问题：不能被改变的东西，根本不可能被弄坏。 你只需要在创建对象时校验一次，之后可以放心地到处传递。

Michael Feathers 有句名言：「面向对象编程通过封装活动部件来让代码易于理解； 函数式编程通过减少活动部件来让代码易于理解。」

函数式架构 vs. 六边形架构

六边形架构函数式架构
核心思想关注点分离（两者相同）
两层领域层 + 应用服务层函数式核心 + 可变外壳
依赖方向单向：外层依赖内层，内层不依赖外层（两者相同）
对副作用的态度领域层可以有副作用，只要不越出领域层（比如领域对象可以改自己的状态，但不能直接写数据库）核心完全没有副作用，全部推到外壳
ⓘ 一句话

函数式架构是六边形架构的一个子集 —— 可以把它看成推到极致的六边形架构。

实战：把审计系统改造成函数式架构

示例项目是一个访客审计系统，用纯文本文件记录每位访客的姓名和到访时间。 新记录追加到最新的文件末尾；一个文件的条数达到上限后，就新建一个序号加一的文件。

第 0 版：直接读写文件系统

public class AuditManager {
    private final int maxEntriesPerFile;
    private final Path directory;

    public AuditManager(int maxEntriesPerFile, Path directory) {
        this.maxEntriesPerFile = maxEntriesPerFile;
        this.directory = directory;
    }

    public void addRecord(String visitorName, LocalDateTime timeOfVisit) throws IOException {
        List<Path> sorted;
        try (var paths = Files.list(directory)) {
            sorted = sortByIndex(paths.toList());
        }
        String newRecord = visitorName + ";" + timeOfVisit.format(ISO_LOCAL_DATE_TIME);

        if (sorted.isEmpty()) {
            Files.writeString(directory.resolve("audit_1.txt"), newRecord);
            return;
        }

        Path currentFile = sorted.get(sorted.size() - 1);
        List<String> lines = new ArrayList<>(Files.readAllLines(currentFile));

        if (lines.size() < maxEntriesPerFile) {
            lines.add(newRecord);
            Files.writeString(currentFile, String.join("\r\n", lines));
        } else {
            int newIndex = indexOf(currentFile) + 1;
            Files.writeString(directory.resolve("audit_" + newIndex + ".txt"), newRecord);
        }
    }
}

from datetime import datetime
from pathlib import Path


class AuditManager:
    def __init__(self, max_entries_per_file: int, directory: Path) -> None:
        self._max_entries_per_file = max_entries_per_file
        self._directory = directory

    def add_record(self, visitor_name: str, time_of_visit: datetime) -> None:
        sorted_files = sort_by_index(list(self._directory.iterdir()))
        new_record = f"{visitor_name};{time_of_visit.isoformat()}"

        if not sorted_files:
            (self._directory / "audit_1.txt").write_text(new_record)
            return

        current_file = sorted_files[-1]
        lines = current_file.read_text().splitlines()

        if len(lines) < self._max_entries_per_file:
            lines.append(new_record)
            current_file.write_text("\r\n".join(lines))
        else:
            new_index = index_of(current_file) + 1
            (self._directory / f"audit_{new_index}.txt").write_text(new_record)

import * as fs from 'node:fs'
import * as path from 'node:path'

export class AuditManager {
  constructor(
    private readonly maxEntriesPerFile: number,
    private readonly directory: string,
  ) {}

  addRecord(visitorName: string, timeOfVisit: Date): void {
    const sorted = sortByIndex(fs.readdirSync(this.directory))
    const newRecord = `${visitorName};${formatTime(timeOfVisit)}`

    if (sorted.length === 0) {
      fs.writeFileSync(path.join(this.directory, 'audit_1.txt'), newRecord)
      return
    }

    const currentFile = sorted[sorted.length - 1]
    const currentPath = path.join(this.directory, currentFile)
    const lines = fs.readFileSync(currentPath, 'utf8').split(/\r?\n/)

    if (lines.length < this.maxEntriesPerFile) {
      lines.push(newRecord)
      fs.writeFileSync(currentPath, lines.join('\r\n'))
    } else {
      const newIndex = indexOf(currentFile) + 1
      fs.writeFileSync(path.join(this.directory, `audit_${newIndex}.txt`), newRecord)
    }
  }
}

逻辑并不复杂，但它和文件系统紧紧绑在一起，很难测：测试前要把文件摆到正确的位置，测试后要读出来检查，再清理掉。 文件系统是共享依赖，测试没法并行；它也让测试变慢；你还得保证工作目录在本机和构建服务器上都存在且可访问。

第 1 版：用 Mock 把测试和文件系统解耦

常规解法：把所有文件操作抽成一个接口，通过构造函数注入 AuditManager，测试时 Mock 这个接口。

ⓘ 这里用 Mock 合理吗？

合理。应用创建的文件是最终用户看得见的（他们会用别的程序，哪怕是记事本，去读这些文件）。 所以与文件系统的通信及其副作用属于应用的可观察行为 —— 正是第 5 章说的 Mock 的唯一合理用途。

比第 0 版好多了：测试不碰文件系统，跑得快，也不用照看工作目录。但还能更好 —— 这个测试的准备部分很绕，Mock 库再怎么努力，也不如朴素的输入输出好读。

第 2 版：重构为函数式架构

与其把副作用藏在接口后面再注入进来，不如把副作用整个移出这个类。 AuditManager 只负责决定该对文件做什么；新的 Persister 类根据这个决定去动文件系统。

往后还能怎么发展

函数式架构在需求增长时也很好扩展：

  • 删除某位访客的所有记录可能涉及多个文件 → 让方法返回多条指令（FileUpdate[]）。
  • 不保留空文件 → 把 FileUpdate 改名为 FileAction，加一个类型字段区分「更新」还是「删除」。
  • 错误处理变得更简单、更显式 → 把错误放进返回值（比如返回 (FileUpdate, Error)）。应用服务检查到有错误，就不把指令交给 Persister，而是把错误信息返回给用户。

函数式架构的代价

适用性：不是所有流程都能「先读完再决定」

审计系统之所以能用函数式架构，是因为它可以在做决定之前就把所有输入收集齐。但实际流程常常没这么直接： 你可能需要根据决策过程中的中间结果，再去进程外依赖查额外的数据。

举个例子：如果访客过去 24 小时内的到访次数超过某个阈值，就要去数据库查他的访问级别。 你不能把数据库对象直接传给 AuditManager —— 那会引入隐藏输入，它就不再是纯函数，也就不能用基于输出的方式测试了。

ⓘ 协作者 vs. 值

AuditManager 的 addRecord() 用到了 maxEntriesPerFile 字段，它不在方法参数里 —— 这算隐藏输入吗？ 不算。它在构造函数签名里写明了，而且是不可变的，从创建对象到调用方法之间不会变。它是一个值。

数据库对象则不同，它是协作者：它是通往「尚未在内存里的数据」的代理。 函数式核心里的类不应该和协作者打交道，而应该和协作者的工作成果 —— 值 —— 打交道。

性能

受影响的不是测试的性能（基于输出的测试和用 Mock 的测试一样快），而是系统本身： 为了遵循「读 — 决定 — 写」，它需要对进程外依赖做更多调用。最初版本的审计系统不会读取目录下所有文件的内容，最终版本却要读。 这是性能和可维护性之间的取舍，没有通用答案。

代码量

函数式架构要求核心和外壳清晰分离，前期要多写一些代码（虽然最终会降低复杂度）。 不是所有项目都复杂到值得这笔初始投资 —— 业务上不重要、或者本身太简单的代码库，投入永远收不回来。 要有策略地使用函数式架构，把系统的复杂度和重要性考虑进去。

★ 不要为了纯粹而纯粹

在大多数项目里（尤其是用面向对象语言时），你没法让领域模型完全不可变，也就不可能只靠基于输出的测试。 通常是基于输出和基于状态混着用，再加少量基于通信的测试 —— 这完全没问题。

本章的目的不是让你把所有测试都改成基于输出的风格，而是让你把尽可能多、且合理的测试改成这种风格。差别很微妙，但很重要。

小结

  • 基于输出：给 SUT 输入，检查它的输出。前提是没有隐藏的输入输出。基于状态：操作完成后验证系统状态。基于通信：用 Mock 验证 SUT 与协作者的通信。
  • 经典学派偏好基于状态，伦敦学派偏好基于通信，两派都用基于输出。
  • 基于输出的测试质量最高：很少和实现细节耦合，而且短小简洁、最好维护。
  • 基于状态的测试需要额外小心（不要为了测试而暴露私有状态），通常更大、更难维护。辅助方法和值对象能缓解但不能消除这个问题。
  • 基于通信的测试也需要额外小心：只验证跨越应用边界、副作用对外可见的通信。它的可维护性最差。
  • 纯函数没有隐藏的输入输出。副作用和异常是隐藏输出；引用内部或外部状态是隐藏输入。
  • 函数式编程的目标是把业务逻辑和副作用分开。函数式架构通过把副作用推到业务操作的边缘来做到这一点。
  • 函数式架构把代码分成两类：函数式核心做决定；可变外壳提供输入，并把决定转化为副作用。
  • 函数式架构是推到极致的六边形架构。区别在于：六边形架构允许领域层内部有副作用，函数式架构则把所有副作用都推出去。
  • 函数式架构用性能换可维护性，而且会增加初始代码量。不是所有代码库都值得改造，要有策略地使用。

自测

calculateShipping(order) 内部调用了 LocalDate.now() 来判断是否周末加价。它是纯函数吗？怎么改？

不是。当前日期是隐藏输入（引用了外部状态）。把日期作为参数传进去：calculateShipping(order, today)，它就变成纯函数，可以用基于输出的测试了。

为什么说可变外壳「越笨越好」？

外壳里的代码只能用较慢、较贵的集成测试来覆盖。如果外壳里没有分支和判断，少量集成测试就够了；所有复杂逻辑都在核心里，可以用又快又便宜的基于输出的测试大量覆盖。

把审计系统第 1 版（Mock）改成第 2 版（函数式）之后，四大支柱里哪一项变好了？

可维护性。测试不再需要复杂的 Mock 设置，只剩朴素的输入和输出，更短、更好读。其他三项保持不变。
