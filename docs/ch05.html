第 5 章

Mock 与测试脆弱性

有人觉得 Mock 是神器，几乎每个测试都用；有人觉得 Mock 是万恶之源，能不用就不用。 真相在中间：Mock 经常导致脆弱的测试，但有一类场景它不仅能用，而且就该用它。 这一章用第 4 章的尺子，把这条界线划清楚。

本章目标

  • 分清 Mock 和 Stub，记住「永远不要断言与 Stub 的交互」
  • 分清可观察行为和实现细节，以及它们与公开 / 私有 API 的关系
  • 理解六边形架构，以及系统内通信和系统间通信的区别
  • 知道 Mock 只该用在哪里：跨越应用边界、且副作用对外可见的交互

测试替身的种类

测试替身是所有「非生产用的假依赖」的总称。按 Gerard Meszaros 的分法有五种： dummy、stub、spy、mock、fake。看着吓人，其实可以归成两大类：

两类的区别归结为交互的方向：

★ 一字之差

Mock：模拟并检查交互。　Stub：只模拟交互。　这个「检查」就是关键区别，马上你会看到为什么。

Mock（工具）不等于 Mock（测试替身）

「mock」这个词被用得很泛。它有时指任意测试替身，有时指 Mock 框架里的类 / 函数 （Mockito 的 mock()、Python 的 Mock、Vitest 的 vi.fn()）。 同一个工具既能造出 Mock，也能造出 Stub —— 造出来的是什么，看你拿它干什么。

拿工具造一个 Mock（检查向外的调用 —— 发问候邮件）：

@Test
void sending_a_greetings_email() {
    IEmailGateway mock = mock(IEmailGateway.class);     // 用工具造出一个 mock（替身）

    sut.greetUser("user@email.com");

    verify(mock, times(1))                              // 检查 SUT 对替身的调用

不要断言与 Stub 的交互

SUT 对 Stub 的调用不是最终结果的一部分，它只是产生结果的手段：Stub 提供输入，SUT 据此生成输出。 对比上面两个例子：

  • sendGreetingsEmail("user@email.com") 是一个真实的结果，而且对业务人员有意义 —— 「给用户发问候邮件」正是业务希望系统做的事。
  • getNumberOfUsers() 根本不是结果，它是 SUT「如何收集报表所需数据」的内部细节。
@Test
void creating_a_report() {
    IDatabase stub = mock(IDatabase.class);
    when(stub.getNumberOfUsers()).thenReturn(10);
    var sut = new Controller(stub);

    Report report = sut.createReport();

    assertThat(report.numberOfUsers()).isEqualTo(10);
    verify(stub, times(1)).getNumberOfUsers();          // ✗ 不要这样做
}

def test_creating_a_report():

    sut = Controller(stub)

    report = sut.create_report()

    assert report.number_of_users == 10
    stub.get_number_of_users.assert_called_once()       # ✗ 不要这样做

  const sut = new Controller(stub)

这种「验证不属于最终结果的东西」的做法叫过度指定（overspecification）。 哪天你给报表加了缓存，或者改成一次查询取回多个数字，报表完全正确，这个测试却红了。

ⓘ 一个替身可以同时是 Mock 和 Stub

第 2 章伦敦风格的测试里，storeMock 就是这样：给 hasEnoughInventory() 设置预设答案（Stub 的角色）， 又验证 removeInventory() 的调用（Mock 的角色）。注意这是两个不同的方法，所以没有违反「不断言 Stub 交互」的规则。 这种两者兼具的替身仍然叫 Mock —— 总得选一个名字，而「是 Mock」这个事实更重要。

Mock / Stub 与命令 / 查询

命令查询分离原则（CQS）说：每个方法要么是命令，要么是查询，不要两者都是。 「问一个问题不应该改变答案。」

当然不是所有方法都能遵守 CQS —— 经典的例外是 stack.pop()，它既移除栈顶元素又把它返回。但能遵守就尽量遵守： 这样只看方法签名就知道它干什么。

可观察行为 vs. 实现细节

第 4 章说过：测试产生误报，是因为它和实现细节耦合了；唯一的出路是只验证可观察行为，关注「做了什么」而不是「怎么做的」。 那么到底什么算实现细节，什么算可观察行为？

可观察行为 ≠ 公开 API

所有生产代码都可以沿两个互相独立的维度分类：

维度怎么区分
公开 API vs. 私有 API语言的访问修饰符：public / private；Python 的下划线前缀约定；TS 的 export 与 private
可观察行为 vs. 实现细节看代码是否直接帮助客户端达成它的某个目标
可观察行为（observable behavior）

一段代码要算作可观察行为，必须做到以下两件事之一：

  • 暴露一个操作，帮助客户端达成它的某个目标。操作是执行计算或产生副作用（或两者兼有）的方法。
  • 暴露一个状态，帮助客户端达成它的某个目标。状态是系统当前的情况。

两件都没做的代码，就是实现细节。

注意：一段代码是不是可观察行为，取决于它的客户端是谁、客户端的目标是什么。 「客户端」可以是同一代码库里的调用方、外部应用，或者用户界面。

💡 判断是否泄漏的经验法则

如果客户端为了达成一个目标，需要在这个类上调用不止一个操作，那这个类很可能泄漏了实现细节。 理想情况下，一个目标应该用一个操作就能完成。上面的例子里，修复前是两步，修复后是一步。 （这和第 3 章「执行段应该只有一行」是同一件事的两面。）

设计良好的 API 与封装

泄漏实现细节和破坏不变量总是如影随形：原来那个 User 不仅泄漏了细节，还没守住封装 —— 客户端完全可以绕过规范化，直接塞一个 200 字符的名字进去。

为什么封装对长期可维护性这么关键？因为复杂度。如果代码的 API 不能引导你「什么能做、什么不能做」， 你就得把大量信息记在脑子里，才能保证新改动不引入不一致。你不可能永远做对 —— 所以，把做错的可能性本身消除掉。封装和单元测试服务于同一个目标：让项目可持续地增长。

ⓘ Tell-Don't-Ask（告诉，别询问）

Martin Fowler 提出的原则：把数据和操作这些数据的函数捆在一起。可以把它看作封装的推论 —— 隐藏实现细节让类的内部不暴露在客户端面前，减少被破坏的风险； 捆绑数据和操作确保这些操作不会违反类的不变量。

例子二：泄漏了一个「状态」

还记得第 4 章的 MessageRenderer 吗？它那个公开的 subRenderers 集合就是泄漏出来的状态。 客户端的目标是渲染 HTML，它只需要 render() 方法。 第 4 章那个脆弱的测试之所以脆弱，恰恰因为它绑在了这个泄漏的细节上。

★ 好的 API 设计会自动改善测试

把所有实现细节设为私有之后，你的测试别无选择，只能去验证代码的可观察行为 —— 它们的抵抗重构能力自动就上去了。 由此还能得出一条准则：只暴露绝对最少的操作和状态。

六边形架构

一个典型的应用由两层组成：

层职责可以这样理解
领域层（domain）业务逻辑 —— 应用存在的根本原因，也是它区别于其他应用的地方领域知识的集合：怎么做（how-to）
应用服务层（application services）在领域层和外部世界之间协调：从数据库取数据、调用领域对象、保存结果业务用例的集合：做什么（what-to）

这个由 Alistair Cockburn 提出的架构强调三点：

  1. 领域层和应用服务层的关注点分离。领域层只负责业务逻辑，不管别的；应用服务层不包含任何业务逻辑，只负责「翻译」和「协调」。
  2. 应用内部的依赖单向流动：从应用服务层指向领域层。领域层的类只能依赖彼此，不能依赖应用服务层。领域层应该与外部世界完全隔离。
  3. 外部应用通过应用服务层维护的公共接口连接进来。谁都不能直接访问领域层。

可观察行为是分形的

每一层都有自己的可观察行为和实现细节。「设计良好的 API」这个原则是分形的：对一整层成立，对一个类同样成立。 当每一层都隐藏了自己的实现细节时，测试也会呈现出分形结构：

对领域类来说，客户端是应用服务；对应用服务来说，客户端是外部调用者。 可观察行为从外层向中心流动，每一层的可观察行为都保持着和某个业务用例的联系。 这就解释了前面反复强调的那句话：每个测试都应该能追溯到一条业务需求；追溯不到，就说明它绑在了实现细节上。

系统内通信 vs. 系统间通信

为什么系统内通信是实现细节？领域类为了完成一个操作而彼此协作的方式，不属于它们的可观察行为，和客户端的目标没有直接联系。

为什么系统间通信不是？你的系统如何与外部世界对话，构成了系统作为一个整体的可观察行为，是它必须始终遵守的契约。 根源在于各个应用是各自独立演进的，必须保持向后兼容：不管你内部怎么重构，发到消息总线上的消息结构不能变， 调用 SMTP 服务的参数个数和类型不能变 —— 否则外部应用就看不懂了。

实例：一次购买

业务用例：顾客尝试从商店购买商品。如果库存足够，则 ① 从商店扣除库存；② 给顾客发一封收据邮件；③ 返回确认。

public class CustomerController {
    private final CustomerRepository customerRepository;
    private final ProductRepository productRepository;
    private final Store mainStore;
    private final IEmailGateway emailGateway;
    /* 构造函数略 */

    public boolean purchase(int customerId, int productId, int quantity) {
        Customer customer = customerRepository.getById(customerId);
        Product product = productRepository.getById(productId);

        boolean isSuccess = customer.purchase(mainStore, product, quantity);

        if (isSuccess) {
            emailGateway.sendReceipt(customer.getEmail(), product.getName(), quantity);
        }
        return isSuccess;
    }
}

class CustomerController:
    def __init__(self, customer_repository, product_repository,
                 main_store: Store, email_gateway: EmailGateway) -> None:
        self._customer_repository = customer_repository
        self._product_repository = product_repository
        self._main_store = main_store
        self._email_gateway = email_gateway

    def purchase(self, customer_id: int, product_id: int, quantity: int) -> bool:
        customer = self._customer_repository.get_by_id(customer_id)
        product = self._product_repository.get_by_id(product_id)

        is_success = customer.purchase(self._main_store, product, quantity)

        if is_success:
            self._email_gateway.send_receipt(customer.email, product.name, quantity)
        return is_success

export class CustomerController {
  constructor(
    private customerRepository: CustomerRepository,
    private productRepository: ProductRepository,
    private mainStore: Store,
    private emailGateway: IEmailGateway,
  ) {}

  purchase(customerId: number, productId: number, quantity: number): boolean {
    const customer = this.customerRepository.getById(customerId)
    const product = this.productRepository.getById(productId)

    const isSuccess = customer.purchase(this.mainStore, product, quantity)

    if (isSuccess) {
      this.emailGateway.sendReceipt(customer.email, product.name, quantity)
    }
    return isSuccess
  }
}

  expect(storeMock.removeInventory).toHaveBeenCalledWith(Product.Shampoo, 5)   // ✗ 系统内通信
})

对应原书 Listing 5.11

removeInventory() 这个调用没有跨越应用边界：调用方和被调用方都在应用内部。它也不是帮助客户端达成目标的操作或状态。 这两个领域类的客户端是 CustomerController，目标是「完成一次购买」。和这个目标直接相关的只有两个成员： customer.purchase()（发起购买）和 store.getInventory()（查看购买完成后的状态）。 removeInventory() 只是通往目标路上的一个中间步骤 —— 实现细节。

重新审视两个学派

现在可以说清楚为什么本教程偏向经典学派了。伦敦学派鼓励对除不可变依赖以外的一切使用 Mock， 而且不区分系统内通信和系统间通信。于是测试既检查类与类之间的通信，也检查应用与外部系统的通信 —— 前者让测试和实现细节耦合，丧失抵抗重构的能力。而这项指标基本是二元的，丢了它，测试就近乎一文不值。

经典学派好得多：它只主张替换测试之间共享的依赖，而这几乎总是进程外依赖（SMTP 服务、消息总线等）。 但它对系统间通信的处理也不完美 —— 它同样鼓励了过度使用 Mock，只是程度轻一些。

不是所有进程外依赖都该 Mock

★ 关键细分

如果一个进程外依赖只能通过你的应用来访问，那么与它的通信就不属于你系统的可观察行为。 一个从外部观察不到的进程外依赖，实际上就是你应用的一部分。

必须保持与外部系统的通信模式，是因为你没法让它们和你的应用同时变更：它们有自己的发布节奏，或者干脆不归你管。 但如果你的应用是某个外部系统的唯一入口，没有任何客户端能直接访问它，向后兼容的要求就消失了 —— 你可以把它和应用一起部署，客户端毫无感知。

应用数据库就是典型例子。你想拆表、改存储过程的参数类型，甚至整个换成另一种存储机制，都没有人会发现。 给这种依赖用 Mock，同样会导致脆弱的测试 —— 你不会希望每次拆一张表，测试就红一片。

ⓘ 那数据库怎么测？

不 Mock 数据库，又不想牺牲反馈速度，怎么办？这是接下来几章的主题： 第 6、7 章讲怎么把业务逻辑和数据库访问分开，让大部分测试根本不碰数据库；第 8、10 章讲怎么用真的数据库写集成测试。

「Mock 验证的是行为」？多数时候不是

🧠 神经元的比喻

常听人说 Mock 是用来「验证行为」的。绝大多数情况下并不是。每个类为了达成目标如何与相邻的类交互，和可观察行为没有关系，那是实现细节。

验证类与类之间的通信，就好比通过测量大脑里神经元之间传递的信号来推断一个人的行为。这个粒度太细了。 别人请你帮忙时，并不关心你脑子里哪些神经元亮了，他只关心你帮没帮上。

只有当 Mock 验证的是跨越应用边界的交互，并且这些交互的副作用对外部世界可见时，它才和行为有关。

小结

  • 测试替身有五种（dummy、stub、spy、mock、fake），归为两类：Mock（mock、spy）和 Stub（stub、dummy、fake）。
  • Mock 模拟并检查向外的交互（SUT 调用依赖以改变其状态）；Stub 只模拟向内的交互（SUT 调用依赖以获取数据）。
  • Mock（工具）是 Mock 库里的类，可以用来创建 Mock（替身），也可以创建 Stub。
  • 断言与 Stub 的交互会导致脆弱的测试：那不是最终结果，而是通往结果的中间步骤。
  • CQS 原则：方法要么是命令，要么是查询。替换命令的替身是 Mock，替换查询的替身是 Stub。
  • 代码可按两个维度分类：公开 / 私有 API，可观察行为 / 实现细节。可观察行为 = 暴露了帮助客户端达成目标的操作或状态。
  • 设计良好的代码：可观察行为与公开 API 重合，实现细节藏在私有 API 后面。
  • 封装是保护代码不被破坏不变量。泄漏实现细节往往意味着封装被破坏。
  • 六边形架构：每个应用是一个六边形，由领域层和应用服务层组成；依赖单向地从应用服务层指向领域层；外部应用只能通过应用服务层接入。
  • 系统内通信是实现细节；系统间通信是可观察行为 —— 只有通过你的应用才能访问的外部系统除外，与它们的交互也是实现细节。
  • 用 Mock 断言系统内通信会导致脆弱的测试。Mock 只在用于系统间通信、且副作用对外可见时才是合理的。

自测

测试里有这样一行：verify(repository).findById(42)。这是好的做法吗？

不是。findById 是查询，替换它的替身是 Stub。断言与 Stub 的交互属于过度指定 —— 它验证的是 SUT 如何获取数据，而不是最终结果。

你的订单服务处理完订单后，会往公司的消息总线上发一条 OrderPlaced 消息，下游有三个团队在消费它。这个调用该不该 Mock？

该。这是跨越应用边界的系统间通信，副作用对外可见，消息的结构是你和其他团队之间的契约，重构后必须保持不变。

一个类有 public calculateTax() 和 public applyTax()，调用方每次都得先调前者再把结果传给后者。问题在哪？

客户端为了一个目标（让订单含税）需要调两个操作，说明 calculateTax 很可能是泄漏的实现细节。应该让 applyTax() 内部自己去算。

动手练习

  1. 实现本章的 CustomerController 及相关类，写出「合理的 Mock」那个测试。 然后把 Customer.purchase 的内部实现换一种写法（比如不调用 hasEnoughInventory），确认测试依然是绿的。
  2. 在你的项目里搜索所有 verify / assert_called / toHaveBeenCalled。 给每一处标上：被验证的调用是系统内的还是系统间的？是命令还是查询？
  3. 挑一个你写的类，列出它所有的公开成员。对每一个问：它直接帮助了哪个客户端达成哪个目标？答不上来的，考虑把它设为私有。
  4. 画出你当前项目的「六边形」：中间是什么？有哪些外部系统？哪些是只有你的应用才能访问的？
